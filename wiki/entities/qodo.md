# Qodo

Qodo 是一家以 AI 代码完整性与测试为核心业务的公司（前身为 CodiumAI）。在《[202604231830]从可观测到可理解用UModel构建Agent原生的代码知识图谱》的"代码理解的五种范式"框架中，Qodo 被列为范式三（Code Graph + RAG 混合）的代表厂商之一。

> [!note] 口径说明
> 公司归属（前身为 CodiumAI、以 AI 代码完整性与测试为主业）为可独立核验的公开背景；下列技术细节均来自上述文章记载，未含独立核验。

## 技术栈（据文章）

- **Qodo-Embed-1**：自研嵌入模型，1.5B 参数在 CoIR 基准上超越 7B 竞品（基准名给出、来源未给、无口径声明 → 已记入 [[ai工程量化效果声明追踪]]）；采用合成数据训练，捕获语法、变量依赖、控制流与 API 用法。
- **客户端代码图**：调用图、继承关系、跨语言链接。
- **服务端索引**：向量库 + 设计文档 + 架构图 + PR/commit 历史。
- **AST 感知切片**：递归切分 + 回填 import 与类定义。

## 在文章论证中的位置

范式三在向量索引上叠加代码结构图，回应"代码不只是文本，还是有结构的图"。Qodo 与 [[augment-code|Augment Code]] 同属此范式，被文章用作"混合路线仍触顶"论点的证据。

### 四大系统性边界

文章认为该范式仍存在四大系统性边界（详见 [[代码理解的五种范式]]）：

1. **图限于代码域**：代码图与运维图割裂
2. **查询能力受限**：仅邻居查找与短路径
3. **索引绑定 IDE 实例**：不可团队复用，非全局资产
4. **缺时序维度**：构建/部署/测试/事件日志等不在图中

这四条边界是 UModel 三维度设计（见 [[代码知识图谱三维度]]）的直接批判靶子。

## 与 [[umodel|UModel]] 的对照

Qodo 所代表的范式三与 [[umodel|UModel]]（范式五）的差异集中在：

| 维度 | 范式三（Qodo / [[augment-code|Augment Code]]） | [[umodel|UModel]]（范式五） |
| --- | --- | --- |
| 查询语言 | 受限于 RAG 框架 | SPL / graph-match 图灵完备 |
| 置信度模型 | 无分层标注 | `__confidence__` + `__extraction_method__` |
| 域覆盖 | 代码域 | 跨域 EntitySetLink |
