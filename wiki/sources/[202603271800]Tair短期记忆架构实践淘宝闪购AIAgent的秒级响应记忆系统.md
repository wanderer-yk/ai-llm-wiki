# Tair 短期记忆架构实践：淘宝闪购 AI Agent 的秒级响应记忆系统

- **作者**：阿里云数据库 Tair 团队（署名"阿里云数据库Tair"）
- **发布渠道**：微信公众号「千问AI平台」（IP 属地浙江）
- **发布时间**：2026-03-27 18:00

## 背景与问题

本文以[[淘宝闪购]]与[[qwen|千问]]合作的"一句话点外卖"场景为背景：用户说一句"帮我点杯霸王茶姬的伯牙绝弦，少糖去冰，送到公司"，背后的 AI Agent 需在数秒内完成意图识别、地址解析、商品搜索、规格匹配、加购下单等一系列操作，涉及多轮对话与多次工具调用，每一步都依赖对"之前发生了什么"的准确记忆。业务目标是将传统 3-5 分钟的点单耗时压缩至 30 秒以内。[[tair]] 在该系统中承担 Agent 短期记忆层的核心存储角色。

## 核心论点一：延迟是记忆层的扩展性分水岭

依据 Little 定律（并发数 ≈ QPS × 延迟），记忆访问延迟从 5ms 上升到 50ms，系统在途请求数膨胀 10 倍，可能迅速耗尽连接、线程和队列资源；而 Agent 每轮对话涉及多次记忆读写，延迟被反复叠加放大，最终可能引发排队、超时乃至雪崩。原文强调："5ms 和 50ms 的差别，不是体验上的优化，而是系统能否稳定扩展的分水岭。"这也是淘宝闪购 Agent 选用 Tair 的核心原因——自研多线程内核提供稳定的低延迟。**注意：此论证属逻辑推演，原文无实测压测数据**（详见 [[little定律并发放大]]）。

## 核心论点二：双类记忆数据模型

短期记忆按**消费者**划分为两类（详见 [[模型记忆与业务上下文记忆分离]]）：

### 模型记忆（Model Memory）—— List

供大语言模型消费的对话历史，每会话一个 Key：

```text
Key:  memory:model:{sessionId}
Type: List
示例：[{"role":"user","content":"帮我点杯奶茶"}, {"role":"assistant","content":"为你找到附近3家奶茶店...","cards":[...]}, ...]

RPUSH memory:model:{sessionId} "{对话记录JSON}"      # 每轮对话结束后追加
LRANGE memory:model:{sessionId} -{N} -1              # 推理前读取最近 N 轮
EXPIRE memory:model:{sessionId} 1800                 # 会话过期 30 分钟
```

说明：写入前将原始数据（文本+卡片富媒体）转换为自然语言格式，以减少 Token 消耗。

### 业务上下文记忆（Business Context Memory）—— Hash

供工具层/意图处理器消费的结构化业务状态：

```text
Key:  memory:context:{sessionId}
Type: Hash
Field 结构：
{
  "session":      "{会话元信息: 用户ID、渠道、会话阶段等}",
  "search":       "{搜索状态: 当前query、搜索结果、推荐商品列表等}",
  "order":        "{订单状态: 购物车内容、已选SKU、商品数量等}",
  "conversation": "{对话状态: 当前意图、上一轮意图、意图切换标记等}",
  "coupon":       "{优惠信息: 可用优惠券列表、已选优惠等}",
  "bizState":     "{业务状态: 收货地址、配送方式、支付状态等}"
}

HSET memory:context:{sessionId} bizState "{更新后的业务状态JSON}"   # 单独更新某个子模块
HGET memory:context:{sessionId} order                               # 读取特定子模块
HGETALL memory:context:{sessionId}                                  # 一次性读取所有上下文
EXPIRE memory:context:{sessionId} 1800                              # 设置过期时间
```

说明：Hash 的 field 级读写使各业务模块独立更新、互不干扰，避免"读完整 JSON 再回写"的竞争（如搜索模块更新推荐结果时不影响订单模块写入购物车）。

### 数据结构选型对比（原文表格，逐字保留）

| 记忆类型 | Redis 数据结构 | 选型理由 |
|---------|--------------|---------|
| 对话历史 | List | 对话是有序时间序列，List 支持有序追加（RPUSH）和范围读取（LRANGE） |
| 业务上下文 | Hash | 按领域拆分为多个字段，支持 field 级独立读写，避免读写竞争 |
| 会话状态标记 | String | 原子性状态标记（如会话阶段），操作简单 |
| 分布式锁 | String | 基于 SET NX EX 实现，保障并发安全 |

## 核心论点三：会话级分布式锁并发控制

同一会话可能因用户快速连续发消息、流式响应中再次输入而并发写入。解决方案（详见 [[会话级分布式锁]]）：

```text
SET lock:memory:{sessionId} {requestId} NX EX 3     # 锁超时 3 秒
HSET memory:context:{sessionId} order "{...}"
RPUSH memory:model:{sessionId} "{...}"
EVAL "if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) else return 0 end"  # 只释放自己持有的锁
```

锁粒度为会话级（sessionId），不同用户会话间完全无锁竞争；秒级超时防止持锁进程异常退出导致长期阻塞。

## 核心论点四：10 倍峰值弹性方案（支撑千问春节红包活动）

- **多线程内核**：Tair 企业版内存型读写性能宣称同规格开源 Redis 的 **3 倍**（厂商自报）。
- **读写分离**：Agent 记忆呈读多写少，读写比 **5:1～10:1**；集群读写分离支持只读副本 1～9 个/分片、分片 2～256 个水平扩展。

```text
日常流量：
  集群 8 分片，每分片 1 只读副本 → 满足日常业务需求

春节活动（5～10 倍峰值）：
  方案一：每分片扩展至 5 只读副本 → 读吞吐线性提升
  方案二：集群扩至 16 分片 + 每分片 3 只读副本 → 读写能力同步翻倍
```

- **无感扩缩容**：详见 [[tair无感扩缩容]]。
- **带宽**：集群可通过增加 LB 扩展（单 LB 上限 20Gbps，分片数超过 8 个时可新增且不断连）；弹性突发带宽详见 [[弹性突发带宽]]。
- **TTL 生命周期**：会话 Key 设 30 分钟 TTL，实现"高峰扩、低谷缩、过期自动清理"。
- **结果声明**：春节洪峰期间 P99 延迟保持毫秒级（厂商自报）。

### 原文总结表（逐字保留）

| 能力 | 实现方式 | 解决的问题 |
|------|---------|-----------|
| 低延迟访问 | Tair 内存读写 | 匹配 Agent 对话链路的实时性要求 |
| 灵活的数据建模 | List + Hash + String 组合 | 适配对话历史、业务上下文等不同记忆类型 |
| 生命周期管理 | TTL 自动过期 | 会话结束后自动清理，降低运维成本 |
| 并发安全 | 分布式锁（SET NX EX） | 保障多请求并发写入时的数据一致性 |
| 弹性抗压 | Pipeline + 读写分离 | 支撑春节活动 10 倍峰值流量，业务无感弹性 |

## 批评性评估（证据强度）

- **厂商自报声明**：3 倍于开源 Redis、支撑 10 倍峰值、P99 毫秒级、288MB/s 等数字均无第三方基准、无规格/负载模型披露，应登记入 [[ai工程量化效果声明追踪]]。
- **"无感扩缩容"内部张力**：文章同段承认迁移最终阶段对应 Slot 的写请求"时延会略有增加"。对刚论证过延迟放大效应的 Agent 链路，"无感"是近似说法。
- **技术缺口**：3 秒锁超时 vs LLM 推理+多次工具调用普遍超过 3 秒，锁超时释放可能引入并发写，文章未提及锁续期/watchdog 机制。
- **未披露细节**：富媒体转自然语言的转换由谁执行（模型/规则）、自身是否构成额外延迟与成本。
