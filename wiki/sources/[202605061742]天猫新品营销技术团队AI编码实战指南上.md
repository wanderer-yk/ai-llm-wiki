## 一、现状与问题诊断

### 四大痛点（原文 2×2 表，逐字保留）

| 写不对 | 写不好 |
|---|---|
| AI 没有完全按照用户意图完成功能，轻则存在缺陷，重则无法运行 | AI 产出的代码不符合要求，包括但不限于代码质量/代码风格/实现方案 |
| **写不了** | **改不动** |
| 项目隐含逻辑太多，文件结构复杂，耦合度高，AI 完全无法按预期完成任务（如一些内部 SDK 工具库，使用说明都在外部文档，AI 无法直接通过代码理解如何使用，自然无法写出对应的使用代码） | 在某些迭代场景中，AI 一直无法输出正确结果，在错误中不断循环，甚至还可能改坏其他部分，此时只能人工介入。而介入后，想要完成修改则需要面对 AI 短时间内生成的大量代码，反而导致效率下降，使用者完全丧失了对项目的把控 |

详见 [[AI生码四大痛点]]。归因分析见 [[AI生码五维归因框架]]（源文章节「导致问题的主要因素与解法」，因素 1–5：隐含信息过多 / 用户输入不精准 / 任务复杂度高 / 缺少自检环节 / 模型与 Agent 差异限制）。

## 二、方法论与优化思路

### 三大核心思想

- [[最大化复用]]——复用提升生码确定性、降低任务复杂度、提高掌控度；子项：模块优先（明确输入输出的标准可复用模块/可信任的黑盒）→ 胶水编程（已有模块+最小胶水代码，代码只负责组合、调用、封装、适配）→ 工作流复用（可标准化/重复性强/复杂度高的流程沉淀为标准 AI 工作流，载体包括但不限于文档、MCP、Skill）
- [[文档先行]]——"文档是 AI Coding 的第一要素，PRD 即单测，文档即代码，优先修改文档而不是代码……并不要求大而全"；对 Spec-kit 的实测校准："理想状态下是有一份可以和代码 100% 互相转换的文档，但是现在实测下来很难达到这种理想状态（没有可以完美描述项目的文档，文档也没法恰好转换到代码），最好的策略还是够用就行"
- [[二八定律]]——20% 时间完成 80% 任务；蜜月期（0%→80%，全新独立逻辑极快）vs 深水区（80%→100%，复杂上下文/边缘 Case/旧逻辑耦合时断崖式下跌）；效率双重点：提高前 80% 的质量 + 提高后 20% 的效率

### 五步模型与掌控介入（逐字保留）

> 一次 AI Coding 的执行流程大概可以概括为：理解用户意图 > 查找上下文 > 设计执行方案 > 代码生成 > 简单校验。

> 由于 LLM 的随机性，每一个执行环节都包含着无限的可能，而掌控 AI 生码，就是在每个环节都进行明确声明与介入，从而保障 AI 按照自己的预期进行产出。

> 这部分主要是基于每个节点进行优化方案讲解，并不代表实际需要严格按照这个步骤进行流程拆分，按需选用即可，具体实践中的取舍和选型在后面的实战案例中会详细说明。

详见 [[AI-Coding五步模型]] 与 [[掌控AI生码环节介入论]]。

### 全流程节点

节点链：前置准备 → 开发前（明确需求内容 + 任务设计与拆分）→ 开发中（新型需求：过程文档/上下文窗口管理/严格解耦/自检机制 + 持续失败场景处置 + 单会话注意力丢失陷阱）→ 开发中（迭代型需求）→ 完成后（资产沉淀）。详见 [[全流程节点]]、[[前置准备]]。

**迭代型需求四大常见问题（原文表，逐字保留）**：

| 场景 | 发生了什么 | 后果 |
|------|-----------|------|
| 改一个功能，坏了另一个 | 添加删除功能时，不小心影响了添加功能 | 花时间排查，可能越改越乱 |
| 想回到"昨天那个版本" | 昨天的代码能用，今天改了一堆，全坏了 | 找不到昨天的版本 |
| 试了三种方案，想回到第一种 | 第一种方案其实最好，但已经被覆盖了 | 要么重写，要么将就 |
| AI 改了不该改的地方 | 让 AI 改一个文件，它顺手改了其他文件 | 不知道哪些被改了 |

迭代型六策略：①及时约束防 AI 目标漂移；②传入精准上下文减少搜索范围；③复杂迭代及时 git 版本管理（多方案对比用分支 / 版本管理用 commit）；④迭代成功率主要依赖仓库架构解耦程度，改不动时依靠极致性的解耦；⑤人工必须介入时采用"人工提供方案，AI 执行改动"的半自动方案（示例：移除函数中硬编码的业务逻辑改为外部传参，改好后同步修改所有调用该函数的代码）；⑥实在无法继续迭代时，借助已有功能文档进行整体代码重构（无文档则让 AI 总结现状，最好从模块向上重构）。"其余部分同新型需求"。

### 出码准确率语料阶梯（原文表，逐字保留）

| 场景 | 出码准确率 | 介入成本 |
|------|-----------|---------|
| AI 自由发挥 | 70% | 高 |
| 有语料的三方包 | 80% | 低 |
| 私有包 + 调用规范 | 95% | 低 |

详见 [[出码准确率语料阶梯]]。

### Chat 场景快捷调优手段（逐字四条）

1. 配置基础的项目规则，并根据实际的问题对其进行一些调优；
2. 提前设计较为解耦的项目结构，提高 AI 迭代的成功率；
3. 接入一些辅助的MCP工具和已验证过的Skills进行能力辅助；
4. 使用一些基础的提示词流程或模版，尽可能描述清楚需求。

## 三、分场景实战案例

### 需求驱动型 vs 工程主导型（七维度对比表，逐字保留）

| 维度 | 需求驱动型 | 工程主导型 |
|------|-----------|-----------|
| 特点 | 强调"要什么功能"；AI 自主决策技术实现；人工介入少，关注结果 | 强调"怎么实现"；人工深度参与实现方案决策；人工介入多，关注代码质量 |
| 代码规范度要求 | 低 | 高 |
| 验收标准 | 低 | 高 |
| 隐含知识量 | 低 | 高 |
| 项目复杂度 | 低 | 高 |
| AI 扮演的角色 | 功能开发者 | 编码辅助员 |
| 案例 | 小二后台页面 / 研发自用工具 | 线上C端页面 / 商家端页面 |

详见 [[需求驱动型与工程主导型]]。

### 需求驱动型（DO WHAT）

三关注点：完全阐明需求点防 AI 臆造偏离；辅助手段保证代码质量以提高迭代成功率；留出人工介入空间，不产出难以介入的代码。

**案例一（小二端列表页）**：按"验收卡口与用户需求"分 [[三种实现风格]]——能用就行型 / 较有要求型 / 严格型（已有常规列表查询页实现模版）。三风格对照表（逐字保留）：

| 维度 | 能用就行型 | 较有要求型 | 严格型（已有一份关于常规列表查询页的实现模版） |
|------|-----------|-----------|------|
| 实现路径 | ① 直接输入接口文档，其他完全由 AI 进行完善；② 提供少量实现限定（使用 tao-design），或者由 AI 自行读取仓库代码进行判断 | ① 提供基础的代码实现规范与文件模版；② 按要求提供 prd，并进行一定的结构化优化 | ① 提供基础的代码实现规范与文件模版；② 按要求提供 prd，并进行一定的结构化优化；③ 提供更严格的具体实现绑定，通过严格的代码模版限定产物格式 |
| 样式 | 组件库兜底基本风格 | 组件库兜底基本风格；功能符合用户要求 | 符合视觉稿/平台规范要求；功能符合用户要求 |
| 可迭代性 | 非复杂情况下可一定程度迭代 | 可一定程度迭代 | 可长期多次迭代（高亮强调） |
| 代码质量 | 组织格式随机，可能产出单个巨型文件，人工介入成本高 | 较规范、轻度解耦，部分逻辑仍留主文件，人工介入成本中 | 完全按统一思路/组件完成，功能实现分散在各个子组件，代码严格解耦（原文作"解藕"），人工介入成本低。附注：这种严格的解耦模式人工编写成本可能过高，交给 AI 编写则是适得其所 |

**问题调试三件套**：[[分支控制]]（AI 生码是覆盖式的，微调期须及时 Commit 存档；工具回退功能"不能过于信任"）；[[报错调试]]（常规报错直接复制给 Agent 自行调试，可解决率 80%——自报口径；未解决部分主要来自三方库内部报错需特判）；[[数据调试]]（示例 prompt 逐字："xxxx显示为空，帮我在关键节点新增console日志，以便我复制给你排查问题"；页面调试也可经 MCP 工具或 cursor 的 browser tab）。

**案例二（中型迭代：货品管理动态属性）**：属性展示/属性筛选/属性编辑三功能。明确需求工作流：接口文档 + 需求 → AI 创建产品文档 → 人工核对后进入下一步（复杂交互先审 AI 拟定的实现方案）。AI 扩写 PRD《货品属性功能需求文档》"二、数据类型说明"表（逐字保留）：

| 属性类型 | 筛选方式 | 编辑控件 |
|---------|---------|---------|
| STRING | 文本匹配 或 枚举多选 | 文本输入框 或 下拉多选 |
| TEXT | 文本匹配 | 多行文本输入框 |
| NUMBER | 数值范围 | 数字输入框 |
| BOOLEAN | 布尔值 | 开关组件 |
| TIMESTAMP | 时间范围 | 日期时间选择器 |
| TIMESTAMP_RANGE | 时间点 | 日期时间范围选择器 |

3.2 迭代效果对比三条件实验（能用就行初版+仅原始需求 / 较有要求型初版+仅原始需求 / 较有要求型初版+人工阐明详细文档）：功能维度分别为"基本符合要求 / 做出来了但不太合预期 / 基本符合要求"；代码质量维度暴露量化阈值——"迭代后主文件行数达到 600 行，基本丧失人工介入可能性"。双结论（逐字）："清晰的prd保证功能符合预期：如果没有预先对AI想要产出的内容进行审核，很容易发生偏离导致结果不合预期"；"优质的代码提高迭代效率：初始的代码对后续迭代的成功率有较大影响，如果源代码已经在堆砌代码，后续迭代时 AI 也会延续这个风格，导致迭代成功率急速下降，且丧失人工介入修改代码的空间"。

### 工程主导型（HOW TO DO）

三关注点（逐字）：①代码需要严格符合工程质量；②编写者要保留对代码大部分的掌控度，且产出内容人工可介入度高；③对于这类复杂度高/隐含知识多的项目，怎么让 AI 可以做/知道做。

红字步骤链五步（案例 C 端归属由三证据聚敛确认：相关埋点 + C 端视觉 + "完整地掌握了淘内C端业务仓库下的开发方式"）：

1. **需求背景与实现拆解**——需求内容原文："需要在页面 Feeds 下新增二级类目配置，且商品卡片点击跳转切换到跳转自有中间页（原来是直接跳转商品详情页），完成视觉更新。"双端拆解表（逐字）：

| 服务端 | 前端 |
|--------|------|
| 需要新增一个 ald solution，且支持二级类目召回支持（be 召回时增加参数） | ① 新增二级类目配置项并更改接口参数；② 重写 feeds 组件（原有旧组件不支持多级 tab），修改卡片与 tab 样式；③ 修改卡片跳转逻辑 |

2. **前置知识准备**——隐含知识三源（业务语义 / 内部平台开发模式 / 团队实现规范）；无前置输入则"AI 完全无从下手"。四问清单：①什么是自建的中间页？什么是商品详情页？怎么进行跳转？②后端仓库内怎么新建一个 solution，有没有什么相关的代码规范？③前端仓库要使用什么工具库？一些基础功能如何实现？④Feeds 组件库如何使用？配置项是什么？怎么更改？前置文档编制五原则：AI 生成配合人工修改；渐进式披露；入口文档全而精 + 详细部分另建补充文档；统一读取的存放位置；冷启动耗时但"值得、且未来必须要完成"。效果（逐字）："被前置文档喂饱后，AI很完整地了解了自己该干什么，且完整地掌握了淘内C端业务仓库下的开发方式"。

3. **技术方案产出**——基于知识问答和代码产出技术方案；AI 使用知识库时应列出参考的具体文档以防偏离（引用溯源）；重代码质量项目需人工完整审查修改技术方案（"毕竟线上bug不能让AI背锅"）；限定格式后技术文档不占太多审查时间。

4. **具体执行阶段-解耦实现**——[[视图分离]]：C 端 AI 编码不好用主因是逻辑与视觉耦合度高 + AI 天生缺乏视觉感知力；解法三段式（AI 完成逻辑代码 → 其他方案完成视觉组件 → AI 绑定）；收益包括 CR 压力骤减（购物车组件只审 index.tsx）、AI 代码拆解重构（商卡 400 行组件改造 + D2C 产出新卡片）、视图分离组件库（feeds 模块 tab 渲染交调用方）。

5. **后期沉淀**——三个子节：组件沉淀（逻辑组件复用不受视觉稿限制 + 视觉素材跨项目复用的双向红利）；知识文档迭代（前置文档仍会理解偏离→针对常见问题补充严格约束→运行时及时修正保证文档有效性）；工作流沉淀（review 全流程，按"可标准化/重复性强/涉及文件多"三筛选标准落成简单 Skill，"标准工作流的沉淀可以让 AI 越来越可控"）。"当日常开发场景枚举到80%以后，AI 会越来越像我们延伸出的双手——不是胡编乱造，而是把我们脑海中的代码搬运到它们应该存在的地方"。四条 Skill 化工作项清单（原文照录）：

```text
1. 后端 ald solution 创建，分步修改相应文件；
2. 在前面的基础上，进行前后端流程串联，如：solution -> 接口文档 -> 前端调用函数生成；
3. 前端天马配置项的新增与相应的读取代码生成；
4. 逻辑代码生成 -> 调用D2C工具生成视觉组件 -> 进行逻辑与视图的绑定。
```
