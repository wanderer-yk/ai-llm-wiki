# 别让AI瞎猜了：用Harness Engineering 终结无限返工

## 核心论点

文章提出 [[harness-engineering]] 方法论，核心论点：AI编程的无限返工问题根源在于任务前置准备不完整（而非模型能力不足），解决方案是构建包含五要素（任务入口、执行依据、工具边界、验证反馈、结果记录）的工程化harness，将 agent 从"偶尔帮忙的生成工具"转化为"研发链路中可靠的执行者"。

## 文章结构

1. **为什么Prompt不够了**：分析前后端场景中 agent 的"三重猜测"和"边界五缺失"，论证 Prompt 的三个根本缺陷（一次性、被动、不可积累）
2. **第一性原理**：瓶颈从"谁来写"转向任务说清/边界定住/验证可跑/结果可接；人的注意力应放在判断而非重复补上下文
3. **把协作链路放进项目里**：四层信息落点模型、任务流转五阶段、agent五步标准动作
4. **初始化后的目录结构与使用方式**：六类核心文件规范、五步初始化流程
5. **前端案例**：[[前端三层分离模型]]（执行依据层→状态暴露层→交付实现层）
6. **后端案例**：后端三层模型、[[执行语义冻结]]、验证五层模型
7. **工具不是重点**：职责分层稳定性、工具能力vs工程条件分离
8. **从最小harness开始落地**：六级优先级渐进路线、三阶段落地路线图
9. **适用边界**：轻量处理/启用harness/人判断的三分法

## 关键主张

- AI返工根源是工程条件缺失，不是模型能力不足
- 对 agent 的三个期待（多做/少问/少出错）本质是工程条件问题
- Prompt Engineering 解决"这一轮怎么说清楚"，Harness Engineering 解决"项目里如何持续做对"——两者互补
- [[多源分治策略]]：每类信息有清楚的位置，而非集中到单一来源（与 [[ssot单文档策略]] 形成对比）
- 不替代人的需求判断和架构取舍（明确边界声明）
