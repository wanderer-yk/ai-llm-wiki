# 从可观测到可理解：用 UModel 构建 Agent 原生的代码知识图谱

作者 [[张城]]（署名"元乙"），发布于微信公众号「[[阿里云云原生]]」（IP 属地浙江），2026-04-23 18:30，原创声明。作者自称来自"阿里云云原生可观测团队"，在可观测领域从业十多年。文章的写作背景是 AI Agent（Cursor、Copilot、Claude Code、Codex 等）深度参与软件开发。官方摘要：对比 [[claude-code|Claude Code]]、[[cursor|Cursor]] 等主流方案，指出现有工具三大局限——关系靠猜测、止步代码域、缺时间维度；提出基于 [[umodel|UModel]] 的 Agent 原生代码知识图谱：AST 确定性提取 + 跨域关联，让 Agent 从"找代码"进化到"懂结构"。作者另有前作《如何用 UModel 构建一个会成长的个人 Wiki》（见 [[如何用UModel构建一个会成长的个人Wiki]]，引述内容整理见下文专节）。

## 核心论断

- Agent 驾驭方式沿 Prompt Engineering → Context Engineering → Harness Engineering 演进，但核心问题"Agent 真的理解你的项目吗？"仍未解决。
- 即使最先进的代码索引方案，也还停留在"找到了片段，但不理解结构"的阶段。
- UModel 是阿里云可观测从日志/指标/链路零散数据采集演进到"面向对象、关系和时序的统一建模"的沉淀产物，本文将其迁移到代码理解域，定位为"活的 GIS 系统"。
- **确定性是 RCA 推理链信任前提**：calls 关系若靠 LLM 猜测，整条推理链不可靠。
- **tree-sitter 双用途分野**（[[tree-sitter双用途分野]]）：Cursor 用它做语义切片（产出向量），UModel 用它做结构提取（产出图谱）——"同一个解析器，服务于完全不同的目标"。
- **架构发现非社区检测**（[[架构发现非社区检测]]）：Louvain/Leiden 发现的是聚类，不是架构。
- **Log 是分水岭**：commit_log、build_log、deploy_log、test_log、incident_log 五种 LogSet 让图谱具备时间维度，"只看结构不看历史，等于只看了一帧截图"。
- 收束命题：UModel 用 Entity+Log 从观测运行系统走向理解代码系统；Agent 同时理解结构、历史、生产表现是 AI 原生软件工程的前提。

## 一、问题定义：两大流派与三类共同失效问题

**无索引流派（Agentic Search）**：[[claude-code]] 信奉 Unix 哲学，不做预索引，用 grep/rg/glob 实时搜索。文中引述 Anthropic 内部测试结论（Boris Cherny 公开分享）：agentic search 性能全面超越 RAG（"by a lot"）；Claude Code 早期版本曾用 RAG + 本地向量库，后放弃。

Agentic Search 工作流（原文 verbatim）：

```text
Agent 收到问题
 → Glob: 按文件名模式匹配（近零 token 成本）
 → Grep (ripgrep): 按内容正则搜索（低 token 成本）
 → Read: 读取完整文件（高 token 成本）
 → 判断 → 下一轮搜索或给出答案
```

规模论据：200 文件 TS 项目可行；5 万文件企业级单仓需 30+ 轮工具调用、几万 token，且只能拼出局部视图。

**CodeIndex 流派**：[[cursor]]、Windsurf、GitHub Copilot 走向量索引路线；[[qodo]]、[[augment-code]] 进一步叠加代码依赖图和 commit 历史索引。

Cursor 管线（原文 verbatim）：

```text
代码仓库
  → tree-sitter 解析为 AST
  → 按语义单元切片（函数、类、逻辑块）
  → 生成向量 embedding
  → 存入 Turbopuffer 向量数据库
  → Merkle Tree 跟踪变更，增量同步
```

工程优化：每 10 分钟 Merkle Tree 根哈希比对只重嵌变化文件；团队成员间 92% 代码库相似度可复用索引；`.cursorignore` 控制索引范围。Augment Code 评测指出 Cursor 在 50+ 文件跨文件重构中不一致——前 30 个文件改对，后 20 个因上下文窗口溢出错改。

**两流派共同失败的三类问题**：
1. 影响范围分析：改 pkg/a2a Adapter 接口的影响范围——向量相似度搜不到依赖链、grep 不完整；
2. 跨域故障归因：生产 SLO 破线是否代码变更所致——运维域数据不在图里；
3. 架构边界检查：跨架构边界的异常依赖——架构层级未被建模。

共性需求 = **确定性结构关系 + 跨域实体关联 + 时间维度变更历史**。

## 二、代码理解的五种范式

沿"无状态搜索 → 有状态推理"轴线排列（详见 [[代码理解的五种范式]]）：

1. 范式一 Agentic Search（[[claude-code]]）
2. 范式二 CodeIndex/向量索引（[[cursor]] 等）
3. 范式三 Code Graph + RAG 混合（[[qodo]]、[[augment-code]]）
4. 范式四 CodeWiki/LLM 文档（[[deepwiki]]，对 Agent 呈现"五难"）
5. 范式五 代码知识图谱（[[umodel|UModel]]，"活的 GIS"）

## 三、三维度与 Entity+Log+Link 建模

三个维度的系统性结合（详见 [[代码知识图谱三维度]]、[[entity+log+link三元组建模]]）：

- 确定性 vs 概率性：AST 置信度 1.0 + SPL/graph-match 图灵完备查询；
- 代码域 vs 跨域：EntitySetLink 连接 code/ops/event/req 域；
- 快照 vs 时间线：五种 LogSet 完整时间维度。

UModel 建模构件与代码域映射（原文表格）：

| 构件 | 作用 | 代码域内容 |
|------|------|-----------|
| EntitySet | 实体现态 | 5 种，`repo_id` 复合主键，多仓库共存 |
| LogSet | 时序事件 | commit_log、build_log、deploy_log、test_log、incident_log，经 DataLink 关联 EntitySet |
| MetricSet | 度量指标 | 可观测域原语，代码域用法未展开 |
| EntitySetLink | 结构关系 | contains、imports、calls、extends、describes、belongs_to 共 6 种 |

关键标识符与公式（原文 verbatim）：

```text
Entity ID = md5(repo_id:pk_value)
__confidence__                # 每条关系标注
__extraction_method__         # EXTRACTED / INFERRED / AMBIGUOUS
INFERRED                      # LLM 语义层信息标注，Agent 选择性采信
```

跨域连接示例：`EntitySetLink: code.module ↔ ops.service / event.alert / req.issue`。

Log 时间关联查询实例（SPL 风格）：

```text
这个模块最近一周被谁修改过？   → commit_log WHERE module_path = X AND time > now()-7d
上次部署之后有没有新增 incident？ → deploy_log JOIN incident_log ON time_window
引入这个依赖之后，构建时间变长了吗？ → build_log GROUP BY week，交叉 commit_log 的依赖变更时间
```

## 四、六阶段构建流水线

DETECT → EXTRACT → RESOLVE → BUILD → SYNC → SERVE（详见 [[umodel六阶段构建流水线]]）。实证项目 [[vibeops-agents]]（~2375 个 Go 文件）经 SHA256 指纹增量检测，增量构建秒级、全量数分钟。

RESOLVE 四类跨文件确定性解析（原文 verbatim）：

```text
Go import github.com/org/repo/pkg/a2a → module_path pkg/a2a
方法 receiver type (s *Server) → 归属 code.type pkg/server.Server
调用 s.HandleRequest() → pkg/server.Server.HandleRequest
接口实现 type Adapter struct implements Handler → extends 关系
```

BUILD 四步架构发现（原文 verbatim）：

```text
Step 1: 图构建
  module 为节点，imports + calls + extends 为有向边
  边权重：calls > imports > extends
Step 2: 层次分析
  计算依赖方向性：A→B 且 B↛A → A 在 B 上层
  识别入度 = 0 的顶层入口和出度 = 0 的底层基础设施
Step 3: 社区发现
  Leiden 算法在有向图上发现功能簇
  resolution 参数控制粒度（~150 模块 → ~15 组件）
Step 4: 标注与命名
  基于依赖方向标注层次：API/Gateway、Service/Business、Infrastructure/Utility
  LLM 命名和描述，与项目文档交叉验证
```

SYNC 同步命令（原文 verbatim）：

```bash
Entity 写入: starops umodel post-logs → __entity logstore
Topo 写入:   starops umodel post-logs → __topo logstore
Schema 同步: starops umodel sync（注册 EntitySet/Link 定义）
```

## 五、SERVE：查询工程与 Agent 交互层

**两步查询模式**（详见 [[两步查询模式]]）：graph-match 仅返回 entity_id，先走拓扑取 id 集合，再经 `.entity` 批量拉取业务字段；聚合统计类查询直接 SQL 查 `__topo` logstore。

```bash
Step 1: .topo | graph-match (n1:code@code.module {__entity_id__: '<id>'})
              -[e]->(n2) project n1, e, n2
Step 2: .entity with(domain='code', name='code.module', ids=['id1','id2',..])
```

```sql
SELECT __dest_entity_id__, count(1) as import_count
FROM log WHERE __relation_type__ = 'imports'
GROUP BY __dest_entity_id__
ORDER BY import_count DESC LIMIT 20
```

自报规模：~11000 实体、~19000 条边（含 vibeops-agents 与 starops-cli 两个项目），单次查询端到端延迟百毫秒。

**Agent 交互层 = CLI + Skill，明确不采用 MCP**（详见 [[agent交互层cli+skill]]、[[意图化子命令设计]]、[[token预算优化输出格式]]）：

```bash
code-wiki query <子命令>     # 图谱查询
  ├── search <keyword>       # 实体搜索
  ├── context <name>         # 符号完整上下文
  ├── impact <path>          # 变更影响分析
  ├── callers / callees      # 调用链
  ├── deps / rdeps           # 依赖 / 反向依赖
code-wiki check <子命令>     # 治理检查
  ├── arch                   # 架构违规扫描
  └── hotspots               # 耦合热点
code-wiki ingest             # 构建/更新图谱
code-wiki status             # 健康检查
```

brief 格式输出示例（< 500 tokens，原文 verbatim）：

```text
$ code-wiki query context pkg/a2a
Module: pkg/a2a
  LOC: 1,247 | Language: Go | Component: a2a-protocol
  Summary: A2A protocol implementation for agent-to-agent communication
Types (17): TaskStore(struct), A2AServer(struct), AgentCard(struct), .
Functions (52): HandleA2ARequest[entry], StartA2AServer[entry], .
Reverse dependencies (9): pkg/api/handler, pkg/server, cmd/vibeops-agents, .
Component crossings: → api, → scheduler
```

Skill 按三场景组织（RCA / 开发 / 治理），使 Agent 免学 SPL 语法。

## 六、三个实战案例（均为作者 VibeCoding 演示 Demo）

**案例一：Agent 自主完成变更影响评估**。子 Agent 仅凭 [[code-wiki]] CLI 和 Skill、未读取任何源代码文件，通过 search→context→impact→check hotspots 完成推理。Agent 最终输出（原文 verbatim）：

```bash
=== A2A 协议修改影响评估 ===
影响范围：
- 直接依赖模块：9 个（pkg/api/handler, pkg/server 等）
- 受影响入口点：3 个（HandleA2ARequest, StartA2AServer, main）
- 跨组件边界：2 处（a2a-protocol → api, a2a-protocol → server）
风险点：
- pkg/a2a/adapter 被 48 个模块导入，全项目耦合度最高
- bus factor = 1，建议增加 reviewer
建议执行顺序：
1. 先修改 pkg/a2a 核心协议定义
2. 同步更新 pkg/a2a/adapter 的接口实现
3. 修改 pkg/api/handler 的调用方式
4. 更新 pkg/server 的初始化逻辑
5. 回归测试 cmd/vibeops-agents 入口点
```

作者自报口径：全程 5 条命令、每条 1-3 秒、总耗时不到 15 秒、Agent 未读取任何源代码文件（详见 [[ai工程量化效果声明追踪]]）。

**案例二：RCA——结构 + 历史 + 生产三维度汇聚的四步定位**（详见 [[代码知识图谱三维度]]）。从 `service-vibeops error_rate > 5%` 生产告警出发，是结构（代码图谱）+ 历史（commit_log）+ 生产（告警）三维度汇聚的端到端演示（原文 verbatim）：

```bash
# 1. 从运维实体定位代码模块
$ code-wiki query context pkg/server
Module: pkg/server
  Functions (23): StartServer[entry], handleRequest, applyMiddleware, .
  Dependencies (12): pkg/a2a, pkg/config, pkg/auth, .
# 2. 追踪调用链，定位可能出错的下游
$ code-wiki query callees pkg/server.handleRequest
Callees of handleRequest:
  pkg/auth.ValidateToken          [component: auth]
  pkg/a2a.HandleA2ARequest        [component: a2a-protocol]
  pkg/scheduler.DispatchTask      [component: scheduler]
# 3. 结合 commit_log 发现 a2a 模块 2 小时前有变更
#    author=xxx, message=refactor adapter interface
# 4. 确认变更影响
$ code-wiki query impact pkg/a2a
Impact of pkg/a2a:
  Direct dependents (9): pkg/api/handler, pkg/server, .
  Entry points affected: HandleA2ARequest, StartA2AServer
# → 根因：a2a 接口重构影响了 server 调用链，检查接口兼容性
```

## 七、展望：四条路线

1. **[[三范式量化评测基准]]**（规划，未落地）：Model + Bash（Agentic Search）vs Model + CodeWiki（LLM 文档）vs Model + UModel（知识图谱）；场景：影响分析/调用链追踪/架构违规检测/RCA 根因定位；指标：准确率/召回率/推理步数/Token 消耗，SWE-bench 式量化评测。这也是对"agentic search vs 索引路线"未决之争的量化裁决方案。
2. **[[agent自主维护图谱]]**（愿景）：代码变更后 LLM 推断关系重评估标记 + 孤立实体/缺失关系/过期数据巡检 + Verify 质量评估体系。
3. **CI 架构守护门禁**（设计；[[验证门禁化]]在代码域的直接实例）：PR 时三命令——`code-wiki ingest --incremental` + `code-wiki check arch` + `code-wiki query impact <changed_files>`。
4. **收束命题**：从可观测到可理解，UModel 以 Entity+Log 从观测运行系统走向理解代码系统；Agent 同时理解结构 + 历史 + 生产表现是 AI 原生软件工程的前提。
