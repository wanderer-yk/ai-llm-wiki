## 核心论题

全文主线：**AI 工程不是推倒重来，而是在传统工程坚实基础上为应对大模型不确定性所做的精准架构升级**——用确定的架构（法与术）驾驭不确定的智能（道）。作者以「道、法、术」三层框架（见 [[道法术分析框架]]）逐层对比 AI 工程与传统工程的变与不变，并以淘天集团搜索团队的 AI 搜索实践（[[淘宝问问]] → [[AI万能搜]]）作为贯穿案例。

金句（小结）：真正的智能，不在于模型能生成多少可能性，而在于系统知道何时该让它说话，何时该让它闭嘴。

产品演进：

| 时间 | 产品动作 |
|---|---|
| 2023年3月 | [[淘宝问问]] 孵化启动，先后尝试对话式助手 / Copilot / 语音助手三种形态 |
| 2025年初 | 基于深度推理大模型推出新一代 AI 搜索产品 [[AI万能搜]] |
| 2025 双11前 | 上线「AI 清单」 |

架构演进：

| 年份 | 架构形态 |
|---|---|
| 2023 | 主流开源框架构建单体 Agent 架构，快速验证可行性 |
| 2024 | 多模态全双工交互 + RAG 为主流技术栈 |
| 2025 | 支持复杂推理的混合智能体体系：分层组件化设计、Multi-Agent 架构、Context Engineering，形成企业级交付工程体系 |

三大技术挑战与对策：

| 挑战 | 对策/解法 |
|---|---|
| ① 架构范式尚不成熟（行业标准缺失、技术栈快速迭代；langchain 三年四换方向） | 务实演进、业务先行：MVP 驱动业务闭环再迭代加固；流式协议不足期「客户端轮询 + 服务端分段缓存」；借音视频基建快速搭多模态实时交互 Demo |
| ② 业务需求高度不确定（验证周期短、方向调整频繁，一年内多次大版本迭代） | 高配置化、可插拔工程框架：抽象核心领域模型与通用组件，复用主搜业务编排能力，Prompt/Tool/SOP 配置热更新 + 细粒度实验 |
| ③ 大模型特性工程难题（高延迟、幻觉、上下文过载、输出非确定性、推理成本不可控） | 将「波动性」视为系统设计基本约束：Context Engineering、异步预加载、熔断降级内建鲁棒性；电商知识库 + 标注平台 + 评估体系形成「模型-数据-工程」闭环 |

成型工程体系五模块：

| 模块 | 要点 |
|---|---|
| 终端 | 跨端框架、答案卡片类型灵活扩展、Markdown 增强、ASR/TTS、动态筛选/流式翻页/内容折叠 |
| 网关与协议 | 流式通信协议端到端低延迟；多模态全双工长连接通道，Agent 与客户端双向实时交互 |
| 服务端 | Multi-Agent 架构 + 统一 Agentic 框架：业务逻辑编排、模型调度、工具调用；开放接口协议兼容多种接入 |
| Multi-Agent 架构 | 与算法团队共建电商场景大模型协作框架；Agent 自主规划交互流程、输出结构化知识、答案原子化/多样化 |
| 大模型 | 自研大模型业务定制，经 Multi-Agent 架构编排交互 |

## 二、道：从「追求绝对正确」到「管理概率预期」

- **不变**：控制复杂性仍是架构设计第一要务；稳定交付与持续演进仍是团队成熟度标尺（引《架构整洁之道》）。「不能因为模型具有『智能』就容忍系统频繁崩溃，也不能以『AI 不可控』为借口放弃对用户体验的基本承诺」。
- **变**：[[确定性vs概率性范式转移]]——传统工程建立在 y=f(x) 严格映射之上；AI 工程运行于概率空间，输出为大模型、prompt、上下文与环境共同「涌现」的结果。「正确性」让位于合理性、相关性、用户满意度等多维指标；AI 工程师的核心任务不是消灭不确定性，而是将其收敛至业务与用户可接受区间。

## 三、法：方法体系之变与不变

- **不变**：分层、解耦、高内聚低耦合、SOLID 仍是基石；高可用与容错仍是生命线（熔断、降级、限流、服务治理反成「保命符」，见 [[波动性即设计约束]]）；SLA 口径由「响应时间 < 200ms」调整为「首字响应时间 < 1s」。
- **变之一**：[[能力抽象对象迁移]]——平台化思维延续，但抽象对象从业务域实体迁移为 AI 能力组件；「变化的不是方法，而是被抽象的对象」。四核心组件：

| 组件 | 定义 | 备注 |
|------|------|------|
| Agent | 独立解决某类问题的智能实体 | 例：AI 助手商品筛选（跑马灯 agent）、双 11 清单对话页清单生成 Agent |
| SOP协议 | 统一 Agent 调度层以及 Agent 执行层调度协议，能对 Agent 和 tool 进行编排 | 对应 langChain 框架中 chain 的概念 |
| Tool | 工具服务，基于主搜编排框架，工具配置化接入 | 支持通用 MCP 协议工具，同时支持本地及远程工具调用 |
| Memory | 记忆模块 | 针对过去回答的结构化存储和检索能力 |

- **变之二**：关注点从「如何定义业务」（领域模型）转向「如何喂养模型」（[[上下文工程]]）。
- **变之三**：[[可控的不确定性边界]]——确定性前/后处理与安全逻辑包裹模型内核，多级兜底；通过编排与路由将「动态生成」转化为「受控执行」。
- **变之四（关键架构决策）**：[[预编排sop模式]]——从 react 式 plan-execute（见 [[plan-and-execute模式]] 的负面证据：误差逐级放大、高延迟高 Token、幻觉难追溯）转向固化 SOP，「以有限灵活性换取高确定性」。
- **变之五**：[[多级意图路由漏斗]]——将大模型不确定性严格限制在必要环节：安全筛查（风险拦截）→ 一级意图识别（闲聊 vs 任务型）→ 多维细化（高价值任务）→ 专用模块精准调度。

## 四、术：工具战术之变与不变

- **不变**：接口契约、日志埋点、压测、灰度、监控告警因 AI 脆弱性反而更关键；multiAgent 框架复用主搜团队多年业务编排框架，AI 请求与传统搜索请求共享同一套限流、熔断、链路追踪；weex2 组件化实现 AI 回答卡片「一次开发、多端通投」。
- **变之一**：[[三大高价值上下文模块]]——profile / Agentic RAG / Memory 由统一 Context Manager 协同按需供给，降低 Token 浪费与幻觉风险。
- **变之二**：[[评估体系多维度量]]——传统断言式 True/False 测试失效，转向人工标注层 + 线上 AB 层双层机制，使团队能「在『不确定』中寻找『相对确定』的优化方向」。
- **变之三**：[[轨迹可视化调试范式]]——调试从日志回溯升级为轨迹可视化，自研 Trace 工具记录全链路。
- **术之精髓**：[[确定性骨架概率性肌肉]]——确定性骨架（稳定架构、可靠基础设施、严谨流程）确保系统不崩，概率性肌肉（灵活推理、语义理解、自适应交互）赋予智能。

## 五、小结与五条建议

- 没有绝对的「传统」与「AI」之分，AI 是一种强大到足以影响架构价值理念、方法体系和实操手段的能力。
- [[AI工程建设五建议]]：祛魅归因、合理性与真实性、MVP 快但需技术纵深、不确定性内建鲁棒性、AI 原生选型。
- 内部张力（已自我调和）：「不是推倒重来/复用主搜编排框架」与建议 5「盲目套用传统架构往往成为演进的枷锁」之间，文中以「在『复用』与『新建』之间，以 AI 工作流的本质需求为准绳」调和，属立场细化而非矛盾。

```
用户输入 → 意图识别 → 上下文组装 → Agent决策 → Tool调用 → 模型生成 → 后处理
```
