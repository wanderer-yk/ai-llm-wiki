# Knowledge Wiki：面向 AI 的项目知识层建设实践

**作者**：有赞共享技术团队
**发布平台**：微信公众号"有赞coder"
**发布时间**：2026年4月7日

## 核心主张

AI Coding 的真正瓶颈不是模型能力，而是上下文传递——能否把任务目标准确传达给 AI。知识库的本质是"降熵"：把人脑中的专家知识提前结构化、外化，降低每次人机协作的信息传递成本。

## 文章结构

文章共六章，系统阐述了面向 AI 的项目知识层建设的完整方法论：

### 第一章：动机——为什么需要 Knowledge Wiki

- **Workspace 模式困境**：跨项目上下文断裂 + 代码膨胀导致 AI "降智"两大现实问题
- 信息论类比：自动驾驶仅需终点坐标（信息熵≈0），企业研发背后是领域模型、业务规则、技术约束、团队规范、历史决策等大量隐含知识
- 关键知识不在代码里，在飞书文档和人脑中

### 第二章：内容定位——沉淀什么、不沉淀什么

- **wiki 五类知识**：认知、导航、排障、隐形、规范——只沉淀 AI 从代码中难以自动发现的信息
- 不沉淀纯实现细节、SQL、一次性排查过程等
- **外部知识筛选四标准**：结论稳定 / 有复用价值 / 非代码中一眼可见 / 能对应到代码逻辑或 wiki 缺口
- **过时 wiki 比没有 wiki 更危险**：AI 会把错误描述当作"先例"系统性复用

### 第三章：技术实现

- **架构选型**：分布式 `.wiki/` 目录跟随 Git submodule，知识与代码同分支同步（详见 [[分布式wiki架构]]）
- **检索方案**：渐进式披露替代向量检索（详见 [[渐进式披露替代向量检索]]）
- **初始化**：多 Agent 逆向工程初始化，Controller→Implementer→Reviewer 三角色（详见 [[多agent逆向工程初始化]]）
- **持续更新**：AGENTS.md 常驻指令 + 三模式 Skill（read/init/update）+ 最小作用域原则 + 人工确认写入闭环（详见 [[知识准入控制]]、[[最小作用域原则]]）

### 第四章：弯路与思考

- 方案对比：Hook 驱动（依赖 IDE）/ Commit 驱动（准确率存疑）/ AGENTS.md + Skill（最轻量，选中）
- Skill description 匹配率不理想，AGENTS.md "始终在场"指令更可靠
- 知识写多了是噪音——Agent 需要精准导航线索，边界比内容更重要

### 第五章：实践结论

- 自底向上从 app 级 wiki 提炼 workspace 级知识
- [[知识复利效应]]：定量证据——配置排查从 30-60 分钟降至 1-2 分钟，每周反馈问题从 10+ 降至 1-2 个
- 智能体质量上限由工程底座完善程度决定

### 第六章：未来规划

- 近期：接入飞书（工单→排查→沉淀闭环）
- 中期：服务端统一管理 + 向量检索（知识量足够大时量变质变）
- 长期：从工具到范式

## 方法论定位

本文将 Knowledge Wiki 定位为 [[harness-engineering]] 在知识层面的系统性落地实践，提出四维框架：
- **约束**：知识准入规则
- **反馈**：AI 行为质量反证知识有效性
- **验证**：update 人工确认环节
- **治理**：最小作用域 + 分层 + 覆盖审查
