## 一、背景：单智能体架构的三大痛点

早期以 workflow + 单智能体上线 AliGo v1，暴露三大痛点：

1. **单智能体技术瓶颈**：Prompt Token 急剧增长导致大模型注意力机制明显衰减；点选需求经百余次 Prompt 调优准确率仍仅约 50%；线上频繁出现"事项识别异常请重试""事项收集结论不输出"等稳定性问题。
2. **架构泛化能力不足**：Agent 间协作机制缺失、规划能力薄弱、无法处理多意图融合。
3. **上下文工程处于初级阶段**：用户对话记录与智能体上下文未分离、缺乏上下文分层共享机制。

四项升级目标：选型适配商旅的 AI 框架、提升落地准确率、缓解稳定性顽疾、支持容器化灵活部署。

## 二、方案

### （一）技术选型

- **技术栈分工**：Python 写核心 AI 逻辑（规划/记忆/LLM 调用）+ Java 写服务层（鉴权/MTop 对接/MCP 服务）。与 [[java声量缺失论]] 观察互补：Java 承担高并发服务层。编者注：选型时间为 2025 年中旬，现 AgentScope 已提供 AgentScope Java。
- **智能体框架**：AgentScope 胜 LangGraph——MCP 调用与 Qwen 集成开箱即用；实时控制、中断处理、沙箱执行等企业级能力；内置 AgentStudio 可视化；原生支持 Qwen 系列（见 [[agentscope]]、[[qwen]]）。
- **Web 框架**：FastAPI 胜 Flask（异步、类型安全、性能、利于大型项目维护）。
- 注：选型对比图与两张架构图为图片，文本不可提取。

### （二）Multi Agent 架构：Handoffs + Routing 混合模式

以主规划智能体（main_plan_agent）为核心协调多个专业化子智能体；行程规划、知识库查询用 Routing（纯路由），信息查询用 Handoffs（交接），按准确度与耗时权衡、可按需调整。

### （三）意图识别智能体：四职责

1. 多意图识别和分类（上下文消歧）
2. 智能体调度决策（结构化调用决策）
3. query 改写
4. 显示推理（"推理过程 + JSON 决策"两段式输出，直接提升意图识别准确度）

模型策略：项目初期样本量有限时选用推理速度快的大模型（文中示例为 Qwen3-Next-80B-A3B-Instruct），通过显式推理输出兼顾速度与准确率；商旅适用场景为意图识别、日期时间转化。可与 [[意图规划]]（马上消费）对照。

### （四）快慢车道分层处理

运行期性能发现：用户通过界面点击触发的明确意图（"为我规划行程""为我提申请""开始规划"）仍走大模型完整分析流程，造成不必要延迟。解法为分层处理：规则引擎快车道命中即直通路由，大模型慢车道处理复杂、长句、多意图请求。与 [[workflow优先于agent]]（有赞）"确定性场景用确定性路径"同向；分流逻辑内嵌于 Prompt 组装层（见 [[动态prompt生成机制]]）。

### （五）实时思考链与流式输出

多智能体架构不可避免增加响应耗时，文章以实时思考链动态展示各智能体推理与协作过程，缓解用户等待焦虑（承认架构代价的坦诚表述——多智能体的延迟代价需用 UX 透明化对冲）。AgentScope 层面三项实现：

- **ReActAgent**：`_reasoning`/`_acting` 双抽象方法 + Hooks 机制（参见 [[react-agent]]、[[react五要素]]）
- **ReActAgent Hook**：print hook 实时拦截 `tool_use`/`tool_result` 消息，驱动 `add_tool_use`/`add_tool_result`
- **TaskCollector**：任务状态收集器，PENDING/DOING/DONE/FAILED 生命周期 + 任务层级关系 + 发布-订阅推送（关键方法 `add_use()`/`add_result()`/`subscribe()`/`unsubscribe()`）

流式输出层四职责：创建 TaskCollector 实例 → 订阅 `task_update`（实时渲染思考链）与 `text`（最终回答）两类消息 → 收集最终回答并维护卡片-任务映射 → 构建结构化响应并生成 SSE 格式输出流。

**ReAct 主循环（伪代码，原文保留）**：

```bash
observation = initial_user_input
history = []

while True:
  # 调用大语言模型，基于当前观察和历史生成思考与行动
  thought, action, action_input = llm_agent.reason_and_act(observation, history)

  if action == "Finish":
    # 任务完成，输出最终答案
    return thought  # 即最终回答
  else:
    # 执行工具调用
    result = execute_tool(action, action_input)
    # 将工具结果作为新的观察
    observation = result
    # 记录本轮推理与执行到历史
    history.append((thought, action, result))
```

**`_acting` 异步工具调用实现（原文保留，含流式返回与中断处理）**：

```python
# 在_react_agent.py中的_acting方法实现了工具调用的实时返回
async def _acting(self, tool_call: ToolUseBlock) -> Msg | None:
  # 创建工具结果消息容器
  tool_res_msg = Msg(.)

  try:
    # 执行工具调用，返回AsyncGenerator
    tool_res = await self.toolkit.call_tool_function(tool_call)

    response_msg = None
    # 异步迭代处理工具响应块
    async for chunk in tool_res:
      # 实时更新工具结果
      tool_res_msg.content[0]["output"] = chunk.content

      # 实时打印输出（除非是完成函数且成功执行）
      if (tool_call["name"] != self.finish_function_name or
          not chunk.metadata.get("success")):
        await self.print(tool_res_msg, chunk.is_last)

        # 处理中断
        if chunk.is_interrupted:
          raise asyncio.CancelledError()

          # 返回最终响应消息
          if (tool_call["name"] == self.finish_function_name and
              chunk.metadata and chunk.metadata.get("success")):
            response_msg = chunk.metadata.get("response_msg")

  return response_msg
```

### （六）上下文工程

四组件架构：全局上下文管理 / 会话记忆管理 / 动态 Prompt（状态机）/ 工具注册管理。本章是 [[上下文工程]] 概念的最强实现证据之一。

记忆架构：以出入栈维护智能体调用链层级 + 共享 sessionId，解决三问题——①模块独立性（便于维护扩展）；②模块间记忆共享（如审批记忆与事项收集记忆）；③完整的执行链路追踪。

**三表存储（源文仅文字描述，无 DDL/字段定义）**：

| 表名 | 职责 |
|------|------|
| 消息存储表 | 存储详细的消息记录 |
| 会话管理表 | 管理会话的基本信息和会话描述 |
| 对话记录表 | 存储精简的对话记录（主要记录用户查询和智能体的最终回答） |

共享策略：默认各智能体独立管理对话历史（隔离），对高相关性智能体按业务关系 + 最小权限原则动态开放必要上下文；官方定性"降低上下文规模的同时显著提升推理准确度与效率"（定性，无数据）。与 [[长记忆四件套]]（小红书）、[[模型记忆与业务上下文记忆分离]]、[[agent短期记忆]]、[[追加式上下文]]、[[上下文压缩策略]]（vivo）形成记忆/上下文治理路线对照。

### （七）Prompt 工程

**反模式**：把业务流程、规则、工具调用规范全量嵌入 Prompt，形成线性"工作流程说明书"，无法适配非线性动态对话，且要求模型在全量规则上实时推理用户状态，对模型能力要求过高。

**定义原文**：动态 Prompt 组装"本质上为 AI 构建一个状态机：通过工程手段结合自然语言理解与程序化状态控制，精准识别用户所处的对话阶段，并将模型注意力聚焦于当前主链路，打造鲁棒性更强、更智能的对话 Agent"。详见 [[动态prompt生成机制]]。

**一句话经验**：协同模型确定当前及下一轮注意力焦点 → 明确业务边界 → 可控范围内交由 AI 自主处理逻辑细节 → 在工程确定性与 AI 灵活性之间实现平衡。详见 [[工程确定性与ai灵活性平衡]]。
