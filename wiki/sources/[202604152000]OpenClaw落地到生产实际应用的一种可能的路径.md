## 核心论断

文章从 Coding Agent 为何率先跑通出发，提出核心论断：**Agent 生产落地的关键不在于模型能力提升，而在于将开放、分散、难回滚的业务执行环境重构为具备可视化、相对封闭、可验证、可恢复特性的操作空间**。详见 [[agent生产落地环境重构论]]。

## 关键概念索引

- **[[coding-agent四特征]]** — Coding Agent 领先的根本原因不是"代码适合大模型"，而是工作环境天然具备可视化、相对封闭、可验证、可回滚四大特征。作者估算 Coding Agent 返工率从 ~50% 降至 ~20%（2024 初→2025 底）。
- **[[agent生产落地四层框架]]** — 将四特征从"环境天然属性"转化为"工程化构建目标"：可视化层→封闭层→验证层→回滚层。总结章进一步凝练为 Agent 生产环境六条件（可视化/封闭/可验证/可推演/可回滚+有产物有历史有责任归属）。
- **[[agent-canvas沙盘机制]]** — 以 Amazon 电商场景 agent canvas 为实证，提出将不可逆业务动作先映射到可推演、可比较、可审查的画布空间，再决定是否推进到真实执行。
- **[[结果产物化]]** — Agent 输出从对话日志升级为可审阅/可比较/可存档的正式产物。
- **[[验证门禁化]]** — 验证从"建议检查"升级为硬性阻断规则。
- **[[业务diff等价物]]** — 为缺乏 git diff 的业务世界人为构造变更对比能力。

## 关键主张

1. "代码的复杂是被工程系统包裹过的复杂"——代码世界复杂但被工程系统包裹，Agent 能在此空间快速迭代/验证/修正；业务世界缺乏这种包裹。
2. "如果没有把环境改造好，Agent 越强，风险反而越大"——环境改造先于能力提升。
3. "多 agent 编排、角色分工、调 prompt、换模型，最后都只是把更强的执行能力放进一个没有护栏的环境里"——对当前 Agent 工程实践的尖锐批评。
4. 沙盘成立后，业务世界首次具备类似代码世界的"分支"能力——先在安全空间形成版本，再决定是否合并到真实世界。
5. 环境就绪则 Agent 从辅助工具升级为生产执行单元；环境不就绪则无论模型能力如何提升、多 Agent 架构如何演进都难以落地业务核心。
