# 从 OpenClaw 看 Agent 架构设计

## 基本信息

- **作者**：互联网搜索团队 - Wang Wenqian
- **发布平台**：微信公众号"vivo互联网技术"（IP 属地广东）
- **发布日期**：2026-04-08

## 核心框架

本文以 [[openclaw]] 和 [[claude-code]] 为核心案例，系统拆解 Agent 架构的四个关键决策维度（[[agent架构四决策]]）：

1. **上下文管理** — 追加式 vs 压缩 vs 任务隔离
2. **工具加载** — tools 字段缓存 vs prompt 内嵌 vs 渐进式加载
3. **工具查找** — 全量注入 vs 追加上下文 vs 子 Agent vs 向量搜索
4. **主循环设计** — 对话驱动 vs 任务驱动

核心论点：**四决策没有标准答案，但每个选择都有明确代价，且决策间互相关联。**

## 上下文管理

### 追加式上下文（Append-only Context）

[[openclaw]] 和 [[claude-code]] 均采用此模式——维护持续增长的对话历史数组，每轮 LLM 调用重发完整历史。Token 增长轨迹：~2K → ~8K → 20 轮后 ~80K。

优势：缓存命中率高、实现简单、上下文连贯。问题：话题混杂、成本与复杂度脱钩。

### 压缩策略对比

| 维度 | Claude Code | OpenClaw |
|------|------------|----------|
| 触发时机 | ~83.5% token 阈值 | 分阶段渐进 |
| 压缩方式 | 一次性摘要生成 | [[记忆落盘]] + 分阶段压缩 |
| 跨会话保留 | 无 | 有（.md 文件加载） |

压缩是安全网而非解决方案：额外 LLM 调用、有损摘要、话题仍混合。

### 任务隔离

以任务为单位隔离上下文：独立窗口、任务内仍追加式、任务间不干扰。消除话题混杂但丧失跨任务连贯性。参见 [[任务隔离]]。

## 工具加载

### Tools 字段与缓存冲突

Anthropic Prompt Cache 按严格顺序（system→tools→messages）构建缓存前缀，tools 变动导致后续全部缓存失效。5→6 个工具的变更可使 100K messages 缓存全部失效。

### 三层解决方案

1. **工具描述移入 prompt** — 嵌入 messages 而非 tools 字段，新增工具不破坏缓存，但需自实现解析/调用逻辑
2. **本地控制台 + 远程 MCP 分层** — 本地仅需 1 个 execute 工具定义（利用模型预训练世界知识），远程用 MCP（标准接口+鉴权）
3. **[[渐进式工具加载]]** — 基础 ~3K tokens 开始，Agent 按需追加到 messages 尾部

核心发现：[[mcp]] 的动态工具发现与缓存稳定性存在不可调和的矛盾。[[claude-code]] 报告 92% 缓存命中率靠的是"永远不改变 tools 列表"。

## 工具查找

四种查找方式共享核心矛盾——在接口维度查找工具但需求在功能维度上查找能力（[[接口维度与功能维度矛盾]]）。

1. 全量注入 tools 字段（准确但缓存失效 + token 开销大）
2. 追加上下文加载（保留缓存但堆满已用完工具描述）
3. 子 Agent 查找（不污染主上下文但缺乏上下文理解）
4. 向量搜索/关键词检索（零 token 消耗但语义模糊时不够准确）

[[skill功能聚合]] 按功能维度组织工具的"说明书"，作为工具查找的缓存层——20 个工具可压缩为 3 个 Skill。Skill 可由 Agent 自动积累，形成自我优化循环。

## 主循环设计

### 对话驱动 vs 任务驱动

参见 [[对话驱动vs任务驱动]]。

- **对话驱动**：对话框既是输入源、输出目标，也是上下文容器。门槛低但一切绑定对话框。
- **任务驱动**：感知→思考→行动循环，聊天框降格为工具之一，支持多感知源（聊天框/Cron/Webhook/fork 子任务）。

### 思考过程作为核心输出

任务驱动中 Agent 核心输出是思考过程而非对话回复，行为可追溯到具体出错步骤。现实约束：RLHF 优化回复满意度导致模型天然倾向对话模式。

### 混合策略

对话作为前端、任务作为后端——用户通过对话提交需求，系统自动转化为任务，后台任务驱动执行。关键是架构层面保留任务隔离能力。

## 四决策关联性

四个决策互相关联：任务隔离影响上下文策略、工具加载方式决定 Skill 组织形式、主循环设计决定任务来源。
