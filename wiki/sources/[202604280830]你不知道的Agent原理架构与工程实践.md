## 第一章：Agent Loop 的基本运转方式

核心实现抽象后 <20 行；控制流为感知→决策→行动→反馈循环，直到模型返回纯文本。核心代码（原文，末行按语义自导出残缺重建为 `?.text ?? ""`）：

```ts
const messages: MessageParam[] = [{ role: "user", content: userInput }];
while (true) {
  const response = await client.messages.create({
    model: "claude-opus-4-6",
    max_tokens: 8096,
    tools: toolDefinitions,
    messages,
  });
  if (response.stop_reason === "tool_use") {
    const toolResults = await Promise.all(
      response.content
        .filter((b) => b.type === "tool_use")
        .map(async (b) => ({
          type: "tool_result" as const,
          tool_use_id: b.id,
          content: await executeTool(b.name, b.input),
        }))
    );
    messages.push({ role: "assistant", content: response.content });
    messages.push({ role: "user", content: toolResults });
  } else {
    return response.content.find((b) => b.type === "text")?.text ?? "";
  }
}
```

扩展原则：主循环基本不变，新能力（子 Agent、上下文压缩、Skills 加载）叠加在循环外部，仅有三种接入方式——扩展工具集和 handler、调整系统提示结构、把状态外化到文件或数据库。分工原则："模型负责推理，外部系统负责状态和边界"，不应让循环体变成巨大状态机。详见 [[agent-loop]]。

Workflow 与 Agent 的区分（归于 Anthropic 的定义）见 [[workflow与agent控制权分界]]，七维对照表原文：

| 维度 | Workflow | Agent |
|------|----------|-------|
| 控制权 | 代码预定义，同输入必走同一路径 | LLM 动态决策，可能需要评测验证 |
| 执行方式 | 工具顺序固定，错误走预设分支 | 工具按需选择，模型可尝试自我修复 |
| 状态与记忆 | 显式状态机，节点跳转清晰 | 隐式上下文，状态在对话历史中累积 |
| 维护成本 | 改流程需修改代码并重新部署 | 调整系统提示即可，无需重新部署 |
| 可观测性 | 日志定位节点，延迟可预估 | 需完整执行记录理解决策链，轮数不固定 |
| 人机协作 | 人在预设节点介入 | 人在任意轮次介入或接管 |
| 适用场景 | 流程固定、输入边界清晰 | 需要中间推理与灵活判断 |

五种常见控制模式（提示链/路由/并行/编排器-工作者/评估器-优化器）见 [[五种常见控制模式]]；[[nanobot]] 的 `spawn` 与 learn-claude-code 子 Agent 模式被引为编排器-工作者原型。

## 第二章：为什么 Harness 比模型更关键

Harness = 围绕 Agent 构建的测试、验证与约束基础设施，四要素：验收基线、执行边界、反馈信号、回退手段（详见 [[harness四要素]]）。

OpenAI "Agent 优先开发实践"案例（3 人 / 5 个月 / 约百万行代码 / 约 1500 个 PR / 约 10 倍传统速度，转述数据），四条工程决策：

1. **Agent 看不到的内容等于不存在**——知识必须存在于代码库本身，`AGENTS.md` 只保留约 100 行作索引，细节拆到 docs 目录按需引用；
2. **约束编码化而非文档化**——编码进 Linter/类型系统/CI 规则的约束才可执行，架构分层靠自定义 Linter 机械强制而非人工 Review；
3. **Agent 端到端自主完成任务**——验证状态/复现 Bug/修复/驱动应用验证/开 PR/处理 Review/自主合并全链路无人介入，查日志、指标、追踪由 Agent 主动完成；
4. **最小化合并阻力**——测试偶发失败重跑而非阻塞；"写代码的纪律没有消失，只是从人工 Review 变成机器执行的约束"。

Codex 临时可观测性栈：日志/指标/追踪三路数据经 Vector 分发到 Victoria 存储，通过 LogQL/PromQL/TraceQL 三个查询接口供 Codex 自主查询验证；整套栈按任务临时创建、任务完成即销毁——Agent 直接查系统状态自验证而非等人报错。

任务四象限（任务清晰度 × 验证自动化程度）：右上角（目标明确+可自动验证）最适合 Agent；左上吞吐天花板是人的审查速度；右下"高效地往错误方向跑"；左下 Agent 基本无用；Harness 的使命是把任务推向右上角。

## 第三章：上下文工程为什么决定稳定性

- **Context Rot**：O(n²) 注意力复杂度下，无关内容占上下文大头导致决策质量下滑；分层问题本质是信息密度而非窗口长度。
- **上下文五层分层**：常驻层（短/硬/可执行）→ 按需加载（Skills 描述符常驻+内容触发注入）→ 运行时注入（时间/渠道/偏好）→ 记忆层（MEMORY.md 跨会话）→ 系统层（Hooks/代码规则完全不进上下文）。
- **确定性逻辑外置**：凡可用 Hooks/代码规则/工具约束表达的都不进上下文。

三种压缩策略（原文表，详见 [[上下文压缩策略]]）：

| 策略 | 成本 | 丢什么 | 适用场景 |
|------|------|--------|----------|
| 滑动窗口 | 极低 | 早期上下文 | 简短对话 |
| LLM 摘要 | 中 | 细节，保留决策 | 长任务、含关键决策 |
| 工具结果替换 | 极低 | 工具原始输出 | 工具调用密集型 |

补充机制：branch summarization、`micro_compact`（每轮替换旧工具输出）、`auto_compact`（超阈值自动触发）。压缩最大风险是保留顺序设错而非摘要不够短。Compact Instructions 保留优先级（原文）：

```markdown
### Compact Instructions 如何保留关键信息
保留优先级：
1. 架构决策，不得摘要
2. 已修改文件和关键变更
3. 验证状态，pass/fail
4. 未解决的 TODO 和回滚笔记
5. 工具输出，可删，只保留 pass/fail 结论
```

标识符原样保留原则：压缩时 UUID、hash、IP、端口、URL、文件名必须原样保留，PR 编号或 commit hash 改错一位会导致后续工具调用失效。

Prompt Caching：KV 缓存精确前缀匹配；缓存友好=前缀稳定；反直觉结论：稳定的大系统提示比频繁变动的小提示成本更低（读取折扣最高 90%）；MCP 工具集频繁变动会持续击穿缓存。

Skills 按需加载：描述符是路由条件而非功能介绍（原文代码）：

```typescript
const systemPrompt = `
可用 Skills：
- deploy: 部署到生产环境的完整流程
- code-review: 代码审查检查清单
- git-workflow: 分支策略和 PR 规范
`;
async function executeLoadSkill(name: string): Promise<string> {
  return fs.readFile(`./skills/${name}.md`, "utf-8");
}
```

描述符字数对比（原文 YAML）：

```yaml
# 低效（约 45 tokens）
description: |
  This skill handles the complete deployment process to production.
  It covers environment checks, rollback procedures, and post-deploy
  verification. Use this before deploying any code to production.
# 高效（约 9 tokens）
description: Use when deploying to production or rolling back.
```

路由准确率实验：基准 73%、无反例降至 53%、加反例升至 85%，响应时间降 18.1%（出处未注明，疑源自 Anthropic Skills 文档）。调用规则：每次回复前先扫描 `available_skills`，有明确匹配时再读取 `SKILL.md`，多匹配选最具体，没有匹配就不读取，一次只加载一个。三大反模式与 Skills vs MCP 上下文成本对比见 [[skill三大反模式]]、[[skills与mcp上下文成本对比]]、[[mcp与bash对比]]。

文件系统即上下文接口（[[文件系统即上下文接口]]）：工具返回的大量 JSON 写入文件，Agent 通过 grep/rg/脚本按需读取；长任务压缩时聊天记录完整落盘、摘要只引用路径，压缩成为"有损但可追溯"的操作。Cursor 的 Dynamic Context Discovery（"默认少给，只在需要时读取"；MCP 工具描述同步到文件夹、Agent 默认只看工具名）A/B 测试总 token 消耗减少 46.9%（出处未注明）。

## 第四章：工具设计决定 Agent 能做什么

- **工具质量优先于数量**：仅 5 个 MCP 服务器就可能带来约 55,000 tokens 定义开销（200K 上下文近三成）；工具过多稀释模型对单个工具的注意力。
- 调试 Agent 先查工具定义——工具选择错误多因描述不准确而非模型能力。
- 好工具/差工具五维对比（原文表）：

| 维度 | 好工具 | 差工具 |
|------|--------|--------|
| 粒度 | 对应 Agent 要完成的目标 | 对应 API 能做的操作 |
| 示例 | `update_yuque_post` | `get_post + update_content + update_title` |
| 返回 | 与下一步决策直接相关的字段 | 完整原始数据 |
| 错误 | 结构化，含修正建议 | 通用字符串 `"Error"` |
| 描述 | 说明何时用、何时不用 | 只写功能说明 |

- 工具设计三代演进（原文）：

```
第一代（API 封装）:  get_post + update_content + update_title
第二代（ACI）:       update_yuque_post(post_id, title, content_markdown)
                     —— 反例：update(id, content) 通用接口
第三代（Advanced Tool Use）: search_tools 按需发现工具定义
```

- ACI（Agent-Computer Interface）核心判据："不能只看工具能不能调用，还要看调用错了之后能不能自己修回来"。结构化错误示例（原文）：

```js
// 差：出错只返回字符串
return "Error: update failed";

// 好：ToolError 含 error_code 与 suggestion
throw new ToolError("文章 ID 不存在", {
  error_code: "POST_NOT_FOUND",
  suggestion: "请先调用 list_yuque_posts 获取有效的 post_id",
});
```

- Advanced Tool Use 三方向（数据出处未注明）：Tool Search（上下文保留率 95%，Opus 4 准确率 49%→74%）；Programmatic Tool Calling（中间数据不穿模型，token 约 150,000→约 2,000）；Tool Use Examples（每工具 1-5 个真实示例，准确率 72%→90%）。
- 消息双类型隔离：

| 类型 | 用途 | 允许内容 |
|------|------|----------|
| `AgentMessage` | 应用层 | 任意自定义字段 |
| `Message` | 发给 LLM | 仅 `user`、`assistant`、`tool_result` 三种标准类型 |

## 第五章：记忆系统如何设计

记忆层是基础设施而非事后补的能力（Agent 无原生时间连续性）。四种记忆按问题划分：工作记忆=上下文窗口 / 程序性记忆=Skills / 情景记忆=JSONL 会话历史 / 语义记忆=MEMORY.md（详见 [[agent记忆四分类]]）。

ChatGPT 四层记忆案例（原文表，详见 [[ChatGPT]]、[[chatgpt四层记忆]]）：

| 层 | 内容 | 持久化 |
|------|-----------|---------|
| Session Metadata | 设备、地点、使用模式 | 否，会话级 |
| User Memory | 约 33 条关键偏好事实 | 是，每次注入 |
| Conversation Summary | 约 15 个最近对话的轻量摘要 | 是，摘要预生成 |
| Current Session | 当前对话滑动窗口 | 否 |

未使用向量数据库、未引入 RAG——[[Markdown优先记忆论]]：大多数 Agent 不需一开始引入向量存储，规模超几千条且确需语义相似度检索再引入。

OpenClaw 记忆三件套：`memory/YYYY-MM-DD.md`（追加写日志）+ `MEMORY.md`（精选事实，Agent 主动维护）+ `memory_search`（70% 向量相似度 + 30% 关键词权重混合检索）。

[[记忆整合指针回退机制]]：触发阈值 `tokenUsage / maxTokens >= 0.5`；成功路径 `llmSummarize(toConsolidate)` → 摘要追加至 `MEMORY.md` → 更新 `lastConsolidatedIndex`；失败路径原始消息写入 `archive/`。最关键原则：只移动指针，不删除原始消息，流程必须可回退。

## 第六章：如何逐步放开 Agent 自主度

自主度不是少几次人工确认，而是让 Agent 在更长时间跨度内稳定推进任务；放权前先补齐三类基础设施（[[agent自主度三前提]]，一手出处为参考文献 [7]）：

1. **跨 session 续跑**——[[initializer-coding双agent跨session模式]]：Initializer Agent 只跑一次，生成 `feature-list.json`、`init.sh`、初始 git commit 和 `claude-progress.txt`；Coding Agent 多 session 循环恢复现场。进度放文件不放上下文；功能清单用 JSON 不用 Markdown；全部 `passes: true` 才算完成。
2. **session 内进度约束**——[[任务状态显式外化]]：同一时间只能一个 `in_progress`；每完成先更新状态再继续；连续多轮未更新时自动注入 `<reminder>`。任务状态 JSON 示例（原文）：

```json
{
  "tasks": [
    {"id": "1", "desc": "读取现有配置", "status": "completed"},
    {"id": "2", "desc": "修改数据库 schema", "status": "in_progress"},
    {"id": "3", "desc": "更新 API 接口", "status": "pending"}
  ]
}
```

3. **慢速 I/O 后台接入**——[[O通知队列模式]]：拖慢主循环的是文件操作/网络请求/长耗时命令等外部 I/O 而非模型推理；慢速 subprocess 放后台线程 + 通知队列在下一轮 LLM 调用前注入结果，比 async runtime 改造更稳更易维护。

## 第七章：多 Agent 如何组织

核心工程问题是隔离与协作而非并行。

- **[[指挥者统筹者两模式]]**：指挥者=同步协作（人与单 Agent 每轮调整决策）；统筹者=异步委派（人只在起点定目标和终点审产出，中间产出为分支/PR 等可持久化工件）。多 Agent 主要价值=把人的持续参与变成对工件的最终审核。
- **[[jsonl-inbox协作协议]]**：自然语言对齐多 Agent 协作会失败；消息结构化、有状态、append-only、崩溃可恢复（原文）：

```javascript
// 消息结构：结构化，有状态，append-only，崩溃可恢复
{
  request_id, from_agent, to_agent,
  content,
  status: 'pending' | 'approved' | 'rejected',
  timestamp
}
// 写入：.team/inbox/{agentId}.jsonl，append-only，崩溃可恢复
// 读取：按行解析，按 status 过滤
```

基础设施三件套：`.team/inbox/{agentId}.jsonl`（协议）+ `.tasks/`（任务图和依赖关系）+ `.worktrees/`（隔离每个子 Agent 的文件修改）；顺序不可反：协议先定→隔离先做→再谈协作并行。

- **[[子agent深度限制与最小提示]]**：设最大深度防无限递归；最小系统提示只含 Tooling/Workspace/Runtime 三节，不带 Skills 与 Memory 指令（权限边界设计）。

- **[[三类评分器]]**（按确定性排序）：

| 评分器 | 方式 | 确定性 | 适用 |
|---|---|---|---|
| 代码评分器 | 字符串匹配、单元测试 pass/fail、结构比对、工具调用参数验证 | 最高 | 有明确正确答案的任务 |

- **[[先修评测再改agent]]**：评测系统四类失真（环境资源不足/评分器 bug/用例与生产脱节/只看聚合分数）表现与模型退化一模一样；环境噪声实验——容器资源 1x→Uncapped 后基础设施错误率跌至近 0 而模型得分几乎不变，"失败"多为环境噪声，先查环境再动 Agent。

OpenClaw 是全文原则的可运行载体，五层解耦架构（[[openclaw五层架构]]，五层表完整）：

### 渠道解耦与最小可运行链路

**[[messagebus渠道agent解耦]]**（原文代码）：

```javascript
// 入站消息结构，Agent 不知道来自哪个平台
const inbound = { channel, session_key, content };
// 每个渠道只需实现三个方法
class ChannelAdapter {
```

**最小可运行链路**（原文完整 AgentLoop 代码；注意 `registerDefaultTools` 注释口径为 shell、fs、web、message、cron，与五层表 shell/fs/web/browser/MCP 存在口径差异）：

```javascript
// MessageBus：渠道和 Agent 之间的解耦层
class MessageBus {
  async consumeInbound() { /* 从队列取下一条消息 */ }
  async publishOutbound(msg) { /* 路由到对应渠道发出 */ }
}
// AgentLoop：消费消息，驱动 ReAct 循环
class AgentLoop {
  constructor(bus, provider, workspace) {
    this.bus     = bus;
    this.provider = provider;
    this.tools   = registerDefaultTools(workspace); // shell、fs、web、message、cron
    this.sessions = new SessionManager(workspace);   // 持久化会话历史
    this.memory  = new MemoryConsolidator(workspace, provider); // 跨会话记忆整合
  }
  async run() {
    while (true) {
      const msg = await this.bus.consumeInbound();
      this.dispatch(msg); // 不 await：不同 session 的消息并发处理，互不阻塞
    }
  }
  async dispatch(msg) {
    const session = this.sessions.getOrCreate(msg.sessionKey);
    await this.memory.maybeConsolidate(session); // token 超阈值时自动整合记忆
    const messages = buildContext(session.history, msg.content);
    const { text, allMessages } = await this.runLoop(messages);
    session.save(allMessages);
    await this.bus.publishOutbound({ channel: msg.channel, content: text });
  }
  async runLoop(messages) {
    for (let i = 0; i < MAX_ITER; i++) {
      const resp = await this.provider.chat(messages, this.tools.definitions());
      if (resp.hasToolCalls) {
        for (const call of resp.toolCalls) {
          const result = await this.tools.execute(call.name, call.args);
          messages = addToolResult(messages, call.id, result);
        }
      } else {
        return { text: resp.content, allMessages: messages }; // 无工具调用，本轮结束
      }
    }
  }
}
// 入口：接上渠道，启动
const bus = new MessageBus();
new TelegramChannel(bus, { allowedIds }).start(); // Channel 只负责收发
new AgentLoop(bus, new ClaudeProvider(), WORKSPACE).run();
```

**[[session并发串行边界]]**：dispatch 不 await，跨 session 并发互不阻塞；同 session 内必须串行（并发写历史与触发 compact 有竞态），生产环境需按 sessionKey 维护队列或 mutex；session 管理不下沉 Channel 层。

### 系统提示与触发模式

**[[系统提示分层叠加]]**：自下而上五层——平台与运行时信息→身份层→记忆层→Skills 层→运行时注入；常驻文件为 SOUL.md、AGENTS.md、TOOLS.md、USER.md、MEMORY.md + Skills 索引，会话级动态注入时间/渠道名/Chat ID。**[[三触发模式加载差异]]**：普通会话加载完整系统提示；子 Agent 仅加载基础运行时信息；heartbeat 单独加载 HEARTBEAT.md；长任务额外加身份重申。

**[[soul-md身份约束文件]]**：SOUL.md 定义 Agent 的身份、约束和完成标准，含四部分：身份定义；核心行为约束（工作空间外不改、不可逆操作先确认、信息不足先提问、保留验证意识）；任务完成标准（完成 = 验证通过 + 结果明确反馈；没验证通过不算完成、部分完成不能报完成、不可逆操作必须先向用户确认）；长任务身份重申机制。

**[[cron与heartbeat主动触发]]**：cron 按 cron 表达式直接触发（CronTask 四字段，示例：工作日早 9 点日志归类）；heartbeat 每 5 分钟轮询待处理任务。

**[[长任务断点恢复]]**：任务进度写 `.openclaw/tasks/{taskId}.json`，每完成一步保存，重启从断点续跑；任务超半小时，崩溃恢复是必选项不是可选项。**[[长任务身份重申]]**：任务超 20 轮后每轮开始重申身份/任务/步骤 X/Y/下一步，压住任务漂移。

```typescript
async function executeShell(args: string[], cwd?: string): Promise<string> {
  // realpath 解析符号链接，path.relative 检查是否在工作空间内
  const workDir = path.resolve(cwd ? WORKSPACE);  // 原文疑为 cwd ?? WORKSPACE

  // 使用 execFile 而非 exec，避免 shell 注入
  const result = await execFile(args, args.slice(1), {  // 原文疑为 execFile(args[0], args.slice(1))

}
```
