## 核心论点

让 AI 持续产出可用的东西，靠的不仅是更好的 Prompt，还需要一套能管住它的工程结构（前言，正文加粗强调，见 [[工程结构优先论]]）。全文以 [[网盘]] Android 存量代码转 [[KMP]] 迁移为实践载体，将这一工程结构具体化为三层架构（[[三层架构管住AI输出]]）：Skill 负责执行、SubAgent 负责调度、Agent Team 负责协作，三者是分层互补而非替代关系。

## 01 章：问题背景 —「迁得稳不稳」

KMP 迁移的核心挑战不是"能不能迁"，而是"迁得稳不稳"。[[网盘]] 主端积累了大量存量代码，页面迁移涉及 UI 层、布局文件、业务逻辑、资源文件四类内容，依赖关系错综复杂，遗漏在编译阶段集中暴露。人工梳理效率低、遗漏率高；AI 直接生成"看起来能跑，接进工程就不行"。AI 直接迁移暴露三个规律性问题（[[AI迁移三规律性问题]]）：

| 规律性问题 | 具体表现 | 对应方向 |
|-----------|---------|---------|
| 同一类操作，不同对话结果不一样 | AI 每次重新理解任务，上下文稍有变化输出就漂移 | Skill |
| 任务越复杂，后期幻觉越多 | 迁移一个页面加载几十个文件，后期早期文件细节被压缩，AI 生成「不存在的方法」 | SubAgent |
| 并行处理没有机制支撑 | UI/布局/业务逻辑本可同时处理，但只有一个对话窗口只能串行 | Agent Team |

## 02 章：三层方案全貌

三层架构定义表：

| 层级 | 技术 | 解决 | 位置 |
|------|------|------|------|
| 执行层 | Skill | 单点执行不稳定 | 所有具体任务的执行单元 |
| 调度层 | SubAgent | 长链路上下文膨胀 | 转化阶段的串行步骤调度 |
| 协作层 | Agent Team | 多类型任务串行效率低 | 提取阶段的并行分工 |

两阶段迁移流程（[[两阶段迁移流程]]）：

- 提取阶段：Agent Team 四路并行（UI、布局、业务逻辑、资源同时提取）
- 转化阶段：SubAgent 串行推进（模块生成 → 资源转化 → 业务代码迁移 → UI 转化），步骤间通过 Memory 传递关键产出
- 兜底：每个执行节点由 Skill 保证输出稳定

选型判断依据只有一条：任务之间有没有强依赖（[[强依赖选型判据]]）：

| 任务关系 | 选型 |
|---------|------|
| 有强依赖，需串行 | SubAgent |
| 无强依赖，可并行 | Agent Team |
| 具体执行动作 | Skill |

## 03 章：Skill — 单点输出稳定

- 输出不稳定的根源是 AI 每次都在"重新理解"任务——不是模型问题，而是没把"怎么做"固化下来。
- 写 Skill 最有用的动作是 Checklist：逐项打勾，解决多步骤任务跳步遗漏（[[checklist驱动skill]]）。
- 分层管理文件：核心规则放主文件，边界情况放 references 目录；Skill 文件太长会导致注意力分散、关键规则被稀释（[[skill分层文件管理]]）。
- 关键决策是把提取和校验拆开：同一个 Skill 里 AI"自己审查自己"天然放水，类比代码 Review 中作者自审（[[ai自审偏差]]）。
- 拆成三个独立 Skill（[[提取校验修复三skill拆分]]）：

| Skill | 职责 |
|-------|------|
| extractor | 以调用语句为入口扫描依赖，生成初始提取包 |
| validator | 独立校验，关注"还缺什么"而非"提了什么" |
| fixer | 只处理 validator 指出的缺口，定向补充 |

- 转化阶段复用同一拆分结构：converter → validator → fixer，证明拆分逻辑通用。

## 04 章：SubAgent — 长链路上下文控制

- 单对话跑完整流程的后期症状：引用不存在的方法、资源 ID 映射对不上、早期约束失效。
- 根因：上下文膨胀必然发生，AI 用"看起来合理"的内容填充被压缩的细节——这是幻觉的来源，比明显错误更难处理（[[上下文膨胀必然论]]）。
- 解法：按步骤拆给拥有独立上下文的 SubAgent，用 Agent-Memory 传递：每个 SubAgent 把关键信息提炼成结构化文件，下一个 SubAgent 启动时读取（[[agent-memory结构化提炼]]）。
- 落地案例：资源转化 SubAgent 写入资源 ID 映射表 → UI 转化 SubAgent 读取后准确处理引用。
- 强调：Memory 文件不是对话记录备份，而是"后续步骤需要什么"的提炼，内容示例为资源映射表、模块结构配置、已确认的接口契约。

## 05 章：Agent Team — 多类型任务并行

- 四类提取文件（UI 组件、布局文件、业务逻辑、资源文件）逻辑完全不同但无强依赖；串行则耗时累加且单 SubAgent 上下文膨胀、专注度分散。
- 拆给四个专业 Teammate 并行，各自只处理一类文件；专注布局的 Teammate 对 include 嵌套引用的识别比通用 Agent 准确很多（[[并行质量收益论]]）。
- 跨 Teammate 依赖通过 Mailbox 消息通道实时处理（[[mailbox消息通道]]）：UI 提取 Teammate 发现代码里动态创建了 Dialog → 通知布局提取 Teammate 补充该 Dialog 的布局文件；业务逻辑发现 API 调用引用了某字符串资源 → 通知资源提取 Teammate 补充（strings.xml/colors.xml 等资源文件）。无需等一个提取全部完成再补充，也无需重新启动一轮。
- 实际效果：相比串行，总耗时接近四类任务里最慢的那条路径而非四段累加（定性声明）；专注度提升带来的提取质量改善比速度收益更明显。

## 06 章：经验总结（四条）

1. **Skill 是被真实错误倒逼出来的，不是提前规划出来的**：前期规范粗糙，在反复纠错中补充边界条件和反例；"这类问题每次都要纠正"就是固化信号；迭代过程把团队踩过的坑沉淀成下次不会再踩的规则（[[skill错误倒逼生成]]）。
2. **上下文膨胀的临界点比想象中早，漂移比崩溃更危险**：幻觉是逐渐偏离而非突然全错；及早拆分任务比等幻觉出现再排查更划算（[[漂移比崩溃危险]]）。
3. **Memory 文件要提炼，不要备份**：原样传递对话历史没有意义，只传后续步骤需要消费的结构化信息；这一原则在实践中需要反复强化。
4. **并行的收益不只在速度上**：专注分工本身提升单类任务处理质量。

## 关键主张清单

- 选型判断依据只有一条：任务之间有没有强依赖（串行 → SubAgent，并行 → Agent Team，执行动作 → Skill）
- 并行不只是效率问题：专注分工本身提升单类任务处理质量，质量改善往往比缩短的时间更重要
- 四路并行不是完全独立的，跨类型依赖由 Mailbox 消息通道实时处理
- 相比串行，并行总耗时接近最慢路径而非四段累加（定性声明）
- 整个方案的稳定性最终由 Skill 规范质量决定；Skill 须"约束执行过程"而非"描述执行目标"
- 提取和校验必须拆开：同 Skill 自审天然放水
- Checklist 是写 Skill 最有效的约束
