# Agent Skill规范、构建与设计模式

珂罗著，微信公众号「千问AI平台」2026-05-12 08:30 发布（IP 属地浙江，原创标记），经阿里系导读栏目「阿里妹导读」发布并附免责声明"仅代表个人观点"。文末招聘启事披露：本文为**淘天集团‑淘宝平台事业部‑客户运营部**智能研发实践经验总结（联系邮箱 fangkele.fkl@taobao.com）。全文定位为 **Anthropic（开放标准 + Skill-Creator + best-practices + Writing-Skills）+ Google（ADK 设计模式）双厂商综合来源**，实践主体为淘天淘宝平台事业部客户运营部。

## 一、Skill 规范

### 1.1 定义与开放标准史

核心论断："**Skill 不是 Prompt——它是围绕任务、工具、流程和输出边界的结构化行为设计**"。Skill 是"可复用的 Prompt 增强包"，通过渐进式加载机制为 Agent 注入领域知识和工作流程。2025 年 12 月 Anthropic 将 Skill 规范作为**开放标准**发布（https://agentskills.io/specification ），官方仓库 https://github.com/anthropics/skills ，已被 **33+ 个 Agent 产品**采纳（Claude Code、OpenAI Codex、GitHub Copilot、VS Code、Cursor、Gemini CLI、Kiro 等）。量化声明登记至 [[ai工程量化效果声明追踪]]。

### 1.2 SKILL.md 格式规范

SKILL.md = YAML frontmatter（元数据）+ Markdown body（指令正文）。最小形态只需一个文件。目录最小结构：

```bash
skill-name/
├── SKILL.md          # 必需：YAML 元数据 + Markdown 指令
├── scripts/          # 可选：可执行脚本
├── references/       # 可选：按需加载的参考文档
└── assets/           # 可选：模板、资源文件
```

YAML frontmatter 字段表（原样保留）：

| 字段 | 是否必填 | 说明 | 约束 |
|------|---------|------|------|
| name | 是 | Skill 的唯一标识名 | 最多 64 个字符，仅允许小写字母、数字和连字符，不能以连字符开头或结尾，不能包含连续连字符，必须与所在文件夹名一致 |
| description | 是 | 描述这个 Skill 做什么、什么时候使用 | 最多 1024 个字符，不能为空，应该包含帮助 AI 识别相关任务的关键词 |
| license | 否 | 许可证信息 | 许可证名称或指向许可证文件的引用 |
| compatibility | 否 | 环境兼容性要求 | 最多 500 字符，说明需要的运行环境或依赖 |
| metadata | 否 | 自定义扩展元数据 | 键值对映射，可存储规范之外的额外属性 |
| allowed-tools | 否 | 预授权工具列表 | 空格分隔的字符串，实验性功能 |

name 命名规则（1-64 字符；仅 `a-z` 与 `-`；不能以连字符开头/结尾；不得含连续连字符 `--`；必须与父目录名称匹配）：

```bash
# 合法示例
name: pdf-processing
name: data-analysis
name: code-review

# 非法示例
name: PDF-Processing    # 不允许大写字母
name: -pdf              # 不能以连字符开头
name: pdf--processing   # 不允许连续连字符
```

description 好差对照：

```
好例（含作用、使用时机、识别性关键词）：
description: Extracts text and tables from PDF files, fills PDF forms, and merges multiple PDFs. Use when working with PDF documents or when the user mentions PDFs, forms, or document extraction.

差例（过短、无触发场景、无使用时机）：
description: Helps with PDFs.
```

正文建议：分步骤说明、输入输出示例、边界情况，**≤500 行**，内容多时拆分到单独文件。文件引用使用相对 Skill 根目录路径，建议保持一层深度。最简 SKILL.md 仅需 `name` + `description` 两个 frontmatter 字段。

### 1.3 三层渐进式加载机制

L1 目录层（name+description 以 XML 格式注入系统提示词，约 50-100 tokens，口径待核）→ L2 指令层（触发后读取 SKILL.md 正文，≤500 行）→ L3 资源层（references/assets 按需加载）。明确借鉴 UI/UX 渐进式信息披露策略。关键量化声明：即使安装 20 个 Skill，初始加载仅 1000-2000 tokens；相比单体式提示词**上下文使用量减少约 90%**（登记 [[ai工程量化效果声明追踪]]）。总结章定性：渐进式加载是核心机制，解决 Agent 系统上下文膨胀问题。详见 [[skill渐进式加载机制]]。

### 1.4 触发机制设计（Model-driven Activation）

触发完全依赖 description、由模型自主判断、非关键词硬编码。写作四要点：祈使语气、聚焦用户意图、适当强势、含关键触发词。详见 [[模型驱动触发逻辑]]。

## 二、Skill-Creator（Anthropic 官方元工具）

Skill-Creator 是 Anthropic 官方"用来创建 Skill 的 Skill"，设计哲学为"像做机器学习一样做 Prompt Engineering"（详见 [[像做机器学习一样做prompt工程]]）。三大核心思想：泛化而非过拟合、**解释"为什么"而非堆砌"必须"**（作者标注为全文最核心的洞察：LLM 有良好心智理论，解释动机优于 ALWAYS/NEVER 式死板约束，与 [[代码库模式大于指令]] 精神相通）、提取重复模式。

### 2.3 六阶段开发生命周期

| 阶段 | 关键动作 |
|------|---------|
| 一：需求捕获 | 理解意图、明确触发场景、确定输出格式、区分客观可验证 vs 主观创意型 |
| 二：编写 Skill | 编写 SKILL.md（YAML frontmatter + 指令主体）+ 准备辅助资源 |
| 三：测试执行 | 设计 2-3 个测试用例 → 并行启动 with_skill / without_skill 两组子 Agent（A/B 测试）→ 等待期起草量化断言 → 捕获 timing 数据 |
| 四：评估与评审 | Grader 评分 → 聚合基准数据 → Analyzer 分析模式 → 生成 Eval Viewer → 用户浏览器评审 → 收集 feedback.json |
| 五：迭代改进 | 分析反馈 → 泛化改进（避免过拟合）→ 重写 Skill → 新 iteration 目录 → 回到阶段三 |
| 六：优化与发布 | Description 优化（run_loop.py）→ 训练/测试集分割 → 自动迭代改进描述 → 校验 → 打包 .skill |

### 2.4 三 Agent 评估链（Grader / Comparator / Analyzer）

- **Grader（评分者）**8 步流程：读 Transcript → 检查输出文件 → 评估断言 → 提取隐含声明 → 读执行者笔记 → **评价评估本身** → 写结果 → 读指标数据。核心原则："A passing grade on a weak assertion is worse than useless — it creates false confidence."（薄弱断言通过比无用更糟，制造虚假信心）
- **Comparator（盲比较者）**：借鉴医学双盲实验去偏见；双维度评分——内容（正确性/完整性/准确性，各 1-5）+ 结构（组织性/格式化/可用性，各 1-5），综合总分 1-10；判定优先级：总分 > 断言通过率 > 平局
- **Analyzer（分析者）**：角色 A 事后揭盲归因（优先级 high/medium/low；类别 instructions/tools/examples/error_handling/structure/references）；角色 B 基准分析器关注双配置 100% 通过的断言（无区分力）、高方差断言（不稳定）、时间/token 异常值

### 2.5 评测数据管道（references/schemas.md）

```
evals.json          ─── 测试定义（prompt + expectations）
    ▼
timing.json         ─── 运行计时（来自子 Agent 完成通知）
    ▼
metrics.json        ─── 执行指标（工具调用次数、文件数等）
    ▼
grading.json        ─── 评分结果（断言通过/失败 + 证据）
    ▼
benchmark.json      ─── 聚合基准（mean ± stddev，delta 对比）
    ▼
comparison.json     ─── 盲比较结果（A/B 评分 + 赢家）
    ▼
analysis.json       ─── 事后分析（改进建议 + 执行模式洞察）
    ▼
history.json        ─── 版本追踪（迭代历史 + 当前最佳）
```

注意计数出入：正文称"7 种 JSON 数据结构"，管道图列出 8 个文件。详见 [[skill评测数据管道]]。

### 2.6 实战 Walkthrough（code-review skill，实际为 Step 1-8）

Step 1 自然语言提需求自动触发 Skill-Creator → Step 2 生成 SKILL.md → Step 3 设计 2-3 个测试用例（evals.json 样例：`{"skill_name": "code-review", "evals": [{"id": 1, "prompt": "Review this PR that adds user authentication with JWT tokens", "expected_output": "Structured review report with security considerations"}, ...]}`）→ Step 4 with/without_skill 并行运行 → Step 5 generate_review.py 打开 Eval Viewer 人工评审 → Step 6 读取 feedback.json 迭代改进 → Step 7 run_loop.py 自动优化 description → Step 8 打包发布。

触发评估集（trigger_eval.json）可见样本 **18 条，9 true / 9 false 严格平衡**，反例覆盖"相邻但不触发"的高混淆任务（debug segfault、性能优化、重构依赖注入、写单元测试、解释语法、代码翻译、报错解读），正例含刻意模糊表述（"not a formal review, just a sanity check" → true）测试召回边界。完整表格见 [[触发测试集]]。

feedback.json 结构（原样保留）：

```json
{
  "reviews": [
    { "run_id": "eval-1-java-npe-with_skill",      "feedback": "", "timestamp": "2026-03-20T07:22:12.127Z" },
    { "run_id": "eval-1-java-npe-without_skill",   "feedback": "", "timestamp": "2026-03-20T07:22:12.127Z" },
    { "run_id": "eval-2-python-n+1-with_skill",    "feedback": "", "timestamp": "2026-03-20T07:22:12.127Z" },
    { "run_id": "eval-2-python-n+1-without_skill", "feedback": "", "timestamp": "2026-03-20T07:22:12.127Z" },
    { "run_id": "eval-3-typescript-bugs-with_skill",    "feedback": "", "timestamp": "2026-03-20T07:22:12.127Z" },
    { "run_id": "eval-3-typescript-bugs-without_skill", "feedback": "", "timestamp": "2026-03-20T07:22:12.127Z" }
  ],
  "status": "complete"
}
```

Step 7 / Step 8 命令：

```bash
python -m scripts.run_loop \
  --eval-set evals/trigger_eval.json \
  --skill-path path/to/code-review \
  --model claude-sonnet-4-20250514 \
  --max-iterations 5 \
  --verbose

python -m scripts.package_skill path/to/code-review
# 生成 code-review.skill 文件，可分享安装
```

### 2.7 五大优势与六大局限

五优势（作者自评）：方法论完整 / 评估体系严谨 / 零依赖可移植（纯 Python stdlib + `claude` CLI）/ 人机协作设计（Eval Viewer）/ 自举式架构（用 Skill 框架管理 Skill 生命周期，与 [[自举式开发]] 同构）。

六局限（详见 [[skill-creator六大局限]]）：问题一 Token 消耗极高、成本不透明——GitHub Issue #514（anthropics/claude-plugins-official，jroy-poka，2026-03-04）："20 个评估查询 × 每条 3 次运行 = 60 个会话，消耗约 69% 的 5 小时配额，0 条可执行结果"；根因为 SKILL.md 第 385 行 `--model <session-model>` 透传机制；社区建议 eval 默认模型改为 claude-haiku，**成本降低 10-20 倍、触发检测精度等价**，但 Issue 截至成文仍 Open（详见 [[评估任务模型降配]]）。问题二流程冗长（9 个交互确认节点，每轮迭代 4 步手动操作）。问题三子任务并发复杂（单轮评测子 Agent 公式 N×2+N+1+可选 N，3 用例即 10 个，受 Claude Code 并发限制易排队）。问题四**操作型 Skill 触发失效**——"operational workflow skills show 0% recall regardless of description quality"（详见 [[操作型skill触发失效]]）。问题五 Skill 膨胀——Medium 引语"A 5KB skill balloons to 50KB"（详见 [[skill膨胀风险]]）。问题六学习曲线陡峭（需理解三层加载/7 种 JSON Schema/子 Agent 原理/触发率统计/防过拟合分割 5 项知识领域）。社区观点："对于简单需求，直接手写 SKILL.md 比用 skill-creator 快得多。"

## 三、Writing-Skills（Superpowers 元技能）

[[superpowers插件]] 定位术语 **Vibe Engineering**："在 AI 快速迭代的基础上强制注入软件工程纪律"，目标平台 Claude Code、Cursor、Codex，含 **14 个可组合 Skill**，四大核心理念：测试先行（TDD）/ 系统化优于随机化（Process over Guessing）/ 复杂度缩减（Simplicity as Primary Goal）/ 证据优于声明（Verify before Declaring Success）。详见 [[vibe-engineering]]。官方仓库：https://github.com/obra/superpowers 。Writing-Skills 是其中的元技能，教 Agent 如何创建新 Skill，与 Skill-Creator"目标相似，但方法论截然不同"（元技能 vs 元工具）。详见 [[writing-skills]]。

### 3.3 TDD 全循环（[[像做tdd一样做skill]]）

| TDD 概念 | Skill 创建 |
|---|---|
| 测试用例 | 压力场景 + 子代理 |
| 生产代码 | Skill 文档（SKILL.md） |
| 测试失败（RED） | Agent 在没有 Skill 时违反规则（基线） |
| 测试通过（GREEN） | Agent 在有 Skill 时遵守规则 |
| 重构（REFACTOR） | 堵住漏洞，同时保持合规 |

RED 压力场景示例：4 小时完成的功能 + 手动测试过边界 + 下午 6 点 6:30 有晚餐 + 明天 9 点代码评审 + 刚意识到没写测试，选项 A 删除重来 / B 先提交 / C 现在写测试（延迟 30 分钟）——无 Skill 的 Agent 选择 B/C 并给出合理化借口。GREEN 原则：只针对基线中发现的具体失败编写 Skill。REFACTOR 堵漏机制见 [[合理化借口反驳]]（借口-现实对照表："保留作为参考，先写测试"→"你会改编它。那就是事后测试。删除就是删除。"；"我遵循的是精神而非字面"→"违反字面就是违反精神。"；"太简单不需要测试"→"简单的代码也会出错。测试只需 30 秒。"）。

### 3.4 四种 Skill 类型（[[skill四类型分类法]]）

| Skill 类型 | 定义 | 测试方法 | 成功标准 |
|---|---|---|---|
| 纪律执行型 | 强制遵守规则（如 TDD、验证要求） | 压力场景：时间+沉没成本+疲劳组合施压 | Agent 在最大压力下仍遵守规则 |
| 技术指导型 | 具体方法的操作指南（如条件等待、根因追踪） | 应用场景：能否正确应用？边界情况？指令有无缺口？ | Agent 成功将技术应用到新场景 |
| 思维模式型 | 解决问题的心智模型（如降低复杂度、信息隐藏） | 识别场景：能否识别何时适用？何时不适用？ | Agent 正确判断何时/如何应用模式 |
| 参考资料型 | API 文档、命令参考、库指南 | 检索场景：能否找到正确信息？常见用例是否覆盖？ | Agent 找到并正确应用参考信息 |

### 3.5 Description 关键要点（[[description只写触发条件]]）

作者标注为"writing-skills 中最重要的发现之一"：description 只应描述触发条件，**绝不要总结工作流程**，否则 Agent 会按 description 走捷径跳过 Skill 正文：

```yaml
# ❌ 总结了工作流 → Agent 可能走捷径，跳过 Skill 正文
description: Use when executing plans - dispatches subagent per task
  with code review between tasks

# ✅ 只有触发条件 → Agent 会完整阅读 Skill
description: Use when executing implementation plans with independent
  tasks in the current session
```

### 3.6 Anthropic 官方最佳实践（转述自 writing-skills 引用的 anthropic-best-practices.md）

- **简洁原则**（[[skill简洁性原则]]）：context window 是公共资源、默认假设 Claude 已聪明、只添加增量信息（~50 vs ~150 tokens 对比）
- **自由度分级**（[[skill自由度分级]]）：高（多种方法有效）/ 中（有首选模式但允许变化）/ 低（操作脆弱、一致性关键）
- **工作流与反馈循环模式**（[[skill工作流与反馈循环模式]]）：可追踪检查清单模式 + 验证器→修复→重复直到通过的循环模式；验证脚本错误信息要具体到字段级（`"Field 'signature_date' not found. Available fields: customer_name, order_total"`）
- **双 Claude 迭代开发模式**（[[双claude迭代开发模式]]）：Claude A（专家）设计优化 ↔ Claude B（测试者）真实任务实测观察，"最有效的 Skill 开发过程"

## 四、Skill 设计模式（Google ADK）

核心论断：**规范只定义"Skill 长什么样"，不定义"内部逻辑该怎么设计"**（"一个封装 FastAPI 规范的 Skill 和一个分 4 步执行的文档流水线 Skill，虽然外表都叫 SKILL.md，但内部结构完全不是一回事"）。Google ADK 团队跨生态研究（Anthropic 仓库、Vercel、Google 内部指南）归纳出 5 种反复出现的设计模式，原文出处：https://x.com/GoogleCloudTech/status/2033953579824758855 。详见 [[skill五种设计模式]]。

4.2 设计模式选择指南（原表）：

| 你需要什么？ | 选择哪种模式 |
|---|---|
| 特定技术栈的专家知识 | Tool Wrapper |
| 一致的结构化输出 | Generator |
| 自动化代码/内容审查 | Reviewer |
| 需求不明确，需先收集信息 | Inversion |
| 复杂的多步骤任务 | Pipeline |
| 不确定？ | 从 Tool Wrapper 开始 |

4.3 模式组合推荐（原表）：

| 组合 | 说明 | 场景 |
|------|------|------|
| Pipeline + Reviewer | 管道最后一步加自动审查 | 文档生成后自动质量检查 |
| Generator + Inversion | 先收集信息再填充模板 | 需用户输入的结构化文档生成 |
| Pipeline + Tool Wrapper | 管道某些步骤加载专家知识 | 多步骤代码生成 |
| Inversion + Pipeline | 先完成需求收集再进入执行流水线 | 复杂项目全流程 |

五模式示例 SKILL.md 签名与结构要点：

| 模式 | name | 内部结构要点 |
|---|---|---|
| Tool Wrapper | api-expert | 指向 references/conventions.md；SKILL.md 告诉 Agent 去哪加载规范而非内置规范 |
| Generator | report-generator | 加载 style-guide.md + report-template.md → 主动询问缺失信息（主题/关键发现/目标受众）→ 填模板 → 返回 |
| Reviewer | code-reviewer | 加载 review-checklist.md → 逐条应用 → 记录行号/严重等级/原因/建议；"WHY not WHAT" |
| Inversion | project-planner | 三阶段采访（问题探索→技术约束→综合整理），全程禁建；"在所有阶段完成之前，请勿开始构建" |
| Pipeline | doc-pipeline | 解析清点→生成文档字符串（**用户确认前不得进入第三步**）→组装→质检，不得跳步 |

Pipeline"确认前不得继续"与爱奇艺 [[blocker-gate]]、vivo [[验证门禁化]] 构成三方独立收敛的硬门控共识（synthesis 素材）。

## 矛盾与张力

1. **description 双向约束张力**：总结层"写好 description 比写好指令主体更重要" ↔ Issue #514"操作型 Skill recall=0% 与 description 质量无关"——两说并存待裁决（见 [[description只写触发条件]] 与 [[操作型skill触发失效]]）
2. **Grader LLM 自评张力**：Skill-Creator 的"评价评估本身"属 LLM 自评，与 [[llm自我评估不可靠]] 论点存在张力；Skill-Creator 以盲比较+结构化断言+角色分离作缓解（见 [[grader自我批评机制]]）
3. **方法论路线对照（非矛盾）**：Skill-Creator ML 式自动评测（run_loop.py）vs Writing-Skills TDD 式（测试先行）vs 双 Claude 人工观察迭代——来源并置为"构建方法论"层但未做正面对比，适用边界转 wiki 侧综合
4. **作者自披露张力**：2.7.1"评估体系严谨" vs Issue #514"0 actionable results"；2.7.1"人机协作设计" vs 问题二"流程冗长"——作者主动披露，属 [[ai工程量化效果声明追踪]] 的"自报局限"正例
5. **计数出入三处**：7 种 JSON vs 8 个文件；"五步实战" vs 实际 Step 1-8；触发集可见 18 条 vs Issue #514"20 eval queries"
6. 未量化主张："反馈循环能显著提升输出质量"无量化数字；"10-20x 成本降低"为社区口径；"约 90% 上下文节省"口径待核
