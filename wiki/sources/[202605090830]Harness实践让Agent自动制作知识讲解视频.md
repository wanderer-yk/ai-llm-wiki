## 核心命题：视频是 Vibe Coding 出来的网页

作者声明其知识讲解视频既不是视频生成模型也不是 NotebookLM 做的，而是"Vibe Coding 出来的网页"，核心理由是**可控**——字体、配色、每步停留时长、精确数字均可改几行代码搞定，比视频模型"抽卡"稳定且成本低（原话："答案就俩字：可控"）。作者认为 NotebookLM 只能出静态图做不了动画，Remotion 框架反而限制模型发挥（作者主观判断，无第三方佐证）。

上期视频案例：输入仅一篇 Anthropic 博客文章（claude.com 的 Claude Code prompt caching 文，URL：`https://claude.com/blog/lessons-from-building-claude-code-prompt-caching-is-everything`），输出网页将原文拆为 **13 个章节、100 多个细粒度讲解步骤**，16:9 画布、悬浮底部隐藏进度条、画面无页眉/页码/品牌标识（纯净录屏画面）。注意：本次实战项目实际为"50 多步"，"100+ 步"为能力上限与实例规模之差。

## 无 Harness 的失败模式与 Harness 定义

直接下指令的失败模式：①稿子与画面对不上；②章节数与音频数不一致；③后期章节风格漂移。Harness 的定义（职责四要素）："划定边界、管理状态、设立检查点、在关键节点拦住错误"，详见 [[Harness职责四要素]]。

## 视频网页四步关键流程

文章变口播稿（书面语→短句、口语、第二人称）→ 口播稿拆开发大纲（段→步骤、步骤→章节、章→话题，大纲是开发稳定性关键）→ 每步做视觉演示（TCP 握手画时序图、DNS 查询画节点链路、反垃圾审判画评分仪表盘，"把抽象概念演出来"）→ 步骤与口播对齐。详见 [[视频网页四步关键流程]]。

## 成熟 Harness 六大核心部分（逐字表格）

| 核心部分 | 它解决的问题 | 典型作用 |
|---------|------------|---------|
| 上下文管理 | 模型到底看到了什么 | 组织系统提示词、项目文档、历史对话、任务状态、外部资料 |
| 工具系统 | 模型到底能做什么 | 搜索、读写文件、调用 API、执行代码、操作浏览器 |
| 执行编排 | 模型下一步该做什么 | 决策、分步执行、工具调用、结果回写 |
| 状态与记忆 | 系统如何跨步骤保持连续性 | 保存任务进度、中间结果、长期偏好 |
| 评估与观测 | 系统怎么知道自己做得对不对 | 结果验收、过程追踪、指标监控、质量评估、错误归因 |
| 约束与恢复 | 出错了怎么办，怎么避免跑偏 | 权限控制、格式约束、重试机制、回滚与校验 |

详见 [[Harness六大核心部分]]；与爱奇艺五要素的对照见 [[ConardLi六核心与爱奇艺Harness五要素对比]]。

## Skill 核心设计（第 2 章，2.1–2.7）

- **2.1 执行和编排**：四阶段两检查点流水线（内容编写→Plan 检查点→开发→Audio 检查点→音频合成→录屏），检查点处 Agent 被强制停下，详见 [[四阶段两检查点流水线]]。
- **2.2 上下文管理**：信息拆成六份文档按阶段按需读取，对抗"注意力稀释"，详见 [[分阶段文档按需加载]]。
- **2.3 状态与记忆**：三文件工作记忆——"大纲管结构边界，口播稿管叙事节奏，原文章管信息密度"，`outline.md` 兼任持续记忆与任务边界，详见 [[文件化工作记忆]]。
- **2.4 工具系统**：无特殊工具，用好文件读写即可；并行开发的严格隔离机制四条，详见 [[并行开发隔离机制]]。
- **2.5 约束与恢复**：反馈修复最小切片，"出错"最常见形式是用户觉得不对而非代码报错，详见 [[反馈修复最小切片]]。
- **2.6 评估与观测**：作者称"花心思最多的地方"——自评失真对策 = 硬性自检规则 + 三级评审执行方式，见 [[硬性自检规则]]、[[三级评审执行方式]]；与既有页 [[评测agent乐观偏差]] 为同一现象两种命名。
- **2.7 回过头看**：该 Skill 与 OpenAI/Anthropic 搭的 Harness 本质无区别，只是层级不同，详见 [[Skill级Harness论]]。

**自检清单表（逐字）**：

| 产出 | 自检清单 |
|------|----------|
| script.md（口播稿） | 口语化、B站风、无AI味、信息保留≥60%、念出来不别扭 |
| outline.md（开发计划） | 节奏规划（step数/时长/信息池）、无动画细节、与script时间误差<10% |
| CHAPTER-CRAFT.md（单章实现） | 有动图、不套模板、字大留白、逐个揭示、素材真实、代码隔离 |

**问题层→最小切片对照表（完整四行）**：

| 问题层 | 最小切片 |
|--------|----------|
| 节奏（太快/太慢） | 调整对应 step 的 narration 文本长度，或拆/合 step |
| 视觉（动画不对） | 只改对应 step 的 CSS / 动画逻辑 |
| 内容（信息太薄/太密） | 回 article.md 信息池补充或删减，只改对应 step |
| 代码（编译报错） | 定位具体文件和行号，点修 |

## 环境搭建：四工具链（第 3 章）

Claude Code + MiniMax + CC Switch + MMX CLI。（记录：分析过程中曾推测"第四工具=录屏"，正文 3.4 与 4.7 双重证实第四工具实为 MMX CLI。）

```bash
curl -fsSL https://claude.ai/install.sh | bash
```

**CC Switch 下载地址（逐字）**：`https://github.com/farion1231/cc-switch/releases/tag/v3.14.1`；配置流程："+" → 选预设 MiniMax 供应商 → 填 API Key → 模型名全部改为 `MiniMax-M2.7` → 保存 → 首页"启用" → 终端 `claude` 验证。

## 实战：完整流程演示（第 4 章，输入文章《一封邮件发出后的 600 毫秒》）

- **4.1 启动**：`tmux` 进入会话后 `claude --dangerously-skip-permissions`。该参数跳过每次工具调用的权限确认，避免"并行开发时每写一个文件都要手动点确认，整个流程会被打得很碎"；仅限可信目录，"不要在陌生仓库里随便开"（与 [[agent-control-plane]] 权限边界理念互为镜像）。
- **4.2 写—审—校编排**：提示词一（逐字）：`读取 @article.md ，按照 /web-video-presentation 要求，完成第一步。注意编写完成后使用 Agent Teams 创建两个独立 Agent 进行质检。` 实际编排：Content Writer Agent 写口播稿+大纲 → 两个 Reviewer Agent 分别质检 → 主 Agent 校对终版。口播稿 B 站化："句子短一点、节奏快一点、听起来像人在聊天"。
- **4.3 第一次人工确认四问**：①稿子/大纲是否要改；②视觉主题十选一（作者选 blueprint）；③素材准备三模式（作者实战选择清单外的"Agent 自绘"）；④后续章节开发模式三选一（作者选 A）。
- **4.4 首章先行**："第一章定下来之后，后面的章节才知道应该往哪个方向靠"，首章暴露页面密度/字号/动效节奏/信息呈现方式。
- **4.5 并行开发**：提示词（逐字）：`/web-video-presentation 验收无问题，继续使用 Agent Teams 并行开发完后续所有章节，最大并行 3 个 Agent`。每个 Agent 输入包四件：自己负责的章节大纲、Skill 规范、主题变量、第一章代码（参考）；"一定要选 Agent 能力非常强的模型"。
- **4.6 全网页逐步点验**：首章验收四问（画面舒服？节奏顺畅？信息太密？AI 味明显？）；"一定要手动把所有步骤都点完"，50+ 步项目中间某步出问题属正常。
- **4.7 音频合成两步**：先抽取口播文本清单人眼校对（口播 Step 与网页 Step 一一对应），再串行逐条合成（规避 MiniMax 速率限制）；断点续跑（已生成文件自动跳过）；每章子目录、文件名=步骤编号。提示词（逐字）：`使用 Chinese (Mandarin)_Gentleman 温润男声合成所有音频`。
- **4.8 三种播放模式 + OBS 出片**：见 [[三种播放模式]]；出片 = 浏览器全屏 + OBS 录屏，而非渲染视频文件。
- **4.9 版本控制归档与流水线复用**：全部资产（原文/口播稿/大纲/代码/音频）入版本控制，"换一篇原始文章，再沿着同一条流水线跑一遍"，见 [[流水线复用模式]]。

**开发模式三档（逐字表格）**：

| 模式 | 说明 |
|------|------|
| A · 默认 · 逐章确认（推荐） | 每章做完都暂停验收 → 下一章 |
| B · 第 1 章后顺序开发 | 第 1 章验收后，第 2~N 章主线程顺序做完，最后统一验收 |
| C · 第 1 章后并行开发 | 第 1 章验收后，用 subagent 并行做第 2~N 章（用户控制并行数） |

## 最终结论

- "真正的问题不是'模型会不会做'，而是怎么把这些能力编排起来，让它稳定地做完。"
- "Skill 就是把复杂的内容生产流程，拆成一个有流程、有状态、有检查点、有自检、有恢复机制的工程系统。"
- "不是让 Agent 自由发挥，而是给 Agent 搭了一条可重复执行的轨道。"
- **（全文最终定义句，逐字）**："这也是 Harness 最核心的价值：把模型能力、工具能力和人的判断，组织成一条稳定可控的生产流程。" 详见 [[Harness核心价值三元组织论]]。
