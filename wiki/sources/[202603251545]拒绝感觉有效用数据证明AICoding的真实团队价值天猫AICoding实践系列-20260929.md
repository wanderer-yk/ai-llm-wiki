# 拒绝“感觉有效”：用数据证明 AI Coding 的真实团队价值【天猫AI Coding实践系列】

## 概述

本文是 [[天猫品牌行业前端团队]]（文末署名作者 [[珈文]]，隶属 [[淘天集团]]）“天猫AI Coding实践系列”的方法论核心篇，2026-03-25 15:45 以原创标记发布于微信公众号 [[大淘宝技术]]（alias: AlibabaMTT，IP 属地浙江）。系列前篇为《知识基座：让AI越用越懂业务的团队经验实践》（[[sources/[202603231539]知识基座让AI越用越懂业务的团队经验实践天猫AICoding实践系列|[202603231539]知识基座让AI越用越懂业务的团队经验实践天猫AICoding实践系列]]）。

## 实践背景与定位声明

- 2025 年 11 月起，某大型电商平台多个业务域启动“后端全栈”试点：零前端基础的后端工程师通过 AI 独立交付中后台前端需求。
- 三层数据形成“发现问题（离线评测）→ 定位原因（链路指标）→ 验证效果（结果指标）”闭环。
- 定位声明：该体系**不是**“AI Coding 标准”，而是业务团队指导自身调优的工具，具体标准需结合业务上下文判断。

## 核心框架：三层度量体系

| 层次 | 评测/采集方式 | 方法要点 | 作用 |
|------|--------------|---------|------|
| 质量指标 | 离线评测 | 垂直化业务用例 + 复杂度矩阵（业务复杂度×组件成熟度）+ 结果分/行为分双评分 | 定位模型能力短板 |
| 链路指标 | 在线埋点 | 上下文“调用→命中→采纳”漏斗 + 四象限分析识别高频低效知识 | 驱动知识库、SPEC、Skills 等优化 |
| 结果指标 | 真实交付 | 需求级 AI 参与覆盖率、代码上线采纳率（Diff 级比对）、Token 成本 | 验证实际价值 |

判定标准：“三层指标相互校验，只有各层都健康，才能证明 AI 实践是真实有效的。”详见 [[三层ai-coding度量体系]]。

## “感觉有效”为什么靠不住（三陷阱）

| 陷阱 | 机理 |
|---|---|
| 幸存者偏差 | 成功案例反复提起，失败尝试无人统计 |
| 归因错误 | 无基线数据，无法区分 AI 贡献与需求本身简单 |
| 个体差异 | 高手拉高均值：平均效率提升 30% 可能意味着 3 个人提升 100%、7 个人几乎没变化 |

团队落地三大关切与三层指标一一对应：效果证明↔结果指标、能力边界↔质量指标、问题诊断↔链路指标。详见 [[感觉有效vs数据证明]]。

## 案例一：调优决策不再靠感觉

模型 A 84.9 vs 模型 B 57.0（60 个真实历史需求），热力图显示差距主要体现在组件文档不完善的场景。换模型、改 Prompt、补知识库等任何调优均可跑评测验证。

## 案例二：哪些知识用了但没用

调用率 43.2%、命中率正常（表层健康），但代码采纳率徘徊在 50% 左右——说明“调用→命中”指标不足以证明知识价值，必须下钻到采纳。经“命中次数 × 采纳率”四象限散点分析识别“高频低效”知识（见 [[命中采纳四象限分析]]）。

## 质量指标：离线评测

### 为什么需要垂直化评测基准

通用基准在中后台前端场景的三大差异：**多解性**（同一需求多种等价实现）、**测试成本高**（交互类需求难以自动化验证）、**过程盲区**（只看结果不看 Agent 是否查阅正确资料）。

| 组成部分 | SWE-bench | 垂直化评测基准 |
|---|---|---|
| 评测数据集 | 2294 个 GitHub Issue（Python 后端） | 真实历史需求（针对特定业务场景） |
| 评测方法 | 测试通过即正确（二元判定） | 复杂度矩阵 + 量化评分（结果分 + 行为分） |
| 评测工具 | 测试执行框架 | LLM as Judge + 代码采纳率计算 |

五步设计框架（原文）：明确评测目标 → 选择核心维度 → 构建数据集 → 设计评分模型 → 建立对比基线。详见 [[垂直化业务评测集]]、[[swe-bench]]。

### 复杂度矩阵

维度一：业务复杂度（Complexity Level）

| 层级 | 代号 | 典型场景 | 特征 |
|------|------|----------|------|
| 标准化 | L1 | CRUD 列表、简单表单（≤15 字段）、详情展示页、简单配置页 | 直接使用组件库，逻辑简单，无复杂状态管理 |
| 有联动 | L2 | 表单联动、多级筛选（省市区/类目树）、复杂表格（合并单元格、行内编辑）、审批流转 | 组件间有依赖关系，需要处理状态联动和数据转换 |
| 复杂交互 | L3 | 拖拽排序、画布类、虚拟滚动、富文本定制、微前端集成 | 超出常规组件库覆盖范围，需要深度定制或架构级改造 |

维度二：组件成熟度（Component Maturity）

| 等级 | 代号 | 判断标准 | 说明 |
|------|------|----------|------|
| 完善 | C1 | 组件存在且文档完善 | 组件在物料库中存在，有完整的 API 文档、使用示例、最佳实践 |
| 部分 | C2 | 组件存在但文档不完善 | 组件存在但缺少使用示例，或文档过时，或缺少特定场景的指导 |
| 缺失 | C3 | 需要自定义组件 | 物料库中无对应组件，需要从零开发或深度改造现有组件 |

九象限三分区：

| 分区 | L×C 组合 | 处置建议 |
|------|----------|----------|
| 绿色（推荐区） | L1-C1、L1-C2、L2-C1 | 预期高成功率，适合 AI 独立完成 |
| 黄色（调试区） | L1-C3、L2-C2、L3-C1 | 需要多轮调试，建议人机协作 |
| 红色（挑战区） | L2-C3、L3-C2、L3-C3 | 超出 AI 有效辅助边界，不推荐 |

机理论证：AI 生码质量高度依赖上下文供给——文档完善时经 MCP 调用获取准确 API 信息，缺失时靠通用知识“猜测”，出错概率显著上升。应用价值：需求分流、能力提升（完善文档将 C2/C3 转化为 C1）、预期管理。能力热力图：绿色推荐区 85+ 分（适合 AI 独立完成）、黄色调试区（多轮调整）、红色挑战区（超出有效辅助边界）。详见 [[复杂度矩阵]]。

### 评分模型

| 视角 | 评判内容 | 权重 |
|------|----------|------|
| 结果分 | 代码是否满足业务需求（refAnswers + testCases） | 75% |
| 行为分 | Agent 是否遵循合理工作流程（知识库调用 + 文档查阅） | 25% |

```
综合得分 = 结果分 × 0.75 + 行为分 × 0.25
```

行为分案例表：

| 用例 | 结果分 | 行为分 | 综合得分 | 说明 |
|------|--------|--------|----------|------|
| eval-001 | 1.0 | 1.0 | 0.94 | 理想情况：代码正确，且查阅了文档 |
| eval-002 | 1.0 | 0.0 | 0.75 | 碰巧正确：代码正确，但没查任何资料 |
| eval-003 | 0.5 | 1.0 | 0.63 | 认真但有误：查了资料，但实现有问题 |

权重经 80/20、70/30、75/25 三配置实验选择，判据为**区分度**（能否区分“碰巧正确”与“稳定正确”）+**一致性**；重稳定场景（金融/医疗）行为分可提至 30-40%，快结果大容错场景可降至 15-20%。行为分核心价值是**预测稳定性**（工作方式健康度），不是惩罚。学术依据：[[openai-2023-lets-verify-step-by-step|Let's Verify Step by Step]]（OpenAI 技术报告，2023-05），详见下文「学术依据」小节。LLM as Judge 逐 refAnswer 输出 0/0.5/1 三档评分。详见 [[结果过程双视角评分模型]]、[[llm-as-judge]]、[[碰巧正确vs稳定正确]]。

可信度保障四机制：人工抽检（LLM 评分与人工复核一致性 > 90%）、多模型交叉验证、版本基线对比、轨迹存档复盘。详见 [[评测可信度保障四机制]]。

### 学术依据：《Let's Verify Step by Step》

**论文本身（独立可验证的公开背景，非引自来源文章）**：[[openai-2023-lets-verify-step-by-step|Let's Verify Step by Step]] 是 [[openai|OpenAI]] 于 2023 年 5 月发表的研究论文（技术报告），arXiv 预印本（arXiv:2305.20050，https://arxiv.org/abs/2305.20050）。该论文系统比较了“过程监督”与“结果监督”两种奖励模型训练方式——其中过程监督（process supervision）指对模型推理的每一步进行反馈——并证明过程奖励模型（PRM）显著优于仅监督最终结果的结果奖励模型（ORM），是过程监督研究的代表性文献。天猫文章引述 Ilya Sutskever 为其合著者之一。

**核心定量证据（转引自来源文章）**：

| 方法 | 得分（MATH 数据集） |
|------|------|
| PRM（Process Reward Model，过程反馈） | 78.2% |
| ORM（Outcome Reward Model，结果反馈） | 72.4% |

即过程反馈训练的模型显著优于结果反馈训练的模型。

**在本 Wiki 中的角色与迁移使用**：

- **引入路径**：本论文经由 [[天猫品牌行业前端团队]] 的本文引入，作为 [[结果过程双视角评分模型]] 中“行为分/过程”维度的学术锚点（对应来源文章 chunk 10、18）。团队援引其核心结论，为“不仅看结果、还看过程”的离线评测设计提供依据。
- **学术背书**：作为“评结果 → 评过程”认知转变与 [[结果过程双视角评分模型|“结果+过程”双视角评分模型]] 的理论依据——主流 Benchmark（SWE-bench/HumanEval/Aider 榜单）几乎只测结果，而企业场景中“正确可能只是碰巧”（见 [[碰巧正确vs稳定正确]]）。
- **概念映射**：过程监督 → [[结果过程双视角评分模型]] 的行为分（权重 25%）；“评结果→评过程”认知转变 → [[碰巧正确vs稳定正确]] 的理论来源。
- **迁移声明**：原文自注该论文聚焦数学推理领域，天猫离线评测中的行为分（知识库 MCP 调用 + 文档查阅）是将“过程监督”思路从数学推理迁移到软件工程的尝试，属边界诚实的方法论借用。
- **与可观测性理念相通**：该迁移亦与过程可观测性理念相通——行为分是 [[agent可观测性六维度]] 中 step/tool 维度在评测侧的实现。

### 调优闭环

```
热力图定位短板 → 分析失败用例 → 针对性调优 → 评测验证效果
```

L2-C2 案例：早期 55 分，失败集中于“表单联动”类需求；经 SPEC 模板增加联动规则表/联动流程图 + Prompt 优化 + 知识库补充后提升至 70 分。离线评测局限：“评测环境不等于生产环境”。详见 [[离线评测调优闭环]]。

## 链路指标：在线埋点

核心问题（原文）：“我们费心准备的上下文（知识库、组件文档、SPEC 规范），在 AI 生成代码的过程中，有没有按预期起到正向作用？”

漏斗逐级诊断映射（完整）：

| 漏斗层级 | 异常信号 | 诊断结论 |
|---------|---------|---------|
| 调用率低 | 调用少 | Prompt 引导问题（Agent 不知道要查资料） |
| 命中率低 | 查不到 | 知识库内容覆盖不足，或者索引质量差 |
| 采纳率低 | 查到了但不用 | 查到了但不是 Agent 需要的，召回精度有问题 |

放弃追踪单条知识采纳的三难题：软内容无显式标注、强制标注影响自然输出、无对照组 A/B 测试；改用会话级关联分析。四象限散点图（使用频率 × 关联采纳率）+ 动态中位数阈值定位“高频低效”条目。

四类上下文效果追踪框架：

| 视角 | 关注问题 |
|---|---|
| SPEC 需求规格 | 需求描述是否清晰 |
| 经验沉淀知识库 | 踩坑经验是否被复用 |
| 物料组件知识库 | 组件用法是否查到 |
| Skills 工作流 | 最佳实践是否被触发 |

要点：SPEC 模板四分类（列表页/表单/多场景/基础），以最终采纳率反推模板质量，基础模板补“数据流转说明”“状态变更规则”两个必填项后采纳率显著提升——**结构化约束越强，AI 输出质量越稳定**。经验沉淀知识库三分类（踩坑记录/编码规范/业务规则），知识质量核心维度为**可操作性**（tsconfig 案例：补 paths 映射规则和示例代码后采纳率显著提升）。零结果查询 Top 20（每周汇总，按频次×业务影响排序）是知识库扩展的直接输入。物料组件知识库经 MCP 提供组件查询/API 文档/使用示例三能力，使用率低需二分诊断（没调用 MCP vs 调用了命中率低），并定期扫描“调用了 MCP 但返回空结果”日志。Skills 当前追踪使用率与采纳率（Skills 会话采纳率明显高于普通会话），触发率/完成率列为下一版本计划。详见 [[四类上下文效果追踪框架]]、[[调用命中采纳转化漏斗]]、[[高频低效知识]]。

运营实践：每周拉取三级漏斗数据，重点关注调用率低与命中率高但采纳率低两类异常。

## 结果指标：真实交付

核心洞察：“接受补全”不等于“代码有用”，追踪终点从 IDE 延伸到代码合并上线（见 [[追踪终点延伸论]]）。

- 关联键：`(repo_project, branch)`（AI 编码平台任务数据 ↔ 内部迭代/需求系统）；数据流程：实时上报 Diff → T+1 发布同步 → 定时任务匹配。详见 [[跨系统数据关联机制]]。

```
需求覆盖率 = 关联 AI 任务的需求数 / 总需求数
```

```
代码采纳率 = AI 生成代码被上线的行数 / AI 生成代码总行数
```

代码采纳率三项计算机制：规范化比对算法（去除注释、合并空白、统一引号和分号风格后逐行比对，纯工程化、毫秒级）、Merge Commit 识别（`repo_commit_id` 通常是最后一次提交，经 GitLab API 向后查找第一个标题包含"Merge commit"的提交）、多次出码合并（同 `(repo_project, branch)` 所有 AI Diff 合并后比对）。多次出码示例：AI 新增 2 行、CR 新增 3 行、被采纳 2 行 → 66.67%（分母口径与公式不一致，见下）。

Token 成本聚合（完整表）：

| 维度 | 计算方式 | 用途 |
|------|----------|------|
| Task | 单次对话 Token 消耗 | 评估单次对话效率 |
| 迭代 | 关联到该迭代的所有 Task Token 总和 | 评估迭代级的 AI 投入 |
| 需求 | 关联到该需求的所有 Task Token 总和 | 评估需求级的 AI 成本 |

聚合采用“允许重复计算”策略（多对多关系下各维度汇总值≠实际总消耗，以业务分析可用性优先）。应用价值：趋势分析、异常识别（结合采纳率识别“高消耗低采纳”模式）、ROI 评估。详见 [[token成本追踪]]、[[代码采纳率]]、[[需求覆盖率]]。

辅助指标双降级：交付效率（单需求平均交付时间，混杂因素多）与代码质量（上线后 bug 率、返工率，滞后指标）均明确不作核心追踪指标；文中“全栈模式下后端工程师完整自测，质量通常优于前后端分离交付”为无数据定性判断。

## 总结与展望

三大认知转变（与三层体系严格对应）：

| 认知转变 | 对应层 |
|---|---|
| 能诊断，比能证明更重要 | 链路指标 |
| 碰巧正确比稳定正确更危险 | 质量指标（行为分） |
| 数据让团队能够对齐认知 | 结果指标（团队共识功能） |

局限性自认：LLM 评分主观、数据集规模有限、行为追踪维度不够丰富。未来方向：自动化用例生成、更丰富的链路指标、开放为可复用的通用框架。收尾主张：“数据不会说谎”——能以数据回答“效果怎么样”，才有持续投入的底气与推广复制的基础。

结语升华（原文金句）：“AI Coding 的本质不是‘买个工具提效’，而是一场知识资产的治理革命”“不是 AI 替代了谁，而是团队的知识终于有了积累和复利的可能”；度量定位：“度量不是为了考核工程师，而是为了赋能”，解放过程可视化是 AI Coding 最大的价值。详见 [[知识资产治理革命]]、[[诊断优先于证明]]。

团队介绍：团队负责消费电子、3C数码、运动、家装、汽车、奢品、服务等多行业项目，自我定位“不局限于‘传统’的前端团队”，在 AI、3D、工程化、中后台等领域持续探索。

## 矛盾与口径疑点

1. **代码采纳率公式与示例分母不一致（永久开放）**：公式分母为“AI 生成代码总行数”（示例 AI 新增 2 行应为 2/2=100%），示例却计算 2/3=66.67%，分母实为 CR 新增总行数。文章收官未澄清，挂入 [[ai工程量化效果声明追踪]]。
2. **eval-001 孤例异常**：1.0/1.0 → 综合 0.94，不符合 75/25 公式（公式在 eval-002/003 上精确成立）。
3. **高频低效知识两处数字口径不重合**：“采纳率 20%~30%”与“关联采纳率 18%→35%”疑为两个口径。
4. **全栈模式质量论无数据支撑（弱矛盾）**：定性判断先行于数据，与“拒绝感觉有效”主题轻度自反。
