## 一、Skill 是什么

Skill 是含 `SKILL.md` 的文件夹（YAML frontmatter + Markdown 正文）。标准目录结构：

```
my-skill/
├── SKILL.md              # 主文件（必须）
├── scripts/              # 可执行脚本（可选）
├── references/           # 详细参考文档（可选，按需加载）
├── resources/            # 模板、清单等资源（可选）
└── examples/             # 示例（可选）
```

**关键机制**：Skill 本质是"知识注入"——不动态生成新工具，只把指令文本注入上下文，LLM 用已有工具（bash、read、edit）执行。加载方式为 LLM 判断需要时调用 `skill` 工具，SKILL.md 全文作为 tool-result 注入对话上下文。与 [[skill提示词注入本质]]、[[agent-skill知识包]]、[[skill三阶段工作原理]] 高度互证。

## 二、Frontmatter

必填字段：

| 字段 | 作用 | 示例 |
|------|------|------|
| `name` | 唯一标识符，小写连字符 | `test-driven-development` |
| `description` | **最关键**——LLM 通过它决定是否加载 | 见下方对比 |

description 好/差对比：

```python
# ✅ 好的 description — 包含触发短语和关键词
description: Deploy applications and websites to Vercel. Use when the user
  requests deployment actions like "deploy my app", "push this live",
  or "create a preview deployment".

# ✅ 好的 description — 定义时序位置
description: Use when implementing any feature or bugfix, before writing
  implementation code

# ❌ 差的 description — 太模糊
description: Helps with deployment stuff
```

description 写法三原则：列举触发短语、定义时序位置、包含产品关键词（与 [[description三大要素]]、[[description触发准确性权衡]]、[[agent欠触发倾向]] 需做字段级交叉核对，见开放问题）。

从 7 个 Skill 中归纳出的 6 种可选扩展字段：

| 字段 | 来源 | 作用 |
|------|------|------|
| `references` | OpenCode cloudflare | 声明最重要的参考文档 |
| `allowed-tools` | Google Labs stitch-loop | 声明需要的工具权限 |
| `type` | Dean Peters discovery-process | 声明 Skill 类型（workflow/component） |
| `best_for` | Dean Peters discovery-process | 最适合的场景列表 |
| `scenarios` | Dean Peters discovery-process | 具体的触发场景示例 |
| `estimated_time` | Dean Peters discovery-process | 预估执行时间 |

## 三、5 种核心设计模式 + 特殊模式

逐一详见各概念页与比较页 [[skill设计模式五加一模式对比]]：

1. **[[skill线性流程模式]]** — 代表 [[vercel-deploy]]（77 行），适用"先做 A，再做 B，最后做 C"的明确步骤操作。
2. **[[skill决策树加按需加载模式]]** — 代表 [[cloudflare-deploy]]（224 行），适用 10+ 分支且每分支大量详细文档的知识域；引出 [[导航型与操作型skill拆分]]。
3. **[[skill循环迭代模式]]** — 代表 [[test-driven-development]]（371 行），适用单次会话内"做→验证→改进"。
4. **[[skill接力棒循环模式]]** — 代表 [[stitch-loop]]（203 行），适用跨 session 持续工作或多 Agent 协作。
5. **[[skill多阶段检查点编排模式]]** — 代表 [[discovery-process]]（502 行），适用跨越多天/多周且有 Go/No-Go 决策点。
6. **特殊模式：[[skill思维框架模式]]** — 代表 [[audit-context-building]]（302 行），控制 LLM"怎么想"而非"做什么"。

选型速查见 [[模式选择决策树]]。

## 四、通用写作技巧

### 4.1 防止 LLM 偷懒的 4 种武器

详见 [[防止llm偷懒4种武器]]：强硬语气（"Delete it. Start over."）/ 借口反驳表（TDD 12 种 vs 审计 6 种）/ 量化阈值 / 负面指令。

### 4.2 教学的 3 种有效方式

详见 [[教学三种有效方式]]：

| 方式 | 原理 | 示例来源 |
|------|------|----------|
| Good/Bad 对比 | `<Good>` vs `<Bad>` 代码示例对比，对比学习效果最好 | TDD |
| 具体命令 | LLM 擅长执行具体指令 | vercel-deploy 每步 bash 命令 |
| 完整示例 | 展示期望的输出格式 | 审计：引用 `FUNCTION_MICRO_ANALYSIS_EXAMPLE.md` |

### 4.3 安全与边界的 3 条原则

详见 [[安全边界三原则]]：

| 原则 | 做法 | 示例来源 |
|------|------|----------|
| 安全默认值 | 默认选择最安全的选项 | vercel-deploy："Always deploy as preview" |
| 权限最小化 | 只在必要时提升权限 | vercel-deploy："Do not escalate the installation check" |
| 人类兜底 | 不确定时交给人 | TDD："ask your human partner" |

### 4.4 知识组织的 3 层架构与 Token 预算

详见 [[skill知识三层架构]] 与 [[skilltoken预算]]：

```bash
第 1 层：Frontmatter（~100 tokens）
  → LLM 扫描所有 Skill 的 description，决定是否加载

第 2 层：SKILL.md 正文（<5K tokens）
  → 核心指令、决策树、流程步骤

第 3 层：references/ 和 resources/（按需加载）
  → 详细文档、示例、清单，LLM 用 read 工具按需读取
```

| 层级 | Token 预算 | 内容 |
|------|-----------|------|
| Frontmatter | ~100 tokens | name + description |
| 主文件 | 2K-5K tokens | 核心指令 |
| 参考文档（单个） | 1K-3K tokens | 按需加载 |
| 总上下文占用 | <10K tokens | 主文件 + 1-2 个参考文档 |

这是 [[skill渐进式披露]] 的量化实例化，与 [[token预算优化输出格式]]、[[skill列表token预算]]、[[分块token预算推导]]、[[渐进式披露替代向量检索]] 互证。

## 五、模式选择决策树

```text
你的 Skill 需要做什么？
├─ 执行一个有明确步骤的操作
│  └─ → 模式 1：线性流程
├─ 在大量选项中帮用户选择正确的方向
│  └─ → 模式 2：决策树 + 按需加载
├─ 在单次会话中反复执行"做→验证→改进"
│  └─ → 模式 3：循环迭代
├─ 跨多个 session 持续推进一个长期项目
│  └─ → 模式 4：接力棒循环
├─ 跨越多天/多周，有阶段划分和 Go/No-Go 决策
│  └─ → 模式 5：多阶段 + 检查点
└─ 需要 LLM 进行深度分析而非快速执行
   └─ → 特殊模式：思维框架
```

## 六、快速上手模板

作者给出两套可直接套用的骨架：**最小可用 Skill（线性模式）**——frontmatter（name+description）→ 一句话核心原则+安全默认值 → Prerequisites → Steps（含 bash 命令）→ Troubleshooting 表；**循环迭代 Skill**——Core Principle 铁律 → Phase/Verify 交替 → Repeat → Rationalizations 表 → Completion Checklist。分别对应模式 1 与模式 3。
