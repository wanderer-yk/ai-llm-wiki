# Qoder Quest 1.0：把执行交给 AI，把选择留给人类

## 概述

本文由后端研发 [[kiritomoe]] 撰写，发表于微信公众号 [[kirito的技术分享]]，系统性地阐述了 [[qoder]] Quest 1.0 的设计理念与实践方法论。文章核心主张为"把执行交给 AI，把选择留给人类"，围绕 [[ai-coding第一性原理]] 的四个维度展开论述，并通过"AI 网关压测项目"实战案例展示了从 Spec-driven 起手到利用 Skill 实现 K8s 环境全自动构建部署的完整闭环。

## 文章结构

### 第一部分：AI Coding 第一性原理

作者提出评估 AI 编码任务的四个维度框架（详见 [[ai-coding第一性原理]]）：

1. **价值** — 这件事是否需要做
2. **优先级** — 这件事有多重要
3. **认知边界** — 利用 AI 突破个人技术栈限制
4. **品味** — 人类基于经验和偏见的方案决策

其中"认知边界突破"强调不应让人类知识储备成为 AI 的上限（如 Java 后端通过 AI 开发前端），而"品味"被定义为人类区别于 AI 的核心差异（详见 [[品味作为人机核心差异]]）。

### 第二部分：Qoder 双模式定位

[[qoder]] 提供两种核心模式：

- **Quest 模式** — 自主执行模式，专为 [[sota模型专属优化|SOTA 模型优化]]，人类扮演架构师角色（关注 Spec、交付、提问）。适合非存量项目（追求交付效率和引入 AI 原生技术栈）。
- **Editor 模式** — 协同辅助模式（Agent/Ask），人类扮演导师角色（提需求、验代码）。适合存量生产项目（追求少量改动和确定性）。

关键设计决策：Quest 模式刻意舍弃文件树导航和单文件代码对比，传达从"阅读代码"转向"阅读意图"的理念（详见 [[代码作为中间产物]]）。

### 第三部分：interview 与 spec 机制

Qoder Quest 的核心动态机制（详见 [[interview机制]] 和 [[动态spec机制]]）：

- **interview** — 在用户意图模糊时主动提问澄清需求
- **spec** — 非死板 SOP，支持手动勾选或模型自动决策触发，动态生成规格文档

作者推荐新项目以 [[spec-driven起手范式]] 起手，产出完整架构方案后再进入执行阶段。

### 第四部分：AI 网关压测项目实战

作者使用 Qoder Quest 从 0 到 1 构建了完整的 [[ai网关压测项目]]，用于对 [[higress]] AI 网关进行性能评估。项目包含施压程序、mock-llm-server、report-server 等组件。

关键实践：
- 以 spec-driven 模式起手产出完整架构
- 迭代中通过描述问题（而非阅读代码）修复 Bug
- 利用 [[skill环境感知]] 机制将 Dockerfile、Helm Chart、云端 K8s 连接配置封装为 Skill，使 AI 直接操作底层集群
- 遇到真实问题（如 O(n²) 拼接超时、PVC 写入超限）时通过 [[自然语言触发心流]] 让 AI 自主排查修复

传统 API 网关压测指标（QPS、RT）不适用于 AI 网关，核心关注 TTFT（首字延迟）、TPOT（单字生成时间）、并发连接数。

### 第五部分：DevOps 重构与开发者角色转变

通过 Skill 机制，[[qoder]] 从编码工具进化为端到端的 DevOps 执行平台（详见 [[devops重构]]）。AI 从助手升级为独立执行者，对话窗口成为直接操作底层集群、读取数据并生成报告的任务中枢。

作者提出开发者角色应从"手工匠人"转变为"工厂设计师"，核心任务从写代码变为[[设计反馈回路]]——设计"AI 写代码→自动构建部署→运行测试→根据结果修正"的自动化流水线。

### 第六部分：认知债务与品味

作者提出 [[认知债务]] 概念：因 AI 代劳而导致人类失去的底层认知能力（如索引优化、死锁排查），其可怕之处在于隐蔽性，直到 AI 失灵时才会暴露。建议偶尔关掉 AI 手写代码以保持对底层的敏感度。

最终将 [[品味作为人机核心差异]] 的本质定义为"选择不做什么"——来源于责任心、踩坑经验和半夜 OnCall 的痛苦记忆，是 AI 无法从海量代码模式中学习到的边界感与审慎。
