## 内容摘要

文章记录阿里系交易领域的问诊 Agent（产品名 [[问诊小助手]]，家族化运营）建设实践。核心主张：研发支持的目标不是“回答问题”，而是**稳定替代工程师完成标准化支持流程**；Agent 必须**可沉淀、可复用、可评估、易迭代**。方法论主线为：[[两类能力形态抽象]] → [[问诊agent四层架构]] → [[小域专精原则]] → [[agent构建演进三阶段]] → [[sop-doc可召回排查文档]] 新范式（执行侧配套 [[手册执行者模式]]，知识侧配套 [[双层召回知识体系]]）→ [[q-score质量评分机制]] 与 [[评分agent坏样本聚焦]] → [[反馈回灌闭环]]。

## 背景痛点

- 内部调研：后端开发人员约 **20% 的时间**用于运维类事务（答疑、排障等）。
- 根因：业务长期演进 + 人员流动 → 知识碎片化/断层；工单系统运行多年未沉淀可复用经验资产；应用架构复杂（一个功能横跨多服务及数十个二方包），排查如“长征”。
- 研发支持隐性成本三来源：重复劳动、上下文切换成本、口径漂移；Agent 化可同时化解人员流动带来的知识断层风险。

| 运营评估层（Ops & Eval） | 问答管理、跟进项跟踪、质量评分、报表监控、反馈闭环。 |

### 订单 ID 排查路径（严格顺序，找到原因可提前终止）

```text
1、查看评价详情：检查扩展字段 pjyl=1 表示已发放
2、检查 ttid：taobao 或淘特 ltao 满足；天猫客户端 tmall 不满足透出条件
3、错误码为 'rateGiftNotGift'：
   使用星环运维日志查询工具（BSP）app: rateplatform
   query: '${orderId} AND (preCheck OR template OR AstoreRenderUtil_getRateGift)'
   并输出完整的关键日志需包含 traceId
   - 如果没有查询到日志：提示未找到关键日志，建议联系值班同学处理，并终止流程
   - 否则严格根据查询到的日志，对照日志说明分析具体原因
   - 如果未查询到有效日志：获取 preCheck=false 的记录，使用 traceId 再次检索
     查询关键字 '${traceId}'，再次进行分析
4、如果上述步骤仍然未确定具体的问题：终止诊断，建议联系值班同学处理
```

传参规范：订单 ID 18 或 19 位、评价 ID 14 位、时间戳 13 位毫秒/10 位秒。

### 质量评估体系关键配置

- Q-score 分制：0–10；有效回答阈值：**Q-score ≥ 7**；人工复核范围：**≤ 6 分样本**。

评分 Agent 核心逻辑（原文）：

```text
1. 输入：历史问答记录 + 当前知识库状态；
2. 处理：结合少量高质量正例与典型负例（few-shot learning），辅以领域规则与扣分项模板；
3. 输出：生成 Q-score 及对应的扣分明细，如"跳步执行"、"引用过时文档"、"未按手册顺序操作"等。
```

反馈回灌闭环管线（原文 ASCII 图）：

```text
线上问答 → 评分 Agent 打分 → 聚焦低分样本（≤6）→ 人工复核 → 根因归因
                              ↓
              更新排查文档 / 补充公共知识 / 优化提示词 → 回灌至训练集
```

### F1 局限的四种失效情形

1. 结论正确但分析过程有瑕疵；
2. 分析过程详尽但建议不完整；
3. 正确识别“无答案”但未解决实际问题；
4. 回答未完全解决问题，但已提供足够线索供工程师快速收口（由 Q-score 容错性承接为中等分）。
