# 打造高效易用的 Agent Skill

百度技术微信公众号 [[百度Geek说]]（GEEK TALK 栏目）发布的原创长文，作者笔名 [[无糖可乐]]，发布于 2026-03-09 18:00（IP 属地上海），全文 8605 字/预计阅读 16 分钟。文章以 Anthropic 的 Agent Skill 体系为中心，系统覆盖"设计原理、编写方法、评测迭代"三部分，是本 Wiki 中首篇将 Skill 从"团队实践封装"（对比 [[生产级skill]]）上升到"通用方法论 + 评测工程"层面的来源。

## 内容结构

- **第 01 章 Skill 是什么，为什么需要它**：Agent 先天缺陷（缺乏私域知识与专属能力）→ 能力扩展演进史（MCP 2024-11 开源 → AGENTS.md 社区约定 → Anthropic 2025-10 推出 Skill → Cursor/Windsurf 跟进）→ 三级渐进式披露 → Skill 的组织与安装（Git 统一管理、Vercel `skills` CLI、社区生态）
- **第 02 章 如何编写一个 Skill**：基本格式（文件夹结构、kebab-case、SKILL.md 大小写敏感、YAML Frontmatter 双必填字段）与三阶段工作原理
- **第 03 章 编写优质的 Skill**：Description 三大要素与触发准确性权衡、Body 两种形态、多层渐进与脚本自动化进阶技巧
- **第 04 章 基于评测迭代**：评测三原则、Description 触发评测（召回率/精确率）、Body 对照实验四步法、五步迭代闭环、双案例（[[Skill-Creator]] 三版演进 + Code-Review Skill SubAgent 架构 20 PR 实测）
- **第 05 章 总结**：四条核心结论 + 本质收尾

## 核心主张

1. Agent 不缺能力，缺的是"知道该怎么做"：大模型没有用户的私域知识和专属能力，即使通过 MCP 获得工具（读 GitHub、查 Sentry、操作 Linear），依然不知道按什么流程、顺序、标准使用工具。
2. Skill 正在统一 Agent 能力扩展的途径：MCP（工具连接）→ AGENTS.md（社区探索）→ Skill（标准化知识包）正在收敛（见 [[agent能力扩展演进]]）。
3. 渐进式披露不仅省 Token，更提升注意力分配效率；自然语言知识表达比硬编码逻辑更灵活、更 Agentic（见 [[skill渐进式披露]]）。
4. Description 决定"什么时候用"，Body 决定"用起来效果如何"（见 [[description三大要素]]、[[skill-body两种形态]]）。
5. Skill 是给概率性系统写的指令，无法靠直觉判断好坏，评测是开发流程不可省略的一环（见 [[skill评测三原则]]）；"拍脑袋觉得差不多了"与"用数据验证确实好了"之间隔着好几轮迭代。
6. 本质收尾：把本来每次都要重新交代的经验、流程和标准，整理一次存下来，之后 Agent 自己就知道该怎么做——省掉重复劳动，换来稳定可预期的输出。通用 Agent 像聪明但不了解你业务的新人，Skill 就是你给他的工作手册。

## 关键结构化数据（逐字保留）

团队 Skill 统一管理的目录组织示例：

```
team-skills/
├── code-review/
│   └── SKILL.md
├── react-state-management/
│   ├── SKILL.md
│   └── references/
├── sprint-planning/
│   ├── SKILL.md
│   └── scripts/
└── .
```

Vercel `skills` CLI 跨平台安装命令：

```bash
# 从 GitHub 安装，自动识别当前环境并放到正确的位置
npx skills add https://github.com/your-team/skills/tree/main/code-review
# 支持 Claude Code、Cursor、Windsurf 等主流 Agent 平台
# 无需关心各平台的路径差异
```

Claude Code 手动安装路径约定：

```bash
# 项目级（只在当前项目生效）
.claude/skills/code-review/SKILL.md
# 全局级（所有项目生效）
~/.claude/skills/code-review/SKILL.md
```

Skill 最小目录结构：

```bash
your-skill-name/
├── SKILL.md          # 必须，入口文件
├── scripts/          # 可选，可执行脚本
├── references/       # 可选，参考文档
└── assets/           # 可选，模板、图标等资源
```

SKILL.md 结构（YAML Frontmatter + Markdown 正文，`name` 与 `description` 为必填字段）：

```markdown
---
name: my-skill-name
description: 做什么。在用户说"XXX"时使用。核心能力包括 A、B、C。
---
# My Skill Name
（正文：Agent 执行指令）
```

Description 正面案例（Figma / Linear）：

```makefile
# 清晰、具体、包含触发短语
description: >
  分析 Figma 设计稿并生成开发交付文档。当用户上传 .fig 文件、
  要求"设计规范"、"组件文档"或"设计转代码交付"时使用。

# 明确的服务边界和触发词
description: >
  管理 Linear 项目工作流，包括迭代规划、任务创建和状态跟踪。
  当用户提到"迭代"、"Linear 任务"、"项目规划"或要求
  "创建工单"时使用。
```

Description 反面案例：

```makefile
# 太模糊，几乎什么都能匹配
description: Helps with projects.
# 缺少触发条件，Agent 不知道什么时候该用
description: Creates sophisticated multi-page documentation systems.
# 过于技术化，没有用户视角的触发词
description: Implements the Project entity model with hierarchical relationships.
```

负向触发说明：

```makefile
description: >
  CSV 文件的高级数据分析，包括统计建模、回归分析、聚类。
  不要用于简单的数据浏览（那个用 data-viz skill）。
```

触发评测集 JSON 示例：

```json
[
  {
    "query": "我们团队要移除 less-loader，把 .less 文件全部转成 PostCSS 方案。项目比较大有 200 多个 LESS 文件，有复杂的 mixin 嵌套，用哪种方式风险更低？",
    "should_trigger": true
  },
  {
    "query": "项目已经在用 PostCSS 了，现在想加 postcss-px-to-viewport 做移动端适配，postcss.config.js 不知道怎么写。",
    "should_trigger": false
  }
]
```

Body 对照实验输出目录结构：

```
eval-workspace/
├── iteration-1/
│   ├── test-case-auth-module/
│   │   ├── with-skill/
│   │   └── baseline/
│   ├── test-case-api-refactor/
│   │   ├── with-skill/
│   │   └── baseline/
│   └── ...
```

触发评测迭代改进决策规则：

| 失败模式 | 调整方向 |
|---|---|
| 漏触发居多 | 补充更多触发关键词和场景描述，把边界推得更宽 |
| 误触发居多 | 增加负向说明（"不要用于…"），收窄适用范围 |
| 两者都有 | Description 定位模糊，重新理清 Skill 核心边界 |

每轮迭代的五步流程（见 [[skill迭代闭环]]）：跑对照实验 → 评分（客观跑脚本/主观人工判断）→ 分析反馈 → 改 Skill → 用完整评测集重跑验证。

## 跨来源关联与张力

- **收敛论 vs 分层论**：本文"Skill 正在统一能力扩展途径（Skill 为终局）"与 [[三大武器库]]（知识库+MCP+Skills 三层并存）及 [[skill-command-mcp三层架构]] 形成对照张力，待综合裁决。
- **欠触发外推 vs 保守回答**：本文"Agent 天生欠触发 → Description 主动外推边界" vs 有赞 [[意图识别保守策略]]"宁可不回答也不答错"——层级不同（工具加载 vs 回答决策），作对照素材。
- **评测方法论共鸣**："评测必不可少/用数据验证"与 [[拒绝感觉有效用数据证明]]（天猫，几乎同构表述）、[[评测agent乐观偏差]]、[[agent评测四要素]]、[[ai工程量化效果声明追踪]] 查询页相互印证。
- **注意力稀缺共识**：渐进式披露的注意力效率论据与 [[上下文工程]]、[[极简agent设计哲学]]、[[渐进式披露替代向量检索]] 趋同。
- **多 Agent 审查同构**：Code-Review SubAgent 架构与 [[四核心子代理角色]]（得物）、[[SubAgent与AgentTeams双模式]]（ConardLi）、[[pre-pr机制]]（美团）同构；Grader Agent 与 [[高阶模型审查低阶模型]]（美团 Judge Model）同构。
