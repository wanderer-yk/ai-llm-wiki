## 前言与问题诊断

前言以「小丫同学凌晨两点第三次删除 AI 生成的订单状态流转代码」切入：产出语法正确、逻辑清晰、带注释，但因缺领域知识完全不可用（[[碰巧正确vs稳定正确]] 的典型症状）。诊断结论：AI「不懂项目、不懂团队、不懂交易领域」，「像一个刚入职的聪明实习生：能写出漂亮高效的代码，但对规矩一无所知」（与天猫 [[code-agent新人类比法]] 跨源同构）。问题本质不是模型不够聪明（作者断言 GPT-4、Qwen、Claude 已足够强大），而是当前 AI 编程工具「无状态无规矩」——每次对话对项目/团队/领域知识从零开始，「就像每天换一个新实习生」。

## 演进的四个阶段（编年）

| 阶段 | 断代 | 编年事件 |
|------|------|----------|
| 一：智能代码补全时代 | 2018–2020 | 2018 Kite 首创深度学习代码补全；2019 TabNine 采用 GPT-2「开创 LLM 辅助编程先河」；2020 微软 IntelliCode 2.0 上下文感知补全。阶段定性：局部优化、高级版自动补全、解决「敲键盘太累」 |
| 二：辅助编程时代 | 2021–2023 | 2021-06 GitHub Copilot 技术预览（基于 OpenAI Codex）；2021-10「正式版」（"AI pair programmer"，断代与公开记载有出入）；2022-11 ChatGPT；2023-03 GPT-4。Copilot 被定性为「分水岭」（注释生成整函数/推断意图/多候选），但也「缺乏对项目整体架构的理解」；2024 超 82% 开发者使用某种 AI 编程助手、Copilot 贡献公司超 40% 营收增长（均为「GitHub 报告」转引，口径未注明） |
| 三：Vibe Coding 时代 | 2025 年初 | 2025-02 Andrej Karpathy（前 OpenAI 联合创始人）提出 Vibe Coding；2025 柯林斯词典年度词汇。定义引文："You just vibe with the AI, describing what you want in natural language, and it generates the code."。三特征：自然语言描述意图/以运行结果而非代码审查验证/迭代对话。企业级局限催生「Prompt 约束式编程」过渡形态（自发在 Prompt 添加编码规范/命名风格/架构要求/异常处理） |
| 四：范式编程时代 | 2025 年至今 | SDD 正式定义：颠覆「代码先行」，将 Spec 置于开发流程核心 |

## SDD 的定义、三理念与权力的反转

- 完整定义：范式编程（SDD）颠覆传统「代码先行」模式，将规范（Spec）置于开发流程的核心；写代码前先将「要做什么、为什么这样做、做到什么程度算完成」沉淀为规范文档，该文档双读者（既给人看、也直接喂给 AI 作为执行依据）；开发者重心「从逐行实现代码，到更高层次的设计与指导」。
- 三核心理念：①规格是唯一真理源（代码、测试、文档全部从规格生成，规格即文档、文档永不过期）；②设计先于实现（先自然语言描述「做什么」，再让 AI 生成「怎么做」）；③可测试性内建（规格中明确定义测试用例，自动生成完整单元测试）。
- 权力的反转（橙色枢纽命题）：不再是文档服务于代码，而是代码服务于规范；结构化、无歧义、可被机器理解的规范取代代码成为唯一「真理之源」，代码降级为「这份真理之源在某个特定技术栈（比如 Java or Python）下的一个自动渲染产物或编译结果」。
- 对 Vibe Coding 的关系是「继承与升华」而非否定（对「代码先行」才是「颠覆」）。

## 三大工程痛点

1. **上下文缺失**：AI 只能看到当前应用的有限内容，不知团队编码规范、历史需求实现方式、已踩之坑——生成的代码可能语法正确但风格格格不入，甚至重复犯已知错误。
2. **知识碎片化**：交易链路核心逻辑、风控规则边界条件、历史故障处理经验零散、私有、难以传递。
3. **重复造轮子**：10 人用 AI 生成 10 段订单状态处理代码，实现各异（switch / diamond / 硬编码），代码库混乱、维护成本指数级上升。

## Trade Spec 的价值定位与核心机制

核心价值一句话（橙色强调）：「通过提案、技术方案、代码生成的全链路规范化，培养适合交易场景的 AI 专家。」

研发链路对比表：

| 环节 | 传统研发 | Spec 平台 |
|------|----------|-----------|
| PRD 分析 | 人工阅读理解 | AI 辅助解析、结构化提取 |
| 任务拆解 | 人工分解 | AI 基于应用/模块自动拆分 |
| 技术方案 | 人工设计 | AI 召回知识库，生成初版方案 |
| 代码实现 | Copilot/Cursor | 基于规范化方案生成 |

等待生成提案/方案的三重收益：知识的显性化（AI 召回的知识点会被记录）、方案的可追溯（每次生成有版本控制）、规范的强制执行（生成过程受领域约束指导）。

正向循环知识体系·四圈模型：

| 圈层 | 阶段 | 机制 |
|------|------|------|
| 第一圈 | 需求开发阶段 | 自动检索知识库，召回历史方案/编码规范/踩坑记录；AI 生成初版技术方案，研发人员补充修正 |
| 第二圈 | 知识沉淀阶段 | 需求完成后研发人员回顾三问（哪些决策关键？哪些问题没遇到过？哪些解法值得复用？），抽象为结构化知识点沉淀进知识库 |
| 第三圈 | 知识库进化阶段 | 新知识点经分类（个人级/项目级/全局级）+ 打标（最佳实践/约束规则/领域知识）后纳入检索范围，下次自动召回 |
| 第四圈 | 方案质量提升阶段 | 反复修改→一次生成到位；易遗漏风险点→主动识别；形成「复利效应」（每一次使用都是对知识库的投资） |

知识管理五维对比表：

| 维度 | 传统方式 | Spec 平台方式 |
|------|----------|---------------|
| 知识载体 | 个人笔记、零散文档 | 结构化知识库 |
| 传递方式 | 人带人、口耳相传 | AI 自动召回 |
| 更新频率 | 滞后、被动 | 随开发流程同步 |
| 可用性 | 需要知道在哪、主动去找 | 需要时自动推送 |
| 人员流动影响 | 知识随人走 | 知识留在组织 |

领域专家的培养：「不是在训练一个通用的代码生成 AI，而是在通过持续的知识沉淀，培养一个懂交易业务的 AI 专家」。AI 是团队的「N+1 号成员」——不会疲惫、不会遗忘、不会离职，但需要「培养」：不是调参数、不是微调模型，而是持续喂给它领域知识、让它在实战中成长（培养优于训练论）。落地场景为新人入职加速（消解「三个月熟悉业务、摸索规范、踩遍前人踩过的坑」），呼应 [[AI领域专家搭档愿景]]。

## 主流 Spec 调研与选型（两张表）

OpenSpec（[[openspec]]）：轻量级、变更驱动的规范管理系统；双文件夹模型（`openspec/specs/` 当前规范 + `openspec/changes/` 变更提案）；每个变更含 proposal.md、tasks.md、design.md（可选）和 delta 规范；完成后归档到 `archive/` 并自动合并到主规范；支持 20+ AI 工具。

SpecKit（[[github-spec-kit]]，文中亦写 Spec-Kit）：完整的规范驱动开发生命周期工具；结构化工作流 7 阶段（文中仅列 5 个阶段名：Constitution → Specify → Plan → Tasks → Implement）；项目宪法 `constitution.md`；模板体系（spec/plan/tasks-template.md）；Git 集成基于分支（如 `001-feature-name`）。

BMAD（[[bmad-method]]）：把软件工程拆成多个专业角色的多 Agent 协作框架（需求分析/架构设计/开发/QA 测试/Reviewer/文档 6 类 Agent）；交付流：需求→规划→设计→编码→测试→文档→部署。

企业级选型对照表（四列：痛点问题｜工具｜适用场景｜适合规模）：

| 痛点问题 | 工具 | 适用场景 | 适合规模 |
|---|---|---|---|
| AI 老忘事、老跑偏 | OpenSpec | 企业级应用，团队协作，复杂重构 | 企业级应用迭代，规范完整全面 |
| 需求不清晰、文档混乱 | SpecKit | 从 0 到 1 构建复杂单体项目 | 初创团队，角色协作，风格一致 |
| 需要完整交付链条、让 AI 像公司一样运作 | BMAD | 完整交付，不仅仅是需求到编码 | 大型项目全流程 |

八维度对比表（最终计分 OpenSpec 7:1 Spec-Kit）：

| 维度 | OpenSpec | Spec-Kit | 推荐场景 |
|------|----------|----------|----------|
| 项目类型 | 现有项目迭代 | 新项目开发 | OpenSpec 适合迭代更新 |
| 变更管理 | Delta 格式，自动合并 | Git 分支，手动合并 | OpenSpec 变更管理更自动化 |
| 规范组织 | 按 capability | 按功能编号 | OpenSpec 更适合模块化项目 |
| 工作流程 | 三阶段（提案→实现→归档） | 七阶段 | OpenSpec 更轻量，Spec-Kit 更完整 |
| 质量保证 | 格式验证 + 一致性检查 | Constitution + Checklist | Spec-Kit 原则执行更严格 |
| 工具集成 | 20+ 工具，统一指令 | 16+ 工具，脚本集成 | OpenSpec 工具支持更广泛 |
| 学习曲线 | 中等（Delta 格式） | 较高（完整生命周期） | OpenSpec 更容易上手 |
| 适用团队 | 中小型团队，快速迭代 | 大型团队，企业级项目 | OpenSpec 更适合敏捷团队 |

选型结论（加粗）：「整体来说 OpenSpec 更适合企业级应用的团队研发，但是可以结合 SpecKit 的部分特性」（混合采用策略）。团队技术方案模版采用 proposal.md/design.md/tasks.md 三文件命名，与 OpenSpec 工件结构一致。注意跨表张力：表 1 SpecKit 适合规模=初创团队 vs 表 2 适用团队=大型团队/企业级项目。

## CodeAgent 选型：双通道

形态论证：Cursor 和 Qoder（[[cursor]]、[[qoder]]）属 L2 IDE 工具，虽有 Agent 模式但**执行环境受限**（行动绑定本地开发环境）；真正的命令行 Agent 是可部署到服务器、CI Runner、Docker 容器中独立执行的**沙箱环境**（L3/L4 成熟度），「生于终端，能力无界」，是实践 SDD、实现 AI 原生工作流的「唯一正确路径」（绝对化断言，与后文「不是银弹」形成口径张力）。

四候选 L3 对比：

| 层级 | 出处 | 候选 | 定性 |
|------|------|------|------|
| L3 | 业界 | SOTA模型（类别统称，后文实锤为 [[claude-sonnet-4-5]]） | 为「自治」而生的工作流引擎，核心 Agentic Autonomy |
| L3 | Google | [[gemini-cli]] | （描述段在原文中缺失） |
| L3 | 阿里对外 | [[qoderquest]] | 为「交付」而生的任务委托引擎，核心 Spec-Driven Autonomy，端到端自主交付 |
| L3 | 公司内 | [[aone-agent]] | 为「协作」而生的多智能体编排引擎，Agent Leader 拆解编排 + 领域 Agent 并行全链路 DevOps |

双通道定论（橙色加粗）：「**用 SOTA模型触及能力边界、用 Aone Agent 守住安全底线**」。理由：SOTA 模型代表行业智能体自治能力天花板（自主规划+多步推理、最繁荣 MCP 生态、`SOTA模型.md` 规则快速验证）；淘系三重硬约束（C3 级代码安全合规、Aone 流水线深度集成、大规模团队答疑支撑）恰对应 [[aone-agent]] 四优势（内部模型可选/安全红线合规/OpenAPI 深度集成/知识库与模板沉淀）。SOTA 通道自建选 Python（Java 因生态薄弱、适配工作量大、交付周期不可控被排除），选型核心原则为「MVP 的交付速度和效果确定性」。

沙箱 MVP 部署（Step1 链路打通 → Step2 可视化调优 → Step3 MVP 实现）：底层选型 [[aonesandbox]]（安全隔离与网络互通的平衡；弹内测试网模式；集团生产网禁止运行沙箱类服务）；通过 [[claude-agent-sdk]] 复用 Anthropic 工程成果。Step1 Demo 代码（正文将 claude 匿名化为「SOTA模型」，代码保留原始标识）：

```python
async def main():
  options = ClaudeAgentOptions(
    system_prompt="You are an expert Python developer",
    permission_mode='bypassPermissions',
    cwd="/Users/sanglonglong/PycharmProjects/pythonProject4/claude",
    env={
      "DISABLE_PROMPT_CACHING": "0",
      "ANTHROPIC_BASE_URL": "https://idealab.alibaba-inc.com/api/code",
      "ANTHROPIC_AUTH_TOKEN": "xxxx",
      "ANTHROPIC_MODEL": "claude_sonnet4_5",
      "ANTHROPIC_SMALL_FAST_MODEL": "claude-haiku-4_5"
    }
  )
  async for message in query(
          prompt="现在几点了",
          options=options
  ):
    print(message)
asyncio.run(main())
```

运行结果（节选）：模型串 `claude-sonnet-4-5-20250929`，2 turns、Bash `date` 工具调用成功、总成本 $0.079、耗时 9.7 秒、cache_read 15097 tokens。内部网关见 [[ideatalk]]。

## 交易领域四特殊性与建设路线

| # | 特殊性 | 依据 | 推论 |
|---|--------|------|------|
| 1 | 合规要求高 | 资金流转，代码变更需符合监管和内部风控 | — |
| 2 | 历史包袱重 | 多年历史、技术栈复杂、约定俗成规则多 | — |
| 3 | 容错空间小 | 一个交易 bug 可能导致资损 | 规范化生成是必要的防线 |
| 4 | 领域知识密集 | 大量业务概念、流程规则、异常处理逻辑 | — |

非银弹定论：面对星环架构理解、多仓库依赖、资金链路叠加优惠等复杂性「使用范式编程依然具有很高的难度和挑战」，但它是「目前我们能找到的、最适合企业级中小需求场景适配的 AI 编程方法论」。

按需求规模分级的三阶段建设路线图：阶段一小需求跑通跑顺（交易领域知识库+高频场景知识点沉淀+Spec 规约建设+完整质量评估反馈体系；每月小需求占一半以上）→ 阶段二中等需求（跨仓库/二方库依赖多/逻辑链路长/多系统协作；重点是构建跨系统领域知识和需求拆解 Agent）→ 阶段三大需求（Multi-Agent 领域分治、SubAgent 负责专属领域；关键决策和质量把关由人主导——AI 生码掌控性局限自认）。

平台六环节已实现链路：需求 PRD 输入 → Proposal 整合 → 技术方案生成 → 生码执行 → 研发评审 → 流水线集成。平台建设六阶段路线的第六阶段为「知识沉淀」——研发过程自动归档，形成加粗强调的「生产-沉淀-复用」知识飞轮（前五阶段文中未逐一列出）。

## 领域知识构建

领域知识双层结构：**知识点**（细粒度、轻量化，一句话形式，用于 Agent 推理中的概念澄清与认知校正）与**知识库**（组织化存储体系，解决通用大模型无法覆盖的专有知识召回）。专有知识四缺口例证：Pandora Boot 启动流程、HSF 服务调用方式、交易域订单状态机流转规则、优惠计算业务约束。

知识底座生成侧选型（wiki 生成方式三方案对比表）：

| 对比维度 | 手工编写文档 | DeepWiki 自动生成 | SOTA模型+subAgent |
|---|---|---|---|
| 时间成本 | 高（需人工编写和维护） | 低（自动化） | 低（自动化） |
| 覆盖范围 | 范围有限 | 全量覆盖 | 可指定覆盖核心入口 |
| 一致性 | 因人而异 | 格式统一 | 格式统一 |
| 可定制性 | 无 | 稍低 | 较高 |
| 跨仓库知识 | 支持 | 不支持 | 支持 |

定论：「选择 SOTA模型+subAgent 来生成仓库 Wiki」，核心理由是「在自动化效率和工程可控性之间取得了更适合研发场景的平衡」；跨仓库聚合通过同目录 clone 多仓库后统一生成。[[deepwiki]] 落选（与天猫系列实证使用 DeepWiki 形成同一集团内的路线分化）。AI 生成文档定位为「起点」，研发人员补充关键细节、逐步迭代完善。

知识库召回侧：MCP chunk 召回基线存在**盲检索**（全貌无感知+query 质量依赖+领域术语缺失→漏召）与**断语义**（切片割裂因果与全局结构→碎片≠知识→误解/幻觉）双问题。解法为双路召回：①KBase 语义检索服务（向量检索找「语义相关」，适合模糊需求如「商家如何表达订单金额及优惠」；但召回依赖内部排序策略、平台侧不可控、含噪音）；②索引导航式召回（先筛文档、再精确搜：看索引摘要判断相关库→下载→关键词搜索定位类名/方法名；每一步可追溯可解释；定位对象为代码入口+技术规范文档）。分工：KBase 解广度（「不知道该看什么」），索引召回解精度（「如何准确找到代码位置」），双防漏召与信息过载。

知识点机制：两大场景——概念澄清（「Aone 变更和代码仓库分支的关系」「Diamond 配置和 Tair 缓存的使用场景区分」等易混淆运维概念）与代码定位（「业务术语→代码位置」映射，如「种草列表」例；无补充时模型大概率找错代码位置导致后续修改失效）。工程迭代：v1 全量注入 Prompt→知识点数量增长后占用上下文窗口、反而幻觉+注意力分散；v2 为每个知识点增加**触发关键词字段**，先匹配命中再召回内容，精准触发+防上下文膨胀。文档噪音弱召回论：完整文档因周边描述性文字过多导致召回不精准，一句话知识点形式让 Agent 快速建立正确认知映射。

## 技术方案模版与两阶段流水线

「一个最通用的 Spec 包含 proposal.md、design.md、tasks.md，通过这三个文件结构化的格式强制将开发思维进行分离，使 AI 和人类能专注于各自的阶段性任务。」

| 文件 | 职责定义 | 核心功能 |
|------|----------|----------|
| proposal.md | 定义变更的目的和范围（Why & What） | 确保人类与 AI 对业务价值达成一致 |
| design.md | 技术设计图：描述系统结构、关键决策以及数据模型或 API 接口的变更 | 技术方案的结构化表达 |
| tasks.md | 详细的实施任务清单 | AI 按清单一步步具体地消化任务并推进实现 |

Spec 规约设计核心 = 制定可落地的技术方案模版 + 工程化手段组装；提案落地需预置仓库目录、接口、wiki 等信息并按需召回。复杂技术方案生成任务拆分为 proposal（提案生成）与 design（设计生成）两个独立任务，采用两阶段流水线架构、形成上下游依赖关系。

## 渐进式披露、Hooks、Skills 与疑问点机制

问题：提案阶段召回信息不断叠加，一次性加载全部提示词导致「提示词膨胀→关注点不集中」，末端遗忘提交代码等要求（模型指令跟随问题）。解法为 Hooks + 渐进式披露：

- **Hooks 事件驱动机制**：AI 生命周期事件（如「生码总结完成」）自动触发预设动作（命令行提交代码），保证关键动作一定被触发（硬保证），与 Sandbox 生码结束后回调服务端同原理。
- **Skills 提示词懒加载**：渐进式披露类比商品页懒加载；核心指令与 assets 资源分离——原方案 300 多行全量堆砌致注意力被格式信息稀释，Skills 方案精简为 50 行核心指令+模板/示例按需加载；知识库召回的文件读取/摘要匹配/MCP 下载三个离散操作封装为语义明确的「知识库召回」技能；一次提案生成中 5 个 Skills 被渐进式披露；带来模板修改不动核心指令、同一 skill 跨 proposal/design 阶段复用、分 skill 单独调试三重收益（与 [[渐进式披露替代向量检索]]、[[mcp工具封装模式]]、[[skill-command-mcp三层架构]] 跨源同构）。
- **疑问点机制**（软澄清）：异步任务提交模式下 Agent 沙箱独立执行无法实时交互，需求不明只能基于假设生成、偏离即整体返工。Agent 在提案阶段主动识别并输出不确定因素（需求改动范围模糊、功能入口代码位置不明等），由问题描述+澄清建议组成、JSON 格式输出；proposal 生成后展示在研发补充页面，用户补充作为增强上下文传递给 Design/Code 阶段，可说明或忽略——把「生成后返工」前置为「生成前对齐」（与 [[blocker-gate]] 硬门控形成软/硬对照）。

## 效果展示与评测体系

Spec 平台 6 个功能区：变更列表区（变更记录，按状态筛选）、PRD 输入区（粘贴 Markdown 或[[钉钉文档]]链接一键导入）、提案展示区（功能拆解/技术要点/疑问列表）、技术方案区（在线编辑和确认）、知识库配置区（召回策略和优先级配置）、执行状态区（生码进度+[[aone]] 变更链接和 CR 评审入口）。

三维度评测体系：质量、效率、使用度 + 可衡量/可归因/可优化三性 + 标准化数据收集模板（与天猫 [[三层ai-coding度量体系]]、有赞 [[agent评测四要素]] 跨源对位）。

生成质量评测：方案/代码两维度，F1-score 为核心指标。**当前基线（2026年1月）：F1-方案 94.44%｜F1-代码 62.66%**。git 行级保留率计算脚本（逐字保留）：

```python
#!/usr/bin/env python3
import subprocess
import sys
import re
import os
print("当前目录:", os.getcwd())
print("Git 根目录:", subprocess.check_output(["git", "rev-parse", "--show-toplevel"], text=True).strip())

FIRST_COMMIT = "848a9aca3a884d0968ad064f1f620aebe2cb36d2"      # AI 生成的 commit
FINAL_COMMIT = "247c73cd8fb179cbc7f0451a6ad17758fefc4076"      # 研发最后一次 commit

def run(cmd):
    result = subprocess.run(cmd, shell=True, capture_output=True)
    # 只有当错误信息包含 "not a git repository" 时，才认为不在 Git 仓库
    if result.returncode != 0:
        stderr = result.stderr.decode('utf-8', errors='ignore')
        if "not a git repository" in stderr:
            print("❌ 当前目录不是 Git 仓库，请在 rp-client 目录下运行")
            sys.exit(1)
        else:
            # 其他错误（如 commit 不存在）正常返回，由上层处理
            return result.stdout.decode('utf-8', errors='ignore')
    return result.stdout.decode('utf-8', errors='ignore')

def is_meaningful(line):
    s = line.strip()
    if not s or s.startswith(('#', '//', '/*', '*', '"""', "'''", '--')):
        return False
    if s in {'{', '}', '(', ')', ';', ','}:
        return False
    if any(s.lower().startswith(k) for k in ['import ', 'from ', 'package ']):
        return False
    return any(c.isalpha() for c in s)

def get_parent(commit):
    p = run(f"git log --pretty=%P -n 1 {commit}").strip()
    return p.split()[0] if p else None

def get_added_lines(a, b):
    diff = run(f"git diff --no-color {a} {b}")
    lines = set()
    file = None
    for line in diff.splitlines():
        if line.startswith('diff --git'):
            file = line.split()[-1][2:]
        elif line.startswith('+') and not line.startswith('+++'):
            content = line[1:]
            if file and file.endswith(('.py', '.js', '.java', '.go', '.ts')) and is_meaningful(content):
                lines.add(re.sub(r'\s+', '', content.strip()).lower())
    return lines

# === 计算 ===
BASE = get_parent(FIRST_COMMIT)
if not BASE:
    print("❌ FIRST_COMMIT 必须有父 commit")
    sys.exit(1)

run(f"git checkout {FINAL_COMMIT}")

ai_lines = get_added_lines(BASE, FIRST_COMMIT)
final_lines = get_added_lines(BASE, FINAL_COMMIT)
retained = ai_lines & final_lines

precision = len(retained) / len(final_lines) if final_lines else 0   # 有效率
recall = len(retained) / len(ai_lines) if ai_lines else 0            # 保留率

# F1-score
if precision + recall == 0:
    f1 = 0
else:
    f1 = 2 * (precision * recall) / (precision + recall)

print("\n" + "="*50)
print("AI 采纳核心指标（含 F1-score）")
print("="*50)
print(f"有效率 (Precision) : {precision:.2%} → 最终成果中来自 AI 的比例")
print(f"保留率 (Recall)    : {recall:.2%} → AI 写的被保留的比例")
print(f"F1-score          : {f1:.2%} → 综合效能（调和平均）")
print("="*50)
```

研发效率评测表与基线（40% 声明的正式溯源）：

| 指标 | 定义 | 目标值 |
|------|------|--------|
| 分阶段耗时 | 提案、技术方案、生码耗时 | 提案 ≤ 8 分钟；方案 ≤ 3 分钟；生码 ≤ 10 分钟 |
| 端到端生成时长 | 从提交请求到返回可用结果的总耗时 | ≤ 3h |
| 研发效率提升比 | (传统耗时 - 使用平台耗时) / 传统耗时 × 100% | ≥ 50% |

当前基线（2026年1月）：提案 8 分钟｜方案 4 分钟｜生码 15 分钟｜端到端生成时长 30 分钟｜研发效率提升比 40%（提案压线达标，方案/生码/提升比三项未达自设目标；端到端大幅达标）。

平台易用度评测表与基线：覆盖领域数（目标「交易后链路全覆盖」，基线 2 个）、周活跃用户数（持续增长，基线 8 人）、人均使用频次（≥3 次，基线 2 次）、用户满意度「NPS」（5 分制定期问卷，目标 ≥4，基线 4.5——实为 CSAT 式口径而非标准 NPS）。

案例级 F1：F1-doc 手算 TP=4/FN=0/FP=1 → 88.9%；F1-code 执行脚本得 47.13%（归因三推测：细节影响/PRD 不清晰/知识库不完善）。评分体系优化四项规划：①行级 diff 局限自认（衡量字符级一致性而非语义正确性，等价重构/变量重命名/顺序调整都会拉低得分）；②语义级评测（AST 提取函数签名、调用关系、控制流，计算结构相似度）；③意图对齐评测（PRD 功能点为锚点，大模型判定是否实现相同意图，输出功能覆盖率报告——LLM-as-judge 变体）；④CI 自动化评测流水线（埋点识别 trade spec 生成的 commit，CR 合并自动触发，结果回写形成任务级评测档案）+ 评测-归因-优化闭环（低分 case 归因为知识库缺失/PRD 模糊/模型理解偏差，反哺知识库与 prompt 调优）。
