## 第一部分（本篇）：我们团队做了什么

### 背景：后端向前，前端向后

原文逐字："为了顺应 AI 时代的潮流，我们团队开始了**后端向前，前端向后**的全栈化转型运动。"转型分工：小二工作台与研发工具的开发交由后端（"交付分割线下面的部分，即前面所提到的需求驱动型"），前端承担 C 端 solution 的编写；两个方向均开展 AI 生码探索。详见 [[后端向前前端向后]]。

| 最为严苛 | C 端频道 | 0 容忍 | 明显则 0 容忍 | 高 | 高 |

### AI 生码总思路

业务团队在 AI 基建快速迭代下的重点是**沉淀自己团队的工作流与 AI 资产**——颠覆性新产品出现时可快速接入，且"这部分是其他 AI 工具无法代劳，只能由我们自己进行建设与沉淀的"。核心思想为"**通过最大化复用来提高整体效能**"（代码、知识、工作流、工具的复用），全文围绕此主线展开。详见 [[业务团队AI资产沉淀论]]、[[最大化复用]]。

### 4.1 小二端——AI 主导的对话生码

场景三特征：无视觉还原度要求、页面间独立性强/项目耦合度低、实现形式自由——因此适合 AI 编码完成全部需求，后端同学**基本不介入实际代码**。三阶段演进（详见 [[小二端AI主导对话生码]]、[[分阶段生码辅助演进]]）：

- **初期——统一生成方案**：面向"前端练习生"（转型后端同学），目标为风格一致代码 + 贴近小二端视觉规范 + 一定 AI 迭代成功率；手段为小二端开发培训、基础代码实现规范（页面间完全解耦 + 代码约束）、高频页面代码模版。
- **中期——辅助补齐前端经验短板**：针对"需求描述不准确"（术语无概念→频繁返工）与"垂类场景/复杂问题没有经验"（被 AI 临时方案带跑、踩坑死循环）两类高频问题，对策为后台新增「AI案例实践中心」（B 端常见页面标准化 prompt 模版）、MCP 速查工具「天猫新品业务编码助手」（对话获取模版→输入需求→输出标准化页面 PRD 供 AI 生成）、基于 Gemini 3.0 多模态能力特调的图片转结构化提示词工具（"相较于直接传图给编程工具，转换后的结构化描述词有更好的页面还原效果"，未量化）、以及"生码沉淀"机制（从 AI 省下的时间中划出一部分记录实现过程与踩坑心得，案例分新增型/更新型需求）。
- **后期——需要更简单、无感、且一致的方案**：体验反馈驱动（大部分人倾向基础 Chat 对话模式，"不想跳出编辑器进行额外的操作（甚至不想配mcp）"；业务复杂、仓库多，文档与规范改动无法及时同步），对策为轻量级团队知识库（"其实更多用在C端开发"）：类 Skill 形式封装开发规范与代码模版，git 仓库管理 + npm 包作为资源承载与版本管理工具，文件链接实现多级文档管理与索引、"渐进式披露，不会过度占用 token"；AI 通过 curl 读取 npm 包下 CDN 资源获取知识，不依赖具体编码工具，接入只需配置在编辑器 Rules；还可借用 CodeWiki 进行知识库问答。最终形成统一知识源四特征——"及时更新、不依赖编码工具、支持问答、使用无感"，完成团队基础开发方案的统一收口。

**未来展望两难题**（自陈未解）：①精细化微调无法达到效果——纯 AI 对话场景难以完成精细化页面细节操作；②开放式场景如何保证尽量统一——未枚举/无法枚举页面的产出随使用者与编码工具"天差地别"（"有时候甚至可以通过页面风格判断是谁，用什么工具写的页面"）。详见 [[精细化微调困境]]、[[开放式场景一致性难题]]。

### 4.2 C端——全栈开发模式下的 AI 辅助

三大建设方向：①质量验收标准高 + 隐含逻辑多，无法全 AI 完成；②链路长、仓库多，需有效串联；③高频高耗时节点分析优化。

**主要 Action（五项，原文清单）**：
1. 代码结构与公共组件的设计（提高生码效率与代码可控度）；
2. 多类高频开发流程的标准化 workflow 沉淀；
3. 基础团队知识库（统一读取方案 + 快速知识查询）；
4. 让 AI 基于知识库内容产出技术方案并人工审核（"后期考虑提供专用的技术方案 Agent，并进行技术方案的打分评测"）；
5. 开发流程中的工具辅助（走查辅助、接口查询、页面检查MCP）。

**未来方向三轴**：①完善知识库的生成与自动更新方案，"弱化人工参与度，提高资产沉淀效率"；②"建设更加 AI 友好的代码架构"，提高整体生码效果；③"进一步提高整条链路的 AI 串联度，完成整体提效"（开发流程的串联 + 现有工具的串联），配 svg 图示"理想化的C端纯 AI Coding 流程"。

## 第二部分（本篇）：活用 AI，掌握编码小技巧

### 5.1 还能实现什么功能

- **UI 布局重构两步法**：先让 AI 解释旧布局并做区块划分标记，再描述迁移方向并新增功能；配图题注"让 AI 理解布局，让 AI 瞎子也能看得见"。详见 [[UI布局重构两步法]]。
- **复杂 prompt 构建**（neko 智能参数调试面板案例，六项诉求逐字保留）：
  1. 理解 http get/post 参数/正文字段格式；
  2. 分析字段业务/技术语义并精准划分；
  3. 基于字段重构表单面板（原生 js、无前端构建过程）；
  4. 表单以 iframe 加载并与外部参数/正文保持同步；
  5. 基于 postMessage 实现内外双向实时联动；
  6. "同步过程是非常频繁的，需要保持双方原本格式。"
  核心方法："场景功能就很复杂，比较难描述清楚其具体的 prompt。所以可以让 AI 理解你的朴素诉求，并根据诉求去生成 prompt。"（图注："让 AI 去操作 AI，开发者只思考需求是什么"）详见 [[复杂prompt构建]]、[[AI生成prompt]]。
- **复杂的数据转换**：两个要点——"给出原始数据格式内容 与 目标数据格式。格式需要尽量全，覆盖所有的字段"；"后续需要对转换过程做端到端的大量边缘 case 测试"。案例为 IDD→Neko 协议转换（"IDD 到 Neko 中间有极大的协议差别"，"给 AI 最为完整例子让其解决协议转换，人只负责验收"）。详见 [[复杂数据转换方法]]。

### 5.2 还能怎么辅助编程

- **AI 驱动 + 人工决策的多方案选优**（四步）：对不熟悉的项目先让 AI 给出多种供选择方案 → 根据优劣和自身需求选出倾向方案 → 确认方案工程层面对当前项目的改动大小 → 开始实施。详见 [[AI驱动人工决策多方案选优]]、[[人提方案AI执行半自动方案]]。
- **帮助写各种文档**：让 AI 根据功能代码反推使用文档。示例 prompt（逐字）："针对之前 welcome 组件中对导入集合功能的重构，写一份功能文档，比如如何导入 IDD 集合，如何导入 CODE 仓库，如何导入 postman 第等的集合。"（图注："从代码反推出的功能是比较完整的"）详见 [[代码反推文档]]。
- **总结页面信息**：利用编辑器的 MCP 或内置工具访问并理解页面信息，实现此前难以想象的复杂任务。示例 prompt（逐字）：`https://github.com/AlibabaCloudDocs/aliyun_acp_learning/blob/main/大模型ACP认证教程/p2_构造大模型问答系统/2_6_构建Agent完成复杂任务.ipynb 请你根据这个页面的信息，总结出一份摘要，并给出 js 代码实现的几个文中的代码例子。` 案例还展示"和中英翻译一样，AI 可以快速实现代码语言之间的『翻译』"。详见 [[总结页面信息]]。
- **用案例代替思考**（目录外新增条目）：基于提示词工程中的 Few-Shot，"完全案例替代需求描述"。Few-Shot 定义："提示词中包含多个示例。"翻译示例："请模仿以下示例将中文翻译成英文。示例1：'你好' -> 'Hello'。示例2：'谢谢' -> 'Thank you'。示例3：'再见' -> 'Goodbye'。请翻译：'今天天气真好。'"工号权限实战案例（逐字）："你需要改下权限判断的逻辑。我发现有些同学工号是 wb123432，存的实际是 WB123432，就是有大小写区别。有些同学工号是 014515，但是存着的工号是 14515，有首尾空号的区别。你需要对这些异常情况都处理好，确保他们都能有正常的权限。"详见 [[用案例代替思考]]、[[few-shot示例库]]。

### 5.3 还能怎么提升其准确度

- **严厉语气**：引用研究称"非常严厉的语气在某些任务上的准确率可以超过非常礼貌约 4%"（`https://arxiv.org/pdf/2510.04950`，外部引用，论文题目/作者未给出）；团队实证为"大盘新品时令分析里，严厉语气可明显提升输出格式准确度"（定性描述）。建议"如果怎么改都没有效果的提升，不妨试试说些狠话"。狠话示例（逐字）："你要不好好干，我就把你电源拔了"；"你要不好好干，世界上就会有一只可爱的小猫咪被杀死"。详见 [[严厉语气]]。
- **合理质疑**（兑现最后一个目录项）：模型常以"完成用户需求"为第一优先级，忽视项目架构稳定性与维护成本，修复 bug 场景尤甚；案例为 AI 修复依赖缺失时强行将 Node 环境功能包加载进浏览器，而项目已有 Node 与浏览器通信的成熟机制。两条质疑模板（逐字）：详见 [[合理质疑]]。

```
"请尊重项目原本的架构，把破坏性的改动归位，按照更合理的方式进行修复"
"我认为你的实现有待商榷，你重新思考下这个问题并给我更好的解决方案"
```
