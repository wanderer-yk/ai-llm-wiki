# 从0到1：有赞AI客服的实践路径与落地思考

**作者**：有赞共享技术
**发布平台**：微信公众号"有赞coder"
**发布时间**：2026-01-13
**IP 属地**：浙江
**标记**：原创

## 摘要

有赞共享技术团队撰写的 AI 客服系统从 0 到 1 建设实践文章，从研发视角系统回顾了平台选型、模型选择、工作流设计、上下文工程、知识工程、评测反馈和团队协作七大核心环节。文章覆盖电商 SaaS 场景下智能客服的完整落地链路。

## 核心内容

### 一、前言与背景

有赞作为电商 SaaS 平台，自 2025 年初投入 AI 客服领域，商家对客服系统存在较大需求。

### 二、平台选型：智能体开发平台 vs 工程化代码

从内部黑客马拉松出发，先用 [[dify]] 快速验证 PMF（产品市场匹配），后发现生产环境面临三大瓶颈：
- **性能瓶颈**：简单 Python 代码节点执行耗时 40-100ms
- **检索实时性不足**：知识检索组件无法满足客服实时响应要求
- **运维规范缺失**：低代码平台缺乏企业级运维支撑

提出[[三阶段平台演进路线]]：验证期（Dify 快速 MVP）→成长期（Dify+工程化混合）→成熟期（全工程化），并使用 [[spring-ai-alibaba-studio]] 将 Dify 流程导出为标准 Spring AI 工程代码。

### 三、模型选择

核心观点：**选对模型比优化 Prompt 更关键**。使用 [[langfuse]] 作为模型评测工具，从人工验证过渡到系统化评测。后期模型更换成本高且不确定性强。早期使用 [[gpt-4-1]] 进行意图识别，后为降成本切换为 [[qwen]]。

### 四、Workflow 优先于 Agent

提出[[workflow优先于agent]]的架构决策：客服场景追求确定性和可控结果，优先选择确定性 Workflow 而非自主 Agent。同时明确提出未来将从 Workflow 向更具自主性的 Agent 能力演进的渐进路线。

### 五、工作流三版迭代

- **v1**：单节点全能（意图识别+问题改写+负面情绪识别），随业务增长暴露问题
- **v2**：拆分节点降成本（GPT-4.1 换 Qwen），自行维护[[全局历史变量替代平台记忆]]机制，解决 Qwen 对 Dify 记忆机制敏感导致的幻觉问题
- **v3**：[[售前售后流程分离]]提升承接率，基于回复风格差异（售前主动 vs 售后严谨）和知识差异

### 六、上下文工程

提出上下文工程三阶段框架：
1. **信息获取**：多模态提取+实时动态注入+历史 QA 隐性知识
2. **筛选提纯**：入口场景定向检索+语义相关性过滤+权重加权
3. **信息组装**：从文本拼接升级为[[结构化上下文组装]]（XML 标签分层+Prompt 定义优先级），显著减少幻觉

### 七、知识工程三维度

1. **商品知识**：[[多模态知识预学]]（模型多模态能力而非 OCR）+实时查询，提出[[静态动态双路径知识注入]]和[[知识优先级机制]]
2. **历史对话知识**：高频 QA 提取+去重+独立高精度召回，面临[[历史对话知识提取三难]]（调试难/提取难/质量判断难）
3. **文档知识**：[[文档分块参数调优]]，chunk_size=600, chunk_overlap=100

### 八、评测与反馈优化

提出[[agent评测四要素]]框架（评测对象/数据集/指标/反馈闭环），强调 Agent 评测与传统软件测试的本质差异——不确定性、开放性、场景多样性使得无法完全沿用传统测试方法。

### 九、协作与项目管理

分析[[ai项目协作三大特征]]（职责边界模糊/责任分散/认知不统一），提出[[ai原生协作流程]]——Prompt 评审机制+评估指标对齐+产研共同迭代 Prompt/逻辑/数据+文档化决策过程。协作角色分工：产品+研发把控指标和效果反馈，测试人员投入评测基础建设和用例集。

### 十、总结与展望

贯穿全文的核心原则为"**宁可不答，不能答错**"。三大未来方向：智能协同、多维知识挖掘、AI 原生协作体系。
