# Workflow 与 Agent 范式之争如何按场景裁决

**问题**：[[沈询]] 的"[[编程与工作流同源替代论]] + Agent 新范式"主张，与有赞 AI 客服的 [[workflow优先于agent]] 确定性优先策略，如何在场景层面调和？Agent "业务自闭环、分钟级修改"在生产环境是否有实证？

## 双方立场

- **[[workflow优先于agent]]**（有赞共享技术，2026-01）：客服场景优先选择确定性 Workflow 追求结果可控，"宁可让 AI 不回答，也不能让它答错"，未来向 Agent 渐进演进
- **[[编程与工作流同源替代论]]**（沈询，2026-02）：Workflow 与编程同源、本质都是程序控制的流程流转，代码方案已凭复用性和扩展性胜出；Agent 决策权下放，是"更有机会的新范式"和"下一代用户交互新范式"

## 初步调和线索

1. **场景差异**：准确性敏感的客服系统 vs 追求体验差异化的通用创新产品——并非严格矛盾
2. **沈询自己的边界**（[[ai增强与agent体验二分选型]]）：既有系统增强用"代码 + toolcall"，准确性有保障——与有赞确定性优先立场部分收敛
3. **内部张力**：沈询全文高调主张 Agent 新范式，但并未主张 Agent 全面替代；宣传语气与实用建议之间存在落差

## 待验证

- Agent 业务自闭环/"从发现问题到解决问题只需要几分钟"是否有生产实证（目前仅天气推荐穿衣玩具案例与自报声明，见 [[业务自闭环]]、[[ai工程量化效果声明追踪]]）
- Lynxe "解决 80% 以上个人问题"的任务范围与度量方式
- 有赞"未来向 Agent 演进"的具体路径与沈询"Agent 新范式"主张是否收敛

## 第三方证据：阿里商旅 AliGo 的同源双证（2026-02）

阿里商旅 AliGo（[[涂南]]，2026-02）提供了本之争中少见的**同一团队双向行为**证据：

- **同向有赞**：规则引擎**快车道**分流确定性请求（常见城市/标准规则走确定性路径），与 [[workflow优先于agent]] 的确定性优先同向
- **反向沈询**：整体架构从 workflow+单智能体**迁向**代码化多智能体（AgentScope），并以"线性工作流程说明书 Prompt"为反模式批评静态流程描述（见 [[动态prompt生成机制]]）
- 两者的调和恰是"**按请求类型逐条裁决、分层混合**"：确定性子任务走规则快车道，不确定性子任务走多智能体动态决策——支持本页初步调和线索第 1 条（场景差异）并细化到请求粒度
