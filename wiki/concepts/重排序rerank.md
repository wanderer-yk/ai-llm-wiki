# 重排序（ReRank）

重排序（ReRank）是检索流水线中「召回粗筛＋重排精选」两阶段的第二阶段：检索的优点是可以在海量知识中快速找到与 query 相关的内容块 docs，但返回的 docs 可能部分关联度不大，需要 ReRank 对检索返回的 docs 做关联度排序，选取最相关的 top k 个 doc 做后续上下文补充。

## 原理：为什么召回不够准

「在文档的索引阶段，文档的向量是预先计算并存好的，与 Query 无关，这导致它只能表达文档的平均含义。所以，召回的文档仅能说明与 Query 相关，但不能保证精确匹配。」此外，embedding 难以同时平衡多条件逻辑——「推荐一款 2000 元以下、续航好的华为手机」三条件查询中，「华为手机」「2000 元以下」语义权重大，易搜回只满足单一条件的文档。解法是 [[cross-encoder|交叉编码器]]（如 gte-rerank）。

## 三大优点

1. **精度飞跃**：解决「检索回来的资料看着挺像，但就是答非所问」的最佳方案。
2. **多源融合**：向量搜索与关键词搜索（BM25）的排序标准不一，重排序作为统一裁判打出公平分数——混合检索思想的入口。
3. **降低大模型负担**：「给大模型的内容更少、更准，不仅节省 Token 成本，还能显著提高生成答案的质量。同时能够解决‘中间丢失’现象。」（与 [[中间丢失]] 形成症-解配对）

## 四大缺点

1. 增加延时；
2. 有算力开销；
3. 重排序模型有上下文长度限制；
4. 对查询扩写不友好——「如果系统使用了‘多查询（Multi-Query）’技术，生成了 5 个变体问题。那么重排序的计算量会直接乘以 5 倍。」（与 [[多查询生成]] 的组合成本权衡）

## 关联

本概念是 [[rag技术瓶颈]] 中「召回仅说明相关不保证精确匹配」问题的标准解法；缺点清单（延时/算力/长度限制/Multi-Query×5）在源文中无配套缓解方案（top k 控制、异步、蒸馏等均为待研究项）。
