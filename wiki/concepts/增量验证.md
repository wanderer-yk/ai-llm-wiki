# 增量验证

**增量验证**是 [[三阶段对话模型]] 阶段三（迭代反馈）的核心：分模块实现、逐个验证，避免一次性生成大量代码后才发现方向错误、从头再来。

## 三个实践要点

1. **分模块逐个验证**：每个模块独立实现、独立确认
2. **关键节点主动暂停**：表结构确认先行、单测先行、第三方 API 调用前确认
3. **持续同步技术方案**：实现进度实时回写技术方案文档

## 模块状态生命周期

`implemented → reviewed → verified`（三段式）。注意来源内部存在命名不一致 nuance：另一处状态标记为 `[未开始]/[设计中]/[已实现]/[已审查]` 四态，协作流程中又称「标记该模块为『已完成』」，三处粒度不统一，疑为行文非严格对齐。

## 交互范本（节选自来源对话示例）

```
开发者: "实现新商户成长任务分配功能"
AI: "我将分三步实现: 1.先设计数据库表结构... 请确认表结构是否符合需求?"
开发者: "字段没问题,但索引需要加上(operator_id, status)"
AI: "已更新索引设计,现在开始实现Service层核心逻辑... 请验证业务逻辑是否正确?"
```

## 跨来源验证门控共识

- 爱奇艺 [[blocker-gate]]：未完成需求对齐时强制阻断
- vivo [[验证门禁化]]：未通过验证/审批/沙盘的硬性阻断规则
- 本文「关键节点主动暂停 + 单测先行」是**对话流程内**的同类门禁——三方独立提出「未满足条件则不前进」
- 与 [[human-in-the-loop]] 机制同源：人守住关键裁决点
