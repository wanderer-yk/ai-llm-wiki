# AI生码五维归因框架（导致问题的主要因素与解法）

AI生码五维归因框架是天猫新品营销技术团队对 [[AI生码四大痛点]] 的归因与解法体系，源文章节名为「导致问题的主要因素与解法」，沿项目知识、用户输入、任务复杂度、自检机制、模型能力五个维度组织，每项因素配"问题→解法"结构。

## 因素 1：项目/需求隐含信息过多（AI 不知道）

淘内私有项目代码含专属业务逻辑 + 来自四面八方的 SDK 工具库代码，项目知识无处获取——"即使是 Cluade 40 来了也无济于事"（原文如此，疑指 Claude 4.0）：模型能力无法弥补知识缺失。解法：①使用有明确声明的 NPM 包，或接入 artifact7 等辅助文档生成工具；②提供可访问的外部知识库（MCP 工具/项目知识库/需求文档）。

## 因素 2：用户输入不精准，必要信息不足（没给 AI 说）

理论根基（需求模糊填充归因）："代码开发就是从模糊的需求转向无歧义的代码，模糊部分在实现中必然会被补充，实现不合预期的一大原因就是模糊部分没有明确说明。"解法四途径：常见情况 prompt 模版；工具辅助输入扩写 + 模糊部分标记阐明；引入 Spec Coding 方案以详细文档作为 AI 输入；对高频场景做出约定覆盖模糊（如维护持续更新的 AGENT.md）。另有同级解法"意图识别"：AI 基于项目上下文自动推测模糊部分，路径为接入 MCP 扩大感知力 + 代码索引/项目文档/CodeWiki 辅助快速仿写推测（注意与马上消费客服链路的 [[意图规划]] 同名异义）。收束性实践结论：文档"大而全 vs 小而精"权衡——小文档起步 + 按 AI 产出偏离迭代补充，前提是保持工具和模型尽可能不变（多数偏差是重复出现的常见问题）。

## 因素 3：任务复杂度高

"成功率随复杂度提升在某个节点开始骤降。"两个降低角度：**降低任务复杂度**——识别重复的工作流与代码做封装复用；复杂任务拆分（不易测试的大型任务→多个可验收的小型黑盒）；固定实现思路/细节、统一思维模型，通过约定减少思维/选型负担。**降低工程复杂度（文件量、耦合度）**——优秀工程结构设计实现代码/模块/文件天然解耦（"很多生码问题归根到底都是基础代码工程化问题，具有优秀工程结构的仓库天然就有较高的 AI 生成成功率"）；通过代码索引/项目文档/CodeWiki 等辅助手段提高 AI 检索效率，减少因检索困难而新增的无用上下文。

## 因素 4：缺少自检环节

诊断："现在的常规生码流程，只会进行基础的代码规范与语法检测，并没有完整的 Review & Test 的流程。此时的 AI 只是完成了代码生成，并不一定完成了任务，也不一定满足实际的代码质量要求。"解法：代码质量自检（本地自检流程 + Code 平台 AI CR 助手发布前预检，可自定义 CR 规则）+ 功能自检（前端接入 MCP 感知页面测试；后端单测验证；无法测试的大型任务拆分为可验收黑盒——前端视图分离 + 逻辑 hooks 单元测试）。详见 [[自检机制]]。

## 因素 5：模型/Agent 的差异与能力限制

"要将 AI 生码运用在工程中，不仅需要面对模型的短板，还需要对抗模型的随机性。"短板清单（4 条）：

1. **上下文窗口有限**——留存过程文档实现上下文复用（代码上下文：仓库/接口信息；项目上下文：PRD/功能文档）；提供更精准的上下文；用户 Rule 监控注意力状态（"让 AI 每次对话结束都要用谢谢结尾，如果没有则说明上下文窗口已经爆了"）。
2. **随机性/模型差异导致质量不稳定**——提供更严格的约束文档/Spec Coding 方案；补充自检环节。
3. **修改型问题错误率高**——修改型问题＝上下文更多+正确率要求更高的生码任务，叠加 AI 理解力弱 → 准确率更低，即"改不动"的模型侧根因（详见 [[修改型任务难于生成型]]）。
4. **天生对某些问题能力弱，容易卡在死循环里**（死循环困境）——解法为识别常见错误场景、By Case 分析积累经验、沉淀对应解法。
