# 多智能体消息机制

## 简介

在 LLM 驱动的多智能体系统中，消息如何在多个 Agent 之间流转、隔离和格式化是核心技术挑战。[[agentscope|AgentScope]] 通过 MsgHub、MultiAgentFormatter 和 Memory 三大组件协同解决这一问题。

## 核心问题：LLM API 三角色限制

标准 LLM API 仅支持 system/user/assistant 三种角色，无法直接区分"3号玩家"和"5号玩家"的发言。直接将所有对话作为多条 user 消息传入，会导致模型混淆，逻辑推理无从谈起。

## MsgHub：发布-订阅模式的消息频道

### 三种使用方式

| 模式 | 应用场景 | 特点 |
|------|---------|------|
| 自动广播 | 讨论阶段 | Agent `call()` 后消息实时推送给所有订阅者 |
| 手动广播 | 投票阶段 | 关闭自动广播，收集完毕后 `broadcast()` 统一公布 |
| 多实例隔离 | 夜间行动 | 狼人密谋、预言家查验、女巫决策各自独立的 MsgHub 实例 |

### 消息流转方法

- **`call()`** — Agent 主动发言/决策
- **`observe()`** — Agent 被动接收消息写入 Memory，不立即回复
- **`broadcast()`** — 手动广播，将收集的消息统一推送给所有订阅者

## MultiAgentFormatter：消息格式化

### 两步解决方案

1. **消息标记** — Agent 创建时的 `name` 自动绑定到每条消息的 `name` 字段
2. **消息合并** — 将 Memory 中多条独立消息合并为一条带 `<history>` 标签的 user 消息

### 格式化效果

格式化前：9 人 2 轮讨论产生 18 条独立 user 消息，LLM 无法区分说话者。

格式化后：LLM 仅接收 2 条消息：
- 1 条 system 消息（角色设定）
- 1 条 user 消息（含 `<history>` 标签的完整对话历史，每条发言以 `name: content` 格式呈现）

### 模型适配

为通义千问（DashScopeMultiAgentFormatter）、OpenAI GPT、Claude、Gemini 等主流模型均提供了对应的 Formatter 实现。使用仅需一行代码：`.formatter(new DashScopeMultiAgentFormatter())`。

## Memory：对话记忆管理

`InMemoryMemory` 记录完整的讨论历史，使 AI 能回顾对话并判断发言中的逻辑漏洞。Memory 与 MsgHub 配合，确保每个 Agent 只能看到其角色权限内的信息。
