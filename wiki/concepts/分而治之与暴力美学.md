# 分而治之与暴力美学

**分而治之与暴力美学**是对"解决问题的方法进行足够抽象"后得到的两种解题思路（[[阳萌]] 的观点，[[韩春]] 在《业务逻辑的坍塌（下）》第九节引述）。它为"AI Agent 时代该构建什么"这一元问题提供了顶层解题观。

## 两种思路

1. **分而治之（符号主义路径）**：把大问题拆成一个个已知问题，然后通过严谨的数据符号、规则去解决。
   - 难点：大多数事物不是绝对 0 或 1，存在大量微观联系；纯粹借助数据符号表达，要么没有捕捉到微观细节而被忽略，要么表达式过于复杂无法落地。
   - 后果：**很容易把一个问题解决精度达到 50% 或 80%，再往上很难**。
2. **暴力美学（LLM 路径）**：不再需要对细分之后的问题进行精确求解，**直接通过海量参数以及算力逼近原问题**的解决。

## "暴力美学"的实战注脚：担保平台刷单风控案例

监管机构为规避商家跑路风险（如健身房充卡）搭建担保平台，商家通过刷单骗取补贴形成灰产。借助 LLM，**即便不做任何 Context 管理**，仅将商家一段时间内订单及对应买家数据（含征信）组成一个大 Prompt 提交，也能发现问题且效果不错——"实实在在解决了一个痛点问题"。

**证据等级：弱**。此案例为作者转述的单一轶事，无量化指标，仅作定性佐证。

## 适用边界（与上下文工程的张力）

该案例宣称"不做任何 Context 管理也能解决且效果不错"，与 wiki 全库（以及源文自身参考资料 [5] Anthropic context engineering）强调的 [[上下文工程]] 重心形成张力。这**并非硬矛盾**：

- 案例属**一次性痛点场景**——验证可行即可，无需长期演进；
- 工程化纪律面向**规模化**——需要可控、可维护、可评测的系统（参见 [[agent胶水层]]、[[业务知识内化]] 中"胶水代码"的演化语境）。

由此得到适用边界：**暴力美学适合问题验证与一次性突破；进入规模化生产后仍需回到结构化的上下文工程**。

## 内部张力与相关叙事

- 作者一方面论证暴力美学的胜利，一方面全系列强调工程约束与结构化方法——结尾"令人兴奋又焦虑"正是这种张力的自白。
- 暴力美学的史观基础是"结构 60 年未变、变在算力与数据"（[[Transformer历史阶段性]]、[[显存墙与算力墙]]）；而应用侧"脚手架收益远超模型升级"的对照叙事见查询页 [[规模化与脚手架孰为ai进步主因]]。
