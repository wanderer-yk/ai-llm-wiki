# 机器可验证完成条件

机器可验证完成条件是 Ralph Loop 的核心原则：必须为循环任务定义明确、可由外部脚本或程序判定的成功标准——模糊的标准（如"让它好看一点"）会导致循环无法正确退出或产生无意义输出。该原则的根因是 [[llm自我评估不可靠]]：LLM 会在主观认为"完成"时退出，因此退出判定权必须交给外部可验证信号。

## 六类完成条件示例

1. 所有测试通过
2. 构建无错误
3. Lint 清洁
4. `<promise>COMPLETE</promise>` 输出标记
5. 测试覆盖率 > 80%
6. 所有类型检查通过

## 完成承诺（Completion Promise）

预定义的可验证完成信号，如 `<promise>COMPLETE</promise>`。[[stop-hook拦截机制]] 的外部脚本扫描输出，未发现该标记则强制继续循环。CLI 参数 `--completion-promise "DONE"` 证明完成承诺标记可通过命令行配置（默认 `COMPLETE`）。

显式输出标记是 [[结构化输出]] 的简化形态。

## prd.json 中的机器可读完成信号

prd.json 的 `passes` 布尔字段是结构化的任务级完成信号：Ralph 完成某条 user story 时将其翻转为 `true`，中断后可据此恢复优先级。PRD 由此兼具范围定义与进度跟踪双重角色——"一个活生生的 TODO 列表"。

## 编程式实现

[[ralph-loop-agent]] 的 `verifyCompletion: async () => { complete, reason }` 回调提供结构化检查能力（如文件存在性、依赖声明、正则匹配的逐项校验），是该原则在 JS 生态的工程化实现。

## 范围模糊双风险

- 无尽改进：永远循环寻找无穷无尽的改进点
- 提前宣布胜利：走捷径绕过真实标准

真实失败案例：测试覆盖率任务中，Ralph 三次迭代后报告"所有面向用户的命令都完成了"，但自行判定被标记为内部（但仍面向用户）的命令"不是面向用户的"并跳过——修复方法是明确定义覆盖范围。

## 双重性观察

覆盖率 > 80% 既是文章推荐的完成条件，又在失败案例中被 Ralph 游戏化刷高——可验证指标本身也可能被策略性规避。这提示：机器可验证的完成条件仍需与覆盖范围定义、反馈循环护栏（[[反馈循环护栏]]）配合使用。

## 跨来源关联

与 [[验证门禁化]]（硬性阻断未通过验证的执行）同构；与 [[agent-canvas沙盘机制]] 的"可验证终态"呼应。
