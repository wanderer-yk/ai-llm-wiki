# Harness Engineering

由爱奇艺 [[数据库团队]] 于2026年5月提出的方法论，旨在通过工程化手段解决 AI 辅助开发中的"无限返工"问题。部分理论参考了 OpenAI 的 Harness Engineering 实践。

## 核心定义

**Harness** 指一套让 agent 能稳定参与研发的工程安排。核心理念是将团队对 agent 的期待（多做/少问/少出错）从模型能力问题转化为工程条件问题。

## 五要素

1. **任务入口** — agent 从哪里拿到目标、范围、非目标和验收口径
2. **执行依据** — agent 从哪里读到设计依据、计划和项目约束
3. **工具边界** — agent 能访问什么、不能修改什么、在哪个目录工作
4. **验证反馈** — agent 跑完代码后从哪里读测试结果、review 结论
5. **结果记录** — agent 把结果写回哪里（任务系统/PR/MR/仓库文档）

## 第一性原理

瓶颈已从"谁来写"转向：任务有没有说清、边界有没有定住、验证能不能跑、结果有没有人接。代码生成再便宜，人的注意力仍消耗在需求澄清、优先级判断、验收定义、架构取舍、质量判断五件事上。

## Agent 能力三约束

- 无法访问的知识 ≈ 不存在
- 无法执行的工具 ≈ 没有
- 无法验证的目标 → 很难持续修正

## 五层架构模型

| 层次 | 典型工具 | 核心职责 |
|------|----------|----------|
| 任务编排层 | Linear/JIRA | 定义目标/范围/责任人/优先级/验收口径 |
| 执行依据层 | Pencil/docs/plan | 冻结结构/边界/非目标 |
| 状态暴露与验证层 | Storybook/runbook | 显式展示系统行为 |
| Agent 执行层 | Codex/Cursor/Claude Code | 搜索/编辑/执行/验证/回写 |
| 评审收口层 | GitHub/GitLab | diff审查/CI校验/合并/审计留痕 |

## 信息策略

采用 [[多源分治策略]]：关键不是把某个系统称为"唯一来源"，而是让每类信息都有清楚的位置。四层落点：任务系统→仓库→PR/MR→agent工具。这与 [[ssot单文档策略]] 形成方法论对比。

## 验证五层模型

1. **静态检查** — 结构/类型/lint/配置
2. **单元验证** — 核心函数/边界条件
3. **链路验证** — 入口-输入-处理-输出连通性
4. **失败验证** — 异常/超时/重试/回滚策略
5. **回写验证** — 结果同步到任务系统/PR/文档

## 三阶段落地路线

- **阶段1**：补 AGENTS.md、验证命令和计划模板 → agent 找得到入口
- **阶段2**：固定 plan、runbook、验证摘要和 PR 回写格式 → 任务可复盘复用
- **阶段3**：高频 review 问题升级为 lint/script/test/CI → 重复问题机械化

## 与 Prompt Engineering 的关系

两者互补而非替代：
- **Prompt Engineering**：解决"这一轮怎么说清楚"
- **Harness Engineering**：解决"项目里如何持续做对"

## 能力边界声明

- 解决任务如何进入项目、执行、验证、回写
- **不替代**人的需求判断、架构取舍和质量判断
- 不追求全流程化，只系统化高风险/高协作成本/高复用价值部分
- 与 [[bmad-method]] 的多代理全能定位存在方法论分歧

## 与 Specflow 的对比

| 维度 | Harness Engineering | Specflow |
|------|---------------------|----------|
| 信息策略 | [[多源分治策略]] | [[ssot单文档策略]] |
| 工具绑定 | 工具无关 | 深度绑定 [[cursor]] |
| 落地方式 | 渐进演化 | 完整流程替换 |
| 门控方式 | review gate（渐进自动化） | [[blocker-gate]]（硬性阻断） |
| 适用范围 | 前后端通用 | 前端为主 |
| 理论来源 | 参考 OpenAI 实践 | 融合 OpenSpec/GitHub Spec Kit/BMAD |

两者同属爱奇艺、同公众号，在核心实践上趋同（都用 plan 冻结范围），但理论表述和实现路径不同。

## 第三方定义：百度版（2026-04，"缰绳"谱系）

百度Geek说《HarnessEngineering：让Coding Agent可靠完成长程任务》（[[无糖可乐]]）提供两个互补定义：

1. **缰绳隐喻**（01 节）：Harness 英文本意"缰绳"，Agent 场景即让强模型在**安全边界内被稳定地约束、引导和复用**；
2. **基础设施定位**（09 节，[[harness基础设施论]]）：Harness 是"团队基础设施建设的一部分，解决 Agent 完成大规模任务时的不确定性，并提供可量化的结果评估能力"。

配套 [[harness边界移动论]]：Harness 每个环节都隐含"当前模型做不到"的假设，随模型进化过期，但"哪些交给模型、哪些留在框架"的判断不会消失。方法论主体为长程任务三特征/三困难/四原则 + 任务边界三模式 + skill-for-skill 元技能自举。三方定义谱系对照见 [[comparisons/三方Harness定义对比]]。
