# 代码理解的五种范式

"代码理解的五种范式"是《[202604231830]从可观测到可理解用UModel构建Agent原生的代码知识图谱》提出的分析框架，将 Agent 代码理解技术沿"**无状态搜索 → 有状态推理**"轴线排列为五代，UModel（范式五）位于轴线最右端。该框架是全文的批判与论证骨架。

## 五范式总览

| 范式 | 名称 | 代表 | 核心机制 | 根本局限 |
|------|------|------|----------|----------|
| 一 | Agentic Search | [[claude-code|Claude Code]] | grep/rg/glob 实时搜索，零预处理 | 无结构感知、每次从零开始、规模受限、无法全局分析 |
| 二 | CodeIndex/向量索引 | [[cursor|Cursor]]、Windsurf、GitHub Copilot | tree-sitter 切片→embedding→向量库→Merkle tree | 向量相似度是文本层近似匹配，非结构层关系推理 |
| 三 | Code Graph + RAG 混合 | [[qodo|Qodo]]、[[augment-code|Augment Code]] | 向量索引上叠加代码结构图 | 图限于代码域、查询能力受限、IDE 局部、缺时序维度 |
| 四 | CodeWiki/LLM 文档 | [[deepwiki|DeepWiki]] | 仓库→LLM→Wiki 文档 | 对 Agent 五难：难验证/难遍历/难推理/难维护/不可编程 |
| 五 | 代码知识图谱 | [[umodel|UModel]] | Entity+Log+Link 统一建模 + SPL/graph-match | 尚无第三方验证，评测基准仅为规划 |

## 范式一的细化

Agentic Search 信奉 Unix 哲学：零预处理、永远新鲜、隐私友好、简单可靠。工具按 token 成本分层（Glob 近零 / Grep-ripgrep 低 / Read 高）。文章引用 Anthropic 内部测试结论：agentic search 性能全面超越 RAG（"by a lot"，出自 Boris Cherny 公开分享）。但在 5 万文件企业级单仓下需 30+ 轮工具调用和几万 token，只能拼出局部视图。

## 范式二的关键工程事实

Cursor 管线：代码仓库 → tree-sitter 解析为 AST → 语义切片 → embedding → Turbopuffer → Merkle Tree 增量同步。工程优化含每 10 分钟根哈希比对、92% 代码库相似度复用（无口径）、`.cursorignore`。本质论断："更聪明的搜索引擎，不替 Agent 做结构化推理"；其真正价值是语义搜索（自然语言意图找代码，grep 做不到）。Augment 评测显示 Cursor 在 50+ 文件重构中后 20 个文件因上下文溢出错改。

## 范式四的数据库类比

文章将 Wiki 文档类比为数据库的"物化视图"，将 [[umodel|UModel]] 定位为"查询引擎"——物化视图为人类阅读优化（线性叙事），查询引擎为程序化消费优化。

## 范式五的三维度

UModel 与前四范式的关键差异"不是更好的搜索"，而是三维度系统性结合：

1. **确定性 vs 概率性**：AST 确定性提取（1.0）+ 图灵完备查询；
2. **代码域 vs 跨域**：EntitySetLink 打通 code/ops/event/req 域；
3. **快照 vs 时间线**：五种 LogSet 完整时间维度。

## 与既有 Wiki 内容的关系

- 范式一与 [[claude-code]] 纯 grep 记载一致，并对 [[向量检索rag]] 构成反向证据（Anthropic 结论）。
- 范式二直接支撑 [[rag技术瓶颈]] 与 [[向量相似度非结构推理]]。
- 范式五与有赞 [[code-insight]]（AST+符号表双路径）的能力边界需进一步辨析：后者是否等价于本文批判的"Code Graph"层，待对比确认。
- [[三范式量化评测基准]]是该框架的操作化验证方案（规划中）。
