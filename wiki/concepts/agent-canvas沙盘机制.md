# Agent Canvas 沙盘机制

由 vivo [[ding-junjie]] 以 Amazon 电商场景的 [[agent-canvas]] 为实证案例提炼。核心思想：将复杂、开放、不可逆的业务管理动作先映射到可推演、可比较、可审查的画布空间，再决定是否推进到真实执行。

## 从 OpenClaw 走向生产落地的四步路径

### 步骤一：结果产物化
Agent 输出从对话日志升级为可审阅/可比较/可存档的正式产物：配置快照、数据前后对比、变更提案、审批记录、指标验证报告、生效记录和补偿方案。详见 [[结果产物化]]。

> "很多 agent 系统最终沉淀的只有对话和日志，不足以支撑审阅、审批和回溯。"

### 步骤二：验证门禁化
验证从"建议检查"升级为硬性阻断规则。详见 [[验证门禁化]]。

### 步骤三：构造业务 diff 等价物
为缺乏 git diff 的业务世界人为构造变更对比能力。详见 [[业务diff等价物]]。

> "业务世界天然没有 git diff，但不能因此接受'无法知道到底改了什么'。"

### 步骤四：高风险决策前置到沙盘
方案对象化→多角色讨论→Agent 不直接碰真实系统→形成候选提案→批准/驳回/修改/对比有明确载体。

## 沙盘即业务分支

沙盘的本质价值不是展示，而是提供可推演、可审查的决策空间。**当沙盘成立后，业务世界第一次具备类似代码世界中"分支"的能力**——先在安全空间形成版本，再决定是否合并到真实世界。
