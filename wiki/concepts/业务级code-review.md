# 业务级 Code Review

## 定义

业务级 Code Review 是 [[货拉拉大前端]] 提出的 AI 代码评审定位，核心目标是构建一个**有记忆、懂业务、看过线上事故**的 AI 评审助手系统。与通用 AI 代码审查工具不同，业务级 Code Review 强调将团队历史踩坑经验注入 AI 的审查上下文，使 AI 能够识别与历史事故相似的代码模式。

文章核心理念概括为：**"把团队踩过的坑变成模型的直觉"**。

## 解决的痛点

| 痛点 | 传统人工审查 | 通用 AI 工具 |
|------|------------|-------------|
| Diff 数量过多 | 审查疲劳、遗漏 | 无影响 |
| 历史事故遗忘 | 同类问题反复出现 | 缺乏历史知识 |
| 业务上下文缺失 | 依赖审查者个人经验 | 不懂业务逻辑 |

## 系统架构

完整链路包含六大环节：

1. **事件触发**：[[gitlab-webhook]] 监听 Push events 和 Merge request events
2. **Diff 预处理**：[[diff预处理流水线]] 进行特征过滤、切片化、语义重塑
3. **经验召回**：[[rag经验召回引擎]] 基于余弦相似度检索 Top 2 相关历史事故
4. **深度 Review**：LLM 融合原始 Diff + 语义简要 + 检索到的历史问题进行审查
5. **可视化报告**：生成结构化审查报告并发送消息通知
6. **反馈闭环**：开发者标记误报，系统微调检索策略（规划中）

## 工程优化

针对大规模 Diff 场景，系统采用 [[长diff分片并发与报告整合]] 策略，包含 Token 安全余量分片、优先级权重计算、并发 API 调用和多 Chunk 报告整合四项优化。

## 实践效果

系统已在核心业务大组深度落地，老事故复发率明显下降。当历史复盘文档命中时，系统可提示"当前代码与历史事故逻辑模式相似度达 85%"，有效缩小人工审计盲区。

## 与其他 AI 审查方案的对比

### 与美团 Pre-PR 机制的差异

[[pre-pr机制]] 侧重 AI 多轮自查前置审查，在代码提交前由 AI 自动执行多轮检查。货拉拉业务级 Code Review 侧重 RAG 召回历史事故经验注入，核心差异在于"经验驱动"vs"规则驱动"。

### 与腾讯 MR 双重视角审查的差异

[[mr双重视角审查]] 同时审查代码和规划文档，三维度对照。货拉拉聚焦业务上下文与事故复盘匹配，不涉及规划文档审查。

### 与转转六步智能提示词生成法的差异

[[六步智能提示词生成法]] 从 Sonar 静态扫描结果出发生成修复提示词，面向的是代码质量问题（如代码异味、安全漏洞）。货拉拉从 Git Diff 出发进行业务逻辑审查，面向的是业务正确性和历史教训避免。

### 与有赞 Code Insight 的关系

[[code-insight]] 同样使用 RAG/AST 技术进行代码理解，但聚焦于代码搜索与问答场景。货拉拉聚焦于代码审查场景，两者共享 [[gigo原则]]——输入质量决定输出质量。

## RAG 幻觉风险

文章指出，RAG 召回的"似是而非"历史案例会导致模型幻觉和误报。为此系统设计了 [[相似度阈值过滤]]（低于 0.85 的召回结果被过滤），但仍存在改进空间。这与 [[rag技术瓶颈]] 中描述的 RAG 在结构化任务上的固有局限一致。

## 与验证门控共识的关系

货拉拉规划的 [[发布卡点校验]] 将审计结果作为发布流水线的标准条件，与 [[blocker-gate]]（爱奇艺）、[[pre-pr机制]]（美团）、[[验证门禁化]]（vivo）形成跨团队的**验证门控共识**——货拉拉的独特贡献在于门控依据不只是静态规则或 AI 自查，还包含历史事故相似度匹配结果。

## 开放问题

1. 系统的误报率、事故下降百分比等量化数据缺失
2. "反馈学习链路"微调检索策略的具体技术实现未展开
3. 相似度阈值 0.85 的确定依据未说明
