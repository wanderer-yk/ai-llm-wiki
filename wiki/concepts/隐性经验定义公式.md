# 隐性经验定义公式

真正的隐性经验 = 特定场景 + 边缘情况 + 官方文档不会涵盖

## 定义边界

[[珈文]] 明确指出，组件 API 基础用法和框架标准配置不属于隐性经验范畴，应由官方文档维护。隐性经验的核心困境是"太细节不适合写组件文档，太具体不适合写开发规范"。

## 隐性经验三类型

应被系统自动沉淀的隐性经验具体分为三类：

1. **特定场景边缘问题**——如低代码平台生成的 code-diff 组件名与源码仓库组件库不对应
2. **内部基建特殊行为**——如接口地址必须以 / 开头否则被内部网关拦截
3. **多技术栈交叉问题**——如 tsconfig 只配置 `types: ['react']` 会导致隐式引入不存在的类型定义

## 操作化为分类矩阵

[[知识沉淀分类矩阵]] 以"类型/示例/是否应沉淀"三维度将该公式操作化为具体判定规则：组件 API 用法和框架基础配置不应沉淀（属官方文档职责），三类隐性经验应沉淀。

## 与经验库边界的关系

[[经验库内容边界原则]] 进一步给出了实操判定标准：基础属性用法属于组件文档范畴不应入库；特定业务域下组件行为异常及绕过方案属于踩坑经验应入库（如 ProTable columns 属性用法 = 组件文档；业务域B 列宽自适应失效需手动 width = 踩坑经验）。
