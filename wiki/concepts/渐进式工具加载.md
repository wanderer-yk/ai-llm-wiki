# 渐进式工具加载

Agent 工具加载的工程策略：任务开始仅加载基础工具（~3K tokens），Agent 按需将新工具描述追加到 messages 流尾部，已有上下文缓存完全保留。

## 解决的核心问题

Anthropic Prompt Cache 按严格顺序（system → tools → messages）构建缓存前缀。Tools 字段变动导致后续全部缓存失效——5→6 个工具的变更可使 100K messages 缓存全部失效。

[[mcp]] 的动态工具发现（核心价值）与缓存稳定性（成本控制关键）存在不可调和的矛盾。

## 三层解决方案

### 1. 工具描述移入 Prompt

将工具描述从 tools 字段嵌入 messages。优势：新增工具不破坏缓存前缀、与 [[追加式上下文]] 兼容。代价：离开 tools 字段的结构化保证，需自行实现解析/调用逻辑，模型理解自定义 API schema 的可靠性可能下降。

### 2. 本地控制台 + 远程 MCP 分层

- **本地能力用控制台**：仅需 1 个 `execute` 工具定义，永不变化，完美命中缓存，利用模型预训练世界知识（curl/grep/psql/docker），不需要 JSON Schema 定义陌生 API
- **远程能力用 MCP**：标准化接口结构和鉴权

[[claude-code]] 报告 92% 缓存命中率核心策略即"永远不改变 tools 列表"。

### 3. 渐进式加载

任务开始仅 ~3K tokens 基础工具，Agent 按需追加新工具描述到 messages 尾部。工具跟着对话流走，而非钉死在缓存前缀头部。

渐进式加载三阶段示例：`~3K → +mcp_search → +query_db`

## 混合策略

高频核心工具放 tools 字段保证可靠性和缓存稳定，低频动态远程工具通过 prompt 渐进式加载。
