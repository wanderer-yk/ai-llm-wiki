# CoT 驱动意图识别与并行检索

跨端技术团队为 [[AI答疑助手]] 设计的查询侧优化方案（原文小节标题："CoT 驱动的查询分解与并行召回"）：不再直接改写用户查询，而是先让模型推理出解决问题的逻辑步骤，再基于思维过程生成多组查询并行召回，以解决传统 RAG 对提问方式敏感、查询覆盖面窄的问题。

## 四步架构（原文口径）

```
CoT 驱动查询分解与并行召回流程：
1. 识别用户意图   — 模型: qwen-turbo-latest（选型理由: 极低延迟、意图识别无需强推理）
2. 生成思维过程   — 先输出解决问题的逻辑步骤（非直接改写查询）
                    例：白屏问题→环境差异排查→渲染链路检查→监控日志确认
3. 生成多组查询   — 每个步骤产出对应知识库查询关键词组（每步骤可多条）
4. 并行知识库召回 — 所有查询组并行向量检索 → 汇总去重 → 交最终答疑 LLM
```

量化口径：传统串行 query rewriting 产出 2-3 条查询 vs 本方案十几条覆盖不同维度的查询。

## 两大核心区别

1. **思维链作为查询分解骨架**：召回知识天然具有逻辑递进关系，而非语义相近但结构松散的结果堆。
2. **多组查询并行执行**：突破单次检索能力上限，覆盖问题涉及的不同维度。

## 对比论证：query rewriting 两局限

业界主流"过一层模型"（[[Query改写]]）方案的两个本质局限：
- **改写是"平面"的**：仅做语义层同义替换/扩展，不理解问题内在结构，无法捕捉多维度逻辑递进需求；
- **检索是"串行"的**：多样性与覆盖面受限于单次检索能力上限。

## 上下文工程定位：被动 vs 主动

- 传统 RAG 上下文构建是"被动"的：用户问什么检索什么，质量取决于提问质量+检索运气；
- 本方案是"主动"的：先理解问题结构→规划信息维度→有目的地检索组装。

## 边界与展望

- **边界**：意图识别只能解决"用什么去检索"，无法解决检索架构本身的结构性局限（切块切断上下文/无法跨文档关联推理/知识碎片化）——这是引出 GraphRAG→LightRAG 演进的原因。
- **作者自评**："某种程度上已经具备了 Agentic RAG 中'自主规划检索策略'的雏形"（自评定位，无实证，与 [[agentic-rag]] 完整定义存在能力差距）。
- **模型策略呼应**：意图识别选用 qwen-turbo-latest（见 [[qwen]]），与有赞 AI 客服用 qwen 做意图识别形成跨团队呼应。
