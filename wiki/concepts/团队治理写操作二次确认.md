# 团队治理写操作二次确认

**团队治理写操作二次确认**是 RDSHermes 面向团队落地场景的治理机制（**厂商自述，未经第三方验证**）：当 Agent 需要执行写操作时，必须经过二次确认才能执行；会话全程可追溯、可审计。原文将其概括为一句定位——"Agent 能自我进化，但每一步操作都在审计链路上"。

## 问题背景

作者在"Skill 自动进化的下一步"章节指出：开源 [[hermes-agent]] 一人使用时自治问题不大，但团队落地必须回答"谁让 Agent 做了什么"。自进化能力越强（Agent 自主创建/修补 Skill、自主积累记忆），组织对可控性与可追责性的需求就越强。

## 机制内容（厂商自述）

- **写操作二次确认**：变更性操作需人工确认后才执行；
- **会话可追溯可审计**：每一步操作都留存于审计链路；
- 配套 RDSHermes 四件套之一的全链路监控审计：Token 消耗可监控、安全事件有告警。

## 与 [[agent-control-plane]] 的同族关系

zhiyuanfu 提出的 [[agent-control-plane]]（权限/边界/审计）与本文机制共享同一逻辑：**Agent 自主性的释放必须以控制平面为前提**。写操作二次确认+审计可视为该理念在"自进化 Agent 团队落地"新场景的具体化。它与 [[多层安全护栏]] 纵深（Hermes 的 [[记忆内容威胁模式扫描]]、[[skill安全扫描统一门禁]] 加 RDSHermes 的 [[密钥托管凭证隔离]]）共同构成从"内容安全"到"操作治理"的完整链路。

## 与 [[组织级自进化]] 的配平

[[组织级自进化]]（Skill 存储上云、全团队受益）扩大了 Agent 经验的影响范围，写操作二次确认与审计则为这种扩大划定边界——"进化越自由，治理越必要"。二者在 RDSHermes 产品设计中构成一对配平。

## 归因注意

RDSHermes 的全部治理能力描述为厂商侧（阿里系产品推广语境）自述，具体技术实现（确认交互形态、审计存储、权限模型）原文未展开，引用需标注归因。注意与作者展望类方向（如 [[skill创建透明度]]）区分：前者为厂商宣称已实现，后者为开源版未实现的展望。
