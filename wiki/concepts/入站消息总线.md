# 入站消息总线

入站消息总线（MessageBus）指处理**入站方向消息流**（子系统/外部 → 主 Agent）的进程内消息组件，与出站的 MessageTool（`sendCallback`）方向相反、无直接代码耦合——作者总结命名为「双通道消息机制：方向明确，互不耦合」。它是苏雄 800 行框架的第二块核心设计，也是用户渠道、子 Agent、cron 三类消息源的汇聚点。

## 数据结构与实现

`InboundMessage` 四字段：

| 字段 | 含义 |
|------|------|
| `channel` | 消息通道 |
| `senderId` | 发送者标识 |
| `chatId` | 关联会话，格式 `originChannel:originChatId` |
| `content` | 消息内容 |

MessageBus 完整类实现（保留导出件原貌；`!add`/`?delete`/`[.this.queue]` 为疑似渲染损伤，应为 `!.add`/`?.delete`/`[...this.queue]`）：

```typescript
export class MessageBus {
  private listeners = new Map<string, Set<MessageHandler>>();
  private queue: InboundMessage[] = [];
  subscribe(channel: string, handler: MessageHandler): () => void {
    if (!this.listeners.has(channel)) {
      this.listeners.set(channel, new Set());
    }
    this.listeners.get(channel)!add(handler);
    return () => { this.listeners.get(channel)?delete(handler); };
  }
  async publish(message: InboundMessage): Promise<void> {
    const handlers = this.listeners.get(message.channel);
    if (handlers && handlers.size > 0) {
      for (const handler of handlers) {
        await handler(message);
      }
    } else {
      this.queue.push(message);
    }
  }
  drain(channel?: string): InboundMessage[] {
    if (!channel) {
      const msgs = [.this.queue];
      this.queue = [];
      return msgs;
    }
    const matched = this.queue.filter((m) => m.channel === channel);
    this.queue = this.queue.filter((m) => m.channel !== channel);
    return matched;
  }
}
```

## 关键机制

1. **双消费模式**：`subscribe` 实时回调（常驻服务场景）+ `drain` 轮询取空（同步消费场景）。
2. **单路径路由规则**：有订阅者走回调，无订阅者入队列，消息**绝不同时**触发回调和入队。
3. **`system` channel 统一入口**：「内部消息的统一入口」——子 Agent 完成、CronService 触发都通过 `bus.publish()` 发送到该 channel。
4. **无持久化取舍**：纯内存队列，进程重启消息丢失；REPL 场景足够，Bot 场景需接入持久化存储（见 [[有意取舍边界声明]]）。

## 出站侧与回调注入消息通道

出站侧 MessageTool 构造时注入 `sendCallback`（回调注入消息通道）：REPL 下即 `console.log` 终端输出，Bot 场景只需替换回调为 Telegram/Discord 等平台发送函数，「工具系统和 Agent 逻辑不需要任何改动」——[[薄抽象设计哲学]] 中通道热插拔的直接例证。
