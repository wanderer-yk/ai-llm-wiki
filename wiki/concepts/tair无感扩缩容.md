# Tair 无感扩缩容

Tair 无感扩缩容是 [[tair]] 云原生版通过内核级优化实现的集群扩缩容能力：数据以 **Slot 为单位原子性整体迁移**（而非逐 Key 迁移），不会造成 Slot 分裂；同时通过**中心化的控制组件**协调集群行为，使迁移效率更高、决策更精准，扩缩容操作对业务完全透明，应用层无需任何适配。

## 动机：传统 Redis 的迁移错误对 Agent 链路致命

传统 Redis 集群在 Slot 迁移过程中可能产生 `-ASK`、`-TRYAGAIN` 等错误。对 Agent 对话场景而言，任何一次请求失败都可能导致对话中断或记忆丢失（记忆层是每轮对话的必经依赖，见 [[agent短期记忆]]、[[little定律并发放大]]）。因此弹性扩容必须做到"请求不失败"。

## 扩缩容实践（春节 5～10 倍峰值）

```text
日常流量：
  集群 8 分片，每分片 1 只读副本 → 满足日常业务需求

春节活动（5～10 倍峰值）：
  方案一：每分片扩展至 5 只读副本 → 读吞吐线性提升
  方案二：集群扩至 16 分片 + 每分片 3 只读副本 → 读写能力同步翻倍
```

运维团队可按流量实时调整集群规模——活动前扩容、活动后缩容——全程业务无感。

## 内部张力："无感"是近似说法

原文同段承认：在数据迁移的**最终阶段**，对应 Slot 的写请求时延会**略有增加**（但不会失败）；对 Agent 记忆服务表现为个别请求延迟略升，不出现数据丢失或请求报错。考虑到本文以 [[little定律并发放大]] 论证过 5ms→50ms 即可导致在途请求 10 倍膨胀，对一个延迟极度敏感的链路而言，"无感"的表述并不完全成立，引用时应注意这一自述内部张力。

## 内部张力标注（review-3222058b，2026-10-10）

来源一边以 [[little定律并发放大]] 论证 5ms→50ms 延迟上升会使在途请求膨胀 10 倍并耗尽连接资源，一边宣称迁移「对业务完全透明、应用无需适配」，同段又承认迁移最终阶段写请求「时延略有增加」——对以延迟为命门的 Agent 记忆链路，两论断难以同时完全成立。**裁决：保留厂商原话「无感」命名 + 本注记显式标注张力**（不改来源命名，防后续引用误读）；弱化为「低影响扩缩容」的替代方案备而未用。
