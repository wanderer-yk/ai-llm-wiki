# API 优先浏览器自动化

API 优先浏览器自动化是 [[明径]] 在《浏览器自动化：从GUI到OpenCLI》中提出的自动化路径：不与网页界面较劲，直接抓取并复现页面背后的底层 API 请求，用接口调用替代按钮点击，以解决 GUI 自动化效率低、稳定性差（元素定位脆弱、渲染时序不可控）的困境。落地载体是 [[opencli]] 框架。

## 核心主张

- 浏览器里看到的数据，本质上都是前端从某个接口拿回来的。
- 把接口找出来、把请求复现出来，比点按钮靠谱得多。
- UI 自动化在接入策略中只作为最后手段（[[opencli五级认证策略]] 的 Tier 5）。

## 前提约束：懒加载 API 发现

纯静态分析被明确否定。原文以 CAUTION 级 Skill 指令规定：

> 你（AI Agent）必须通过浏览器打开目标网站去探索！不要只靠 `opencli explore` 命令或静态分析来发现 API。你拥有浏览器工具，必须主动用它们浏览网页、观察网络请求、模拟用户交互。

原因：很多 API 是**懒加载**的（用户必须点击某个按钮/标签才会触发网络请求）。字幕、评论、关注列表等深层数据不会在页面首次加载时出现在 Network 面板中——不主动浏览和交互页面，就永远发现不了这些 API。因此探索必须包含「模拟交互 + 二次抓包对比」环节（见 [[agent浏览器探索七步工作流]]）。

## 意义与关联

- **环境重构论的又一实证**：与 [[agent生产落地环境重构论]] 高度呼应——OpenCLI 本质是把浏览器「业务世界」改造为 CLI「可调用执行面」，是「改造环境而非提升模型」的路径；它人为给浏览器业务操作补上了「相对封闭/可验证」的特征（[[coding-agent四特征]]）。
- **与沙盘路线的分野**：[[agent-canvas沙盘机制]]（Amazon）选择把不可逆业务动作映射到可视化沙盘；API 优先路线选择绕过 GUI 直取 API。两条路线对「业务世界不可信 UI」给出不同答案。
- **竞争维度延伸**：该路径是 [[软件竞争可调用性]] 论断的工程化体现。

## 证据强度

工程实践级证据：有实测命令示例（如 `opencli hackernews top --limit 5` 无需浏览器、`opencli bilibili hot` 走浏览器）与可复现工作流，但无量化对比数据（无稳定性/耗时数字），属单作者经验陈述，引用需谨慎。
