# 文件轮询架构

[[zhiyuanfu]] 设计的 Agent 调度层核心架构，四字概括：文件+轮询。文件系统存储 + 轮询调度 + JSON 状态管理。

## 选型理由

1. **出问题让 AI 直接看文件** — 排查门槛最低
2. **方便 Git 版本控制** — 所有状态变更有据可查
3. **本地与生产环境一致** — 无环境差异

## 调度四职能

1. **接收任务** — 写入文件队列
2. **分发执行** — 轮询调用 CLI（[[codex]]→[[gemini-cli]]→[[claude-code]]）
3. **状态管理** — 持久化输入输出到 JSON
4. **失败切换** — 配额耗尽自动换工具+冷却 5 分钟

## 核心定位

"我要做的不是重新造一个 Agent，而是造一个管理 Agent 的调度层"——这是对 [[agent框架三要素]] 和 [[agent-loop]] 的元层抽象。当 [[codex]]/[[gemini-cli]]/[[claude-code]] 本身已是完整 Agent 时，需做的是管理这些 Agent 的调度、并发和失败切换。

## 与其他架构的对比

- 与 [[ssot单文档策略]]（Specflow 的 plan.md 集中）形成架构分歧——本文采用多文件分离策略
- 与 [[openspec]] 的多文件策略（spec/plan/tasks 分离）高度相似
- 起步阶段文件系统+JSON 优于数据库——出 bug 可让 AI 直接读文件排查
