# GraphRAG 工程化四困境

跨端技术团队以 44 篇文档实测 [[graphrag]] 后确认的四个致命工程问题——图结构确实有效解决上下文断裂与跨文档推理，但工程化方案太重，导致其"在我们的答疑场景中几乎不可用"。

## 四困境明细（原文口径）

| 致命问题 | 机制根源 | 量化/定性口径 |
|---|---|---|
| 索引构建成本极高 | 每篇文档实体抽取+关系挖掘均调用 LLM（通常需 GPT-4 级别保证质量），社区摘要又是一轮调用 | 44 篇文档消耗大量 API 调用，"费用不菲"（无金额数字） |
| 不支持增量更新 | 社区结构由 Leiden 在全局图计算；新文档→图谱结构变化→社区边界重划→所有社区摘要重生成 | 文中标注"最致命"；对知识库每天更新的答疑系统代价无法接受 |
| 查询延迟过高 | Global Search 遍历多层级社区摘要+Map-Reduce 聚合 | 一次查询可能耗时 5 分钟以上；Local Search 亦显著高于传统 RAG |
| 对抽取质量高度敏感 | 弱模型/文档表述不规范→图谱噪音→社区划分不合理 | 检索质量反而不如传统 RAG |

## 结论与权衡

- **结论**：GraphRAG 证明了图结构的有效性，但四个困境使其不适合知识库每天更新、要求实时响应的在线答疑场景。
- **场景定位权衡**：GraphRAG = 高成本、极致质量的**离线分析**；LightRAG = 实时响应、频繁更新的**在线答疑**。完整对照见 [[graphrag与lightrag对比]]。
- **GIGO 呼应**：第四困境（抽取质量敏感）本质是 [[gigo原则]] 在图谱构建上的体现——抽取质量直接决定图谱质量。
- **增量更新分水岭**：增量可行性是 GraphRAG 与 LightRAG 选型的分水岭（LightRAG 三步局部增量，见 [[lightrag三函数索引构建]]）。
