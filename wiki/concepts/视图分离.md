# 视图分离（C端逻辑视觉解耦）

**视图分离**是 [[天猫新品营销技术]] 团队在 AI 编码实战指南中提出的 C 端核心工程解法：将业务逻辑代码与视觉/视图代码拆分为可独立编写、独立复用的两部分，用以化解"逻辑与视觉耦合度高、AI 缺乏视觉感知力"导致的 C 端生码失效。它是 [[严格解耦架构设计防技术债]] 在 C 端视觉维度的特化版本，也是 [[D2C]] 工具在工作流中的锚定场景。

## 问题归因

团队在工程主导型案例（C 端复杂业务）的"具体执行阶段 - 解耦实现"步骤中指出，C 端 AI 编码不好用的两个主因：

1. 逻辑与视觉的耦合度太高；
2. AI 天生缺乏视觉感知力。

一次性写完两者会"顾此失彼"，复杂度显著上升。

## 解法三段式

> AI 完成逻辑代码 → 通过其他方案（如 D2C）完成视觉组件的编写 → AI 进行逻辑与视图的绑定。

基础视图分离结构 = **抽象组件**（承载属性与事件）+ **纯视觉组件**（仅绑定事件与属性）。原文 Bad/Good 对比：耦合严重时每次视图修改都波及逻辑实现（Bad）；完全解耦后业务层与视图层可快速迁移复用（Good）。作者注明两文件仅为展示，实践中可合并，"保留分离思维即可"。

## 三重收益与延伸

1. **CR 压力骤减**：购物车组件的 Code Review 只需重点审 index.tsx，"审查压力瞬间少掉大半"——与 [[pre-pr机制]]、[[mr双重视角审查]] 的审查面前置收敛思路互证。
2. **AI 代码拆解重构**：商卡组件含大量逻辑，新样式需求需"从原来 400 行的视觉组件里挑出来所有逻辑代码"；让 AI 将其改造为视图分离结构后，再通过 [[D2C]] 产出新卡片组件并绑定状态与事件，后续迭代更清晰（量化点：400 行）。
3. **视图分离组件库**：预设组件事件、由调用方实现视觉并绑定事件，最大化逻辑复用；实例为 feeds 模块的 tab 渲染交由调用方实现。

## 组件沉淀的双向复用红利

后期沉淀阶段的"组件沉淀"子节补全了价值闭环：视图分离后"业务逻辑组件的可复用度已经不再受限于视觉稿"；反向地，剥离逻辑的纯视觉素材也可以跨项目快速复用——形成逻辑组件与视觉素材的双向复用红利。

## 关联

- [[任务设计与拆分]]：视图分离是"组件拆分到可测试黑盒"策略在 C 端的具体形态（逻辑 hooks 可单测、视觉交给 D2C）。
- [[自检机制]]：功能自检明确建议"前端进行视图分离，对逻辑 hooks 部分进行单元测试"。
- 与 [[coding-agent四特征]] 对照：C 端视觉的"可视化缺口"是业务世界与代码世界的典型差异点。
