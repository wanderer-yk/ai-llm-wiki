# Workflow 与 Agent 的控制权分界

## 核心区分：控制权掌握在谁手里

Workflow 与 Agent 的本质区别不在能力强弱，而在**控制权掌握在谁手里**：执行路径由代码预先写死的是 Workflow，由 LLM 动态决定下一步的是 Agent（此区分在来源中归于 [[anthropic]] 的定义）。

作者的关键观察：现实中不少标榜"Agent"的产品更接近 Workflow；但两者无高下之分，关键是给任务找到合适方案。

## 七维对照表（来源原文）

| 维度 | Workflow | Agent |
|------|----------|-------|
| 控制权 | 代码预定义，同输入必走同一路径 | LLM 动态决策，可能需要评测验证 |
| 执行方式 | 工具顺序固定，错误走预设分支 | 工具按需选择，模型可尝试自我修复 |
| 状态与记忆 | 显式状态机，节点跳转清晰 | 隐式上下文，状态在对话历史中累积 |
| 维护成本 | 改流程需修改代码并重新部署 | 调整系统提示即可，无需重新部署 |
| 可观测性 | 日志定位节点，延迟可预估 | 需完整执行记录理解决策链，轮数不固定 |
| 人机协作 | 人在预设节点介入 | 人在任意轮次介入或接管 |
| 适用场景 | 流程固定、输入边界清晰 | 需要中间推理与灵活判断 |

## 工程含义

- **可观测性代价**：Agent 的隐式上下文意味着必须依赖完整执行记录才能理解决策链——直接支撑 [[trace六项记录清单]] 与 [[agent评测环境验证论]]（"模型可能需要评测验证"）。
- **与"先确定性后自主性"共识互证**：有赞 [[workflow优先于agent]] 与 [[三阶段平台演进路线]]、[[六步落地路径]] 均体现同一策略——先用 Workflow 保住确定性，再向 Agent 渐进放权。
- **与控制模式的关系**：[[五种常见控制模式]] 中的多数模式（提示链、路由等）属 Workflow 侧的结构化控制，佐证"很多场景不需要完整 Agent 自主权"。
- **选型判据**：任务四象限（[[任务四象限]]）提供了何时值得引入 Agent 自主性的量化视角——目标模糊且不可验证时，Agent 自主性反而放大风险。

## 与互补框架的分工

此分界与有赞 [[workflow优先于agent]]（先确定性后自主性）、[[harness四要素]]（为 Agent 任务补工程条件）构成互补：分界决定选型，Harness 决定 Agent 能否跑稳。
