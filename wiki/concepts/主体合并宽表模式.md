# 主体合并宽表模式

[[上下文工程]]数据注入的两条路径之一。围绕同一主体（如员工）预先聚合分散在多个系统中的数据为一张宽表，用一次性开发成本换取长期稳定正确率。

## 核心思路

否定 NLP2SQL（复杂场景准确率难破 80%，容错率为零即不可用）和逐系统 API 对接（工作量大、脆弱性高），转而采用**预计算+聚合**策略。

## 实践案例：员工信息宽表

- 预先聚合 4-5 个系统的员工相关数据
- 40+ 字段：假期余额、考勤记录、培训记录、在职证明等
- 按工号查询，模型回答正确率接近 100%

## 适用条件

- 主体明确且可枚举（员工、客户、供应商等）
- 数据源分散但围绕同一实体
- 查询模式相对稳定
- 对准确率要求极高（容错率接近零）

## 与其他方法的对比

| 维度 | 主体合并宽表 | NLP2SQL | 逐系统 API |
|------|-------------|---------|------------|
| 准确率 | 接近 100% | <80% | 不稳定 |
| 开发成本 | 一次性高 | 中等 | 持续高 |
| 维护成本 | 低（定期同步） | 中等 | 高（上游变更风险） |
| 灵活性 | 低（需扩展宽表） | 高（自然语言） | 中等 |

## 与其他方法论的关联

- 宽表模式的**聚合策略**与 [[harness-engineering]] 的[[多源分治策略]]**分离策略**形成有趣对比——反映不同场景（企业知识查询 vs 研发流程管控）下的信息组织策略差异
