# 架构发现非社区检测

"架构发现非社区检测"是 [[umodel|UModel]] BUILD 阶段的方法论立场：**Louvain/Leiden 等社区发现算法输出的是聚类，不是架构**；架构需要层次、方向和命名，必须在此基础上追加依赖方向层次分析与标注流程。

## 四步架构发现流程（原文 verbatim）

```
Step 1: 图构建
  module 为节点，imports + calls + extends 为有向边
  边权重：calls > imports > extends
Step 2: 层次分析
  计算依赖方向性：A→B 且 B↛A → A 在 B 上层
  识别入度 = 0 的顶层入口和出度 = 0 的底层基础设施
Step 3: 社区发现
  Leiden 算法在有向图上发现功能簇
  resolution 参数控制粒度（~150 模块 → ~15 组件）
Step 4: 标注与命名
  基于依赖方向标注层次：API/Gateway、Service/Business、Infrastructure/Utility
  LLM 命名和描述，与项目文档交叉验证
```

## 价值

输出有层次、有方向、有命名的架构视图，Agent 可据此判断一次调用是否跨越架构层次——直接回应两流派三类无解问题中的"架构边界检查"。案例三中 `check arch` 检出的两条分层违规（utility→api、infra→service）即以此视图为判定基础。

## 内部张力与外部对照

- **内部张力**：文章一方面主张"架构发现"，另一方面案例三的 `check arch` 内置了规定性分层规则（utility/api/infra/service 层级及禁止方向）——发现与规定在同一系统中并存，规则来源与配置方式未说明。
- **与美团 [[标准四层架构迁移]] 的对照**：美团路线是"规定式"（组织统一规定 Starter/Application/Infrastructure/Common 四层并迁移）；UModel 是"发现式标注 + 规定式检查"双重形态。两条路线分别对应架构约定的事前规定与事后审计。
