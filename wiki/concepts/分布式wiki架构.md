# 分布式wiki架构

有赞 Knowledge Wiki 采用的知识存储架构：`.wiki/` 目录跟随 Git submodule，知识与代码在同一分支提交，天然同步。

## 架构设计

```
workspace/
├── .wiki/
│   ├── workspace.yaml        # workspace 级摘要
│   ├── app-a/
│   │   ├── app.yaml          # 应用级摘要
│   │   ├── context-x/
│   │   │   ├── context.yaml  # 上下文级摘要
│   │   │   └── knowledge.md  # 具体知识内容
│   │   └── context-y/
│   └── app-b/
├── app-a/                    # 实际代码仓库（Git submodule）
├── app-b/
└── ...
```

## 核心原则

### 上下文 ≠ Maven 模块

上下文是业务切面，必须基于流程归并后的 Flow Cluster Map 划分，而非按技术包名（Maven module）划分。这是区分"知识架构"和"代码架构"的关键。

### 异步链路最高优先级

Producer/Consumer 无直接调用关系，AI 无法从代码串起异步链路，这类知识是 wiki 最大价值所在。

### 自底向上知识构建路径

- **app 级 wiki** 为基石层，从各应用逆向工程生成
- **workspace 级** 从 app 级中提炼、归并、收敛
- 初始化过程"先穷举再归并"即知识蒸馏

## 与其他方案的对比

| 方案 | 同步机制 | 优势 | 劣势 |
|------|----------|------|------|
| 分布式 wiki（有赞） | Git submodule 天然同步 | 零额外基建、分支级同步 | 各域知识无法交叉检索 |
| 活文档机制（腾讯） | archive 命令主动同步 | 统一管理 | 需要额外工具链 |
| 集中式知识库 | 服务端统一存储 | 全局检索 | 同步成本高、脱离代码上下文 |

## 取舍

作者自认分布式方案的不足：各域知识无法交叉检索、难以全局统计。但这是有意取舍——在当前阶段，确定性和同步可靠性优先于全局检索能力。中期规划引入服务端统一管理来弥补。

## 候选三去向原则

初始化过程中，每个候选流程/概念必须三选一：
1. **保留**——作为独立知识条目
2. **并入**——合并到已有条目
3. **排除**——不写入 wiki，但需注明排除原因

这一原则确保知识库精炼而非膨胀。
