# 任务流程定义困难问题

任务流程定义困难是[[沈询]]指出的 Function Calling 与 MCP 共有的两难：一方面，模型难以仅凭自身能力做出最优的调用步骤序列（自主调度不精确）；另一方面，把任务流程全部写成代码又丧失了模型"走一步看一步"动态调整的核心优势。该问题框架是 Skills 与 Func-Agent 两条技术路线的共同起源——两者都试图在"全代码化"与"全模型自主"之间寻找平衡点。

## 解法谱系

| 路线 | 流程载体 | 特点与代价 |
|---|---|---|
| MCP Server 内代码串接 | 代码型 API 串接逻辑 | 确定性高但僵硬，集成成本高 |
| Skills 文字化流程 | SKILL.md 文字流程 | 适应性增强，但不可能 100% 准确（[[skills-sub-agent包装论]]） |
| Func-Agent 函数化 | 函数暴露能力 + 模型调度 | 文内给出的收尾解法（[[一切都是函数]]） |

## 文字化流程实证

[[lynxe|Lynxe]] 的 `new_branch` 七步 markdown 流程在实际运行中"出错概率很小"（作者自报，无量化口径），被用作"文字化流程可行"的实证——完整流程定义（含 `mvn package`、`pnpm lint`、`git merge upstream/main`、tag 发布等步骤）见 [[lynxe]] 实体页。

## 与 MCP 的关系

MCP 的薄协议转换层（[[mcp薄协议转换层]]）解决的是"怎么调"（标准化接驳），而本问题指向"按什么顺序调"（流程编排）——后者在 MCP 框架下仍需在 Server 内以代码写死，这正是 Skills 以文字化流程发起竞争的切入口。
