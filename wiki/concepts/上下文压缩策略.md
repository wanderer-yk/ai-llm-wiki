# 上下文压缩策略

[[追加式上下文]]模式在 token 膨胀后的缓解机制。核心论断：**压缩是安全网而非解决方案**——压缩本身需额外 LLM 调用、摘要有损、压缩后话题仍混合。

## Claude Code 方案

- 触发时机：token 使用量达到 ~83.5% 上下文窗口时
- 压缩方式：一次性生成摘要（~167K → 摘要 ~10-20K + 近期轮次）
- 跨会话保留：**无**——压缩后的摘要不跨会话保存

## OpenClaw 方案

- 触发时机：分阶段渐进压缩
- 压缩方式：**记忆落盘**（先让模型将重要信息写入磁盘 .md 文件）→ 再对历史进行摘要压缩
- 跨会话保留：**有**——记忆文件跨会话存活，新会话可加载历史记忆

## 记忆落盘（Memory Persistence）

OpenClaw 的独特机制：在压缩前让模型将重要信息写入磁盘 .md 文件。这些文件跨会话存活，新会话启动时加载记忆文件，实现跨会话记忆连续性。

与 Wiki 已有的 [[长记忆四件套]]（小红书 PMO）形成对比——OpenClaw 的记忆落盘是文件级别的持久化，小红书的长记忆四件套（UserProfile + SessionMessage + KnowledgeItem + ContextBuilder）是更结构化的方案。

## 压缩的局限

1. **额外 LLM 调用** — 压缩本身消耗 token 和延迟
2. **有损** — 摘要不可避免丢失细节
3. **话题仍混合** — 压缩不解决多话题混杂的根本问题

## 与其他方案的关联

- [[任务隔离]] 从架构层面避免上下文膨胀，是比压缩更彻底的方案
- [[上下文工程]] 是更宏观的概念，压缩策略是其子集
- Wiki 已有的 [[sdd留痕进化论]]（zhiyuanfu）中的留痕机制与记忆落盘有相似理念——都将关键信息外化持久化

## Hermes 比例阈值方案（2026-04）

- **第三种触发机制**：Hermes 以 50% 比例阈值触发压缩（区别于绝对阈值与摘要式），配套 [[轨迹头尾保护压缩]]（头尾保护、中部裁剪）与 `on_pre_compress()` 钩子提取关键信息落盘；另引入**压缩器模型选择**新对比维度（用小模型压大模型上下文的成本/质量权衡）。
