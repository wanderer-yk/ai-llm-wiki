# 模型记忆与业务上下文记忆分离

模型记忆与业务上下文记忆分离是一种记忆建模方法论：**按消费者划分**记忆（模型消费 vs 业务工具消费），而非按时间或统一结构划分。淘宝闪购 Agent 将短期记忆拆为双轨——Model Memory（模型消费的对话历史）与 Business Context Memory（工具层/意图处理器消费的结构化状态）——分别选用不同数据结构存储。

## Model Memory —— List

存储供大语言模型消费的对话历史，每会话一个 Key：

```text
Key:  memory:model:{sessionId}
Type: List
示例：[{"role":"user","content":"帮我点杯奶茶"}, {"role":"assistant","content":"为你找到附近3家奶茶店...","cards":[...]}, ...]

RPUSH memory:model:{sessionId} "{对话记录JSON}"      # 每轮对话结束后追加
LRANGE memory:model:{sessionId} -{N} -1              # 推理前读取最近 N 轮
EXPIRE memory:model:{sessionId} 1800                 # 会话过期 30 分钟
```

写入前将原始数据（含卡片富媒体）转换为自然语言格式以减少 Token 消耗。RPUSH 有序追加 + LRANGE 范围读取正是 [[追加式上下文]] 思想的持久化数据库实现。

## Business Context Memory —— Hash

存储业务流程中的结构化状态，供工具层和意图处理器查询/更新：

```text
Key:  memory:context:{sessionId}
Type: Hash
Field 结构：
{
  "session":      "{会话元信息: 用户ID、渠道、会话阶段等}",
  "search":       "{搜索状态: 当前query、搜索结果、推荐商品列表等}",
  "order":        "{订单状态: 购物车内容、已选SKU、商品数量等}",
  "conversation": "{对话状态: 当前意图、上一轮意图、意图切换标记等}",
  "coupon":       "{优惠信息: 可用优惠券列表、已选优惠等}",
  "bizState":     "{业务状态: 收货地址、配送方式、支付状态等}"
}

HSET memory:context:{sessionId} bizState "{更新后的业务状态JSON}"   # 单独更新某个子模块
HGET memory:context:{sessionId} order                               # 读取特定子模块
HGETALL memory:context:{sessionId}                                  # 一次性读取所有上下文（意图识别等全局场景）
EXPIRE memory:context:{sessionId} 1800
```

## 为什么分离

- **消费者不同**：模型需要的是"对话文本序列"，业务逻辑需要的是"结构化领域状态"，二者读写模式与生命周期管理方式不同。
- **Hash field 级读写消除竞争**：各业务模块（搜索/订单/优惠/业务状态）独立更新、互不干扰，避免"读完整 JSON 再回写"的竞争——例如搜索模块更新商品推荐时，不影响订单模块正在写入的购物车数据。
- **并发安全由锁补齐**：双轨写入的一致性由 [[会话级分布式锁]] 保障。
