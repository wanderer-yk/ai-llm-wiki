# 多源分治策略

[[harness-engineering]] 方法论中的信息管理策略，主张"关键不是把某个系统称为'唯一来源'，而是让每类信息都有清楚的位置"。

## 核心观点

对话中的六类临时上下文（项目背景/任务范围/实现偏好/验证方式/注意事项/上次失败原因）在换人、换 agent、换任务后全部失效，必须迁移到稳定位置。但稳定不等于集中——应按信息职责分配到不同系统。

## 四层信息落点

| 落点层 | 存放内容 | 典型工具 |
|--------|----------|----------|
| 任务系统 | 目标/范围/状态/责任人/反馈 | JIRA/Linear |
| 仓库 | 设计依据/计划/验证入口/项目约束/结果记录 | Git 仓库 |
| PR/MR | 代码变更/评审讨论/CI结果/合并/留痕 | GitHub/GitLab |
| Agent 工具 | 搜索/修改/执行/验证/回写 | Cursor/Claude Code |

## 与 SSOT 单文档策略的对比

[[ssot单文档策略]]（来自 [[specflow]]）主张所有信息集中在 `plan.md` 一个文件中；多源分治策略主张信息按职责分散到四个稳定位置。这是同公司（爱奇艺）不同团队之间的明确方法论分歧。

可能的深层原因：[[天玑前端团队]]面向前端场景（信息密度相对低、单文件可管理），[[数据库团队]]面向后端场景（信息类型多、职责差异大、单文件难以覆盖）。

## 设计原则

- 每层信息有明确的职责边界，agent 可直接对接而不依赖对话历史
- 工具可替换，但信息落点位置不能长期缺位
- 信息按"谁产生、谁消费、谁维护"分配归属
