# 按场景选人机协作模式三分类对比

三个团队各自提出「拒绝单一流程适配所有需求」的分级决策框架，构成跨团队母题（review-8a8a7ec8/36ac9391 提出）。三者的维度、档位与共识分歧如下。

## 三框架并排

| 维度 | [[需求颗粒度三档协作模式]]（得物·阳凯） | [[场景严苛度分级]]（天猫新品营销） | [[自动化决策层级]]（zhiyuanfu） |
|---|---|---|---|
| **决策变量** | 需求颗粒度/复杂度 | 场景严苛度（交付质量要求） | 实现手段的不确定性成本 |
| **档位** | 三档：小颗粒 Chat 即扫即改 / 中颗粒 Rules+Skills 预设规范 / 中大颗粒 OpenSpec 标准流（SDD） | 五级+**交付分割线**：C端频道（最严苛）→B端商家平台 ‖ 小二端工作台→研发自用工具→研发 DEMO | 五层：目标层→代码层→CLI层→Prompt层→Agent层，**能在下层解决的绝不上推** |
| **核心观察** | 业务越复杂 AI 越易幻觉/需求偏移，Spec 强制先设计后编码 | 错误容忍全线≈0，分级差异实际在交互容忍/代码要求/视觉还原；分割线以下人才可以基本不介入代码 | 80% 的"AI 需求"不需要 AI（cron+curl/jq+awk 可覆盖），过度 Agent 化是过度工程 |
| **决策方向** | 需求侧：先判颗粒度再选流程 | 交付侧：先判场景严苛度再定介入深度 | 手段侧：从最底层确定性手段往上找 |

## 共识

1. **重需求才启用重流程**：三框架都把最重的基础设施（SDD 标准流 / 深度人工介入 / Agent 层）留给最高复杂度档位，低档位用最便宜的机制（对话/免介入/脚本）。
2. **确定性成本最低优先**：与得物第二篇的 [[必须遵守vs建议参考约束分层]]、腾讯 [[代码优先于prompt]] 同构——能用规则的不用提示词，能用脚本的不用 Agent。
3. **反向失控防护**：得物用 Spec 强制 Why（proposal），zhiyuanfu 用「第三天就要补 spec」底线，天猫用交付分割线锁定外部质量——三者都在防「AI 平 competence 下滑」的隐性问题。

## 分歧点

- **决策变量不可互换**：颗粒度是需求属性，严苛度是场景属性，不确定性成本是手段属性。同一个"改 CSS 间距"需求：颗粒度=小（Chat）、若发生在 C 端频道则严苛度=最苛（须深度验证）、按决策层级则是代码层/CLI 层手段——**三框架对同一需求可同时给出不同档位建议，复合使用而非互替**。
- **档位粒度差**：得物三档最粗但可操作；天猫五级有交付分割线这一硬边界；zhiyuanfu 五层是手段谱系而非需求谱系，严格说是元框架。
- **与得物第二篇 [[人类主导AI辅助三分类]] 的关系**：三分类（AI主导/人机协作/人类主导）是权责视角，与本页三框架的流程视角互补而非重复。
