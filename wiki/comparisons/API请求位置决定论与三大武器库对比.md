# API 请求位置决定论 vs 三大武器库

Skills/MCP/Rules 三机制的两套叙事张力跨多轮出现（review-cbac6241/782f7fcb 立项裁决）。

## 两套叙事并排

| 维度 | [[api请求位置决定论]]（百度·Cheer，源码视角） | [[三大武器库]]（腾讯·binxiong，工程组织视角） |
|---|---|---|
| **核心主张** | 三机制本质区别不在功能，而在信息塞入 `messages.create` 请求的**位置不同**——最终都以文本形态进入模型上下文 | 知识库让 AI"知道"、MCP 让 AI"连接"、Skills 让 AI"掌握"——**三层能力分工**协同 |
| **视角层次** | 模型视角：API 收到什么就是什么 | 工程组织视角：团队如何按职能建设与维护能力 |
| **证据基础** | v2.1.88 泄漏源码（函数名证据链，非官方口径） | codebuddy 落地实践 |
| **对"知识库"的处理** | 无此层——CLAUDE.md/Rules 归为被动注入文本 | 显式第一层（核心记忆+辅助记忆双通道、五分类） |

## 裁决：层次不同，均成立

1. **不矛盾，是同一系统的两个投影**：位置决定论回答"模型看到什么"（运行时真相），三大武器库回答"团队建什么"（建设时组织）。腾讯的三层在运行时同样坍缩为注入文本——但坍缩不否定分层对**建设、维护、权限、复用**的组织价值。
2. **位置决定论的边界**：注入位置决定的是上下文占位与触发方式（被动常驻/工具注册/按需注入），不决定工程属性（谁维护、怎么版本化、出错怎么查）——后者恰是三大武器库的领地。
3. **互补裁决规则**：调模型行为差异（触发可靠性、token 预算、缓存）→ 用位置决定论框架；做团队基建选型（知识放哪、能力怎么分层）→ 用三层架构框架。
