# 需求驱动型与工程主导型对比

需求驱动型（DO WHAT）与工程主导型（HOW TO DO）是天猫新品营销技术团队按"验收要求及实际情况"对需求做的二分分类，是其实战案例章的组织骨架：需求驱动型关注"要什么功能"，AI 自主决策技术实现；工程主导型关注"怎么实现"，人工深度参与实现方案决策。

## 七维度对比表（原文逐字保留）

| 维度 | 需求驱动型 | 工程主导型 |
|------|-----------|-----------|
| 特点 | 强调"要什么功能"；AI 自主决策技术实现；人工介入少，关注结果 | 强调"怎么实现"；人工深度参与实现方案决策；人工介入多，关注代码质量 |
| 代码规范度要求 | 低 | 高 |
| 验收标准 | 低 | 高 |
| 隐含知识量 | 低 | 高 |
| 项目复杂度 | 低 | 高 |
| AI 扮演的角色 | 功能开发者 | 编码辅助员 |
| 案例 | 小二后台页面 / 研发自用工具 | 线上 C 端页面 / 商家端页面 |

该表是"验收要求越高 → 掌控率和人工可介入空间要求越高"主张的结构化确证：验收标准行与人工介入特征严格同向。

## 双方三关注点

**需求驱动型（DO WHAT）**：①想办法完全阐明需求点，防止 AI 臆造或偏离；②要有一定的辅助手段保证代码质量、提高迭代成功率；③留出一定的人工介入空间，不要产出一堆难以介入的代码。

**工程主导型（HOW TO DO）**：①代码需要严格符合工程质量；②编写者要保留对代码大部分的掌控度，且产出内容人工可介入度高；③对复杂度高/隐含知识多的项目，解决"怎么让 AI 可以做/知道做"。

## 案例结构非镜像性

两类案例的步骤链不同构，是本对比最重要的发现：

- **需求驱动型案例链**：新建小二端列表页（三种实现风格对比表）→ 问题调试三件套（分支控制/报错调试/数据调试）→ 中型迭代案例（AI 扩写 PRD → 3.2 迭代效果对比与双结论）。
- **工程主导型案例链**：需求背景与实现拆解（服务端/前端双栏任务表）→ 前置知识准备（隐含知识三源识别＋前置文档）→ 技术方案产出（七段模板＋人工完整审查）→ 具体执行阶段·解耦实现（[[视图分离]]）→ 后期沉淀（组件沉淀/知识文档迭代/工作流沉淀四条 Skill 清单）。

后期沉淀为工程主导型独有收尾；案例章二分（需求/工程）与"开发中"节点二分（新型/迭代）为正交维度——案例一为小二端新建，案例二为小二端中型迭代，工程主导型案例经三证据聚敛（相关埋点、C 端视觉、淘内 C 端业务仓库）确认为 C 端。
